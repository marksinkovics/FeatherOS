### R1-01: A metadata block freed and re-allocated within one step loses its new contents at EndStep (the pending forget drops the step copy)

- **Slice:** journal
- **Location:** `src/fs/core/ext/transaction.cpp:691`
- **Severity:** minor (reviewer: important, confidence medium)
- **Status:** fixed (pending commit)

**Failure scenario.** ext4 volume with a journal, 4 KiB blocks, all inside one running transaction (no commit in between, so within about 5 s and below the soft limit). (1) A program creates a file and writes single blocks at every other block offset until its extent leaf X is full (340 extents). X was allocated in this transaction, so X is in the running layer and its bit is clear in the committed bitmap. (2) One write() call then covers the whole range and fills the holes. The first hole insert is a non-append split of the full leaf: two new blocks L and R are allocated, then FreeBlock(X) runs, and NoteFreedBlock puts X into pending_forgets because running holds it. (3) Later in the same WriteExtentFile call L fills up and is split too. AllocateTreeBlock calls AllocateBlock(edit.goal) with the same goal as before; the group is frozen, but X is clear in both the current and the committed bitmap, so X (the first clear bit at the goal) is handed out again. WriteTreeNode(X) puts the new left half (about 170 extents) into the step layer. (4) EndStep walks pending_forgets and calls state.step.Drop(X) and state.running.Drop(X). The new tree node is now in no layer and is never logged or written home, while the parent index that points at X is committed. Reads of that part of the file fetch whatever the disk holds at X (bad magic or checksum, Error::Corrupt, error state or remount read-only), and after the commit the on-disk extent tree references a garbage block: the data under those extents is lost. The same happens for any other free-then-allocate of a young metadata block inside one step (for example an insert before a leaf's first entry, which also replaces the leaf block, followed by another tree allocation).

**Evidence.** transaction.cpp:562-583 NoteFreedBlock adds a freed block to pending_forgets whenever running or committed holds a copy, and nothing ever removes an entry (BlockSet has no remove; pending_forgets is only cleared at 704 and 753). transaction.cpp:514-554 WriteMetadata holds a new step copy for such a block without looking at pending_forgets. transaction.cpp:688-697 EndStep then does state.step.Drop(block) and state.running.Drop(block) for every pending forget, before running absorbs the step at 703. Reuse inside the step is possible because the only guard is the committed bitmap: allocation.cpp:355-375 ORs the current bitmap with LoadCommittedBlockBitmap (transaction.cpp:585-605), and a block allocated in the still-running transaction is clear there. docs/design/M22-P6-s4.md 6.4 and I12 state "A block freed in the running transaction is not allocated again before that transaction commits", which this breaks for blocks allocated in the same transaction. A step that frees and then allocates tree blocks exists: extent_write.cpp:375 (FreeBlock(edit.frees, at.block) after a node is replaced), extent_write.cpp:187-191 (AllocateTreeBlock: FinishFrees, then AllocateBlock(edit.goal)), called repeatedly from the run loop in WriteExtentFile (extent_write.cpp:703-790) inside one Journalled step (write.cpp:1339). Not run as a test; derived from reading the code.

**Verifier.** Traced through the code; nothing prevents it. NoteFreedBlock (src/fs/core/ext/transaction.cpp:562-583) adds a freed block to pending_forgets whenever running holds a copy, and no path removes an entry before EndStep/AbortStep (704, 753). WriteMetadata (514-554) holds a new step copy without consulting pending_forgets. EndStep (688-697) then does step.Drop(block) and running.Drop(block) for each pending forget before Absorb (703), so a block freed and re-allocated as metadata in the same step is in no layer and never logged. Reuse is possible: AllocateBlocks (allocation.cpp:355-375) only ORs the current bitmap with the committed bitmap for a frozen group, and a block first allocated in the still-running transaction is clear in both after FreeBlock (allocation.cpp:611-613). This breaks I12 in docs/design/M22-P6-s4.md:568 for blocks born in the running transaction. A reachable step exists: Write is a single Journalled step for the whole buffer (write.cpp:1339, kernel core_driver.cpp:621 passes the buffer through unchunked), WriteExtentFile loops over holes (extent_write.cpp:703-784), InsertExtent ends with FinishFrees (extent_write.cpp:410) and AllocateTreeBlock runs FinishFrees then AllocateBlock(edit.goal) from the inode group's first block (187-191), so the lowest clear bit, the just-freed leaf, is handed back. Shortest trace: a leaf X created in this transaction holding 339 extents; one write() covers a hole before the leaf's first extent and one more hole. Insert 1 takes the 'count <= capacity, first key changed' branch (extent_write.cpp:316-326): new leaf N, FreeBlock(X) at 375 -> pending_forgets. Insert 2 overflows N (341 > 340) and splits (338-349): the first AllocateTreeBlock returns X, WriteTreeNode(X) puts the left half in the step layer, the root index points at X, EndStep drops it. Note the reporter's own step (3) is slightly off (after the first split it is R, not L, that overflows, and R's own free is not a pending forget), but X is still the block reused for the second split, so the outcome is the same. Result: a committed extent tree pointing at a block with stale contents (Corrupt on read, data under it lost). Graded minor per the rubric because it needs an unusual sequence: a file with hundreds of fragments (a full leaf, 340 at 4 KiB, 84 at 1 KiB) built inside one transaction (under 5 s, below the soft limit) and then one write spanning at least two holes; the consequence, though, is silent on-disk corruption. Not covered by a Known hard limit.

**Reproduction (2026-11-25).** reproduced. Test: `R1-01 a metadata block freed and allocated again within one step keeps its contents` in `src/fs/core/tests/ext_repro_tests.cpp` (tag `[R1-01]`, now a regression test; fix per `docs/design/review-E1.md`). Write returns the full count, but the read-back fails with Error::Corrupt (code 1): CHECK(read.has_value()) false at ext_repro_tests.cpp:128 (live mount) and :142 (after Sync and read-only remount). Seen for ext4 leaves of 83, 82 and 81 extents and ext4-4k leaves of 339, 338 and 337. The setup guard (no commit mid-setup) passed. Root cause: EndStep drops pending-forget blocks from the step and running layers even when the block was allocated again as metadata in the same step.

### R1-02: EndStep fails with OutOfMemory when running plus step counts exceed the layer maximum although the distinct blocks fit

- **Slice:** journal
- **Location:** `src/fs/core/ext/transaction.cpp:684`
- **Severity:** minor (reviewer: minor, confidence medium)
- **Status:** open (trace only)

**Failure scenario.** 4 KiB blocks, so each layer holds at most 1024 copies and limits.hard is 1024 on a normal journal. The running transaction holds 400 blocks (footprint below the soft limit of 512, so BeginStep does not commit), for example after removing a large fragmented file that touched 400 block bitmaps. The next step (a second large remove or truncate) touches 630 metadata blocks, 100 of which are already in running. The distinct count is 930, so neither WriteMetadata nor the check at 673-681 overflows. EndStep then calls state.running.Reserve(400 + 630); BlockLayer::Reserve refuses anything above maximum (1024) and EndStep returns Error::OutOfMemory. FailStep sees no overflow and an error other than NoSpace, so it neither commits and retries nor sets overflowed_alone: the operation fails with ENOMEM although memory and log space are sufficient, and it keeps failing on retry until the periodic commit empties the running layer. The step is rolled back, so nothing is damaged.

**Evidence.** transaction.cpp:684 reserves running.Count() + step.Count(), which counts blocks present in both layers twice and also counts blocks the pending forgets are about to drop (688-697). BlockLayer::Reserve (217-233) returns false for wanted > maximum, where maximum = JournalMemoryBytes / block_size (136). Absorb (274-292) itself reserves only count + fresh, so the stricter reservation at 684 is the only thing that fails. FailStep (760-785) retries only for overflow or NoSpace with freed groups, and the split paths in write.cpp:1340/1354 and namespace.cpp:1116/1153 trigger only on NoSpace with OverflowedAlone().

**Verifier.** src/fs/core/ext/transaction.cpp:684 reserves running.Count() + step.Count(), which double-counts blocks present in both layers and counts blocks the pending forgets are about to drop (688-697). BlockLayer::Reserve (217-221) refuses wanted > maximum = JournalMemoryBytes / block_size (136; 1024 at 4 KiB), and limits.hard is min(ring - 1, that same maximum) (1244), so the distinct-count check at 673-681 passes (it uses step_new, not step.Count()) while the reservation fails. Absorb itself needs only count + fresh (274-283). EndStep returns OutOfMemory; FailStep (760-785) sees overflowed == false and an error other than NoSpace, so it does not commit-and-retry and does not set overflowed_alone, so the WriteSplit/TruncateSplit fallbacks (write.cpp:1340, 1354) do not trigger; NoteError (write.cpp:234-239) ignores non-Corrupt errors. The step is aborted cleanly (AbortStep 709-758), so nothing is damaged: the operation fails with a spurious out-of-memory error until the next commit empties the running layer (at most 5 s, or the next step that pushes the footprint over soft). It needs running near the soft limit (up to about 510 blocks) plus a single step touching more than about 510 metadata blocks with overlap, which is an unusual, very large operation. Not a documented limit (the documented one is NoSpace for a change that does not fit in a transaction alone).

**Reproduction (2026-11-25).** Trace only. Test: `R1-02 EndStep's reservation does not count a block of both layers twice` in `src/fs/core/tests/ext_repro_tests.cpp` (tag `[.repro][R1-02]`). No host image can drive a 4 KiB step with about 775 distinct metadata blocks. The BlockLayer premise check fails as predicted: CHECK(running.Reserve(running.Count()+step.Count())) is false at ext_repro_tests.cpp:170, although the 930 distinct blocks fit in 1024. Trace: transaction.cpp:673-681 passes on distinct counts, :684 fails with OutOfMemory, FailStep (760-785) neither commits nor retries, Absorb (274-283) would have fit. This is an arithmetic check, not an end-to-end failure. Root cause: EndStep reserves running.Count()+step.Count() in the running layer, counting blocks present in both layers twice, instead of the distinct count Absorb needs.

### R1-03: A failure after the extent-tree commit makes WriteExtentFile/AppendExtentBlock free data blocks that the tree already maps

- **Slice:** alloc-extents
- **Location:** `src/fs/core/ext/extent_write.cpp:772`
- **Severity:** minor (reviewer: important, confidence medium)
- **Status:** open (reproduced)

**Failure scenario.** ext4 file whose extent tree has depth >= 1, written so that an insert replaces a tree node: a hole filled before a leaf's first extent (ReplaceExtentNode's 'first logical changed' branch) or a mid-leaf insert into a full leaf (non-append split). The new node(s) are written, the parent/root commit succeeds, and then the post-commit FreeBlock(edit.frees, at.block) of the replaced node fails: bitmap read I/O error, bitmap checksum mismatch in that group, the old tree block's bit already clear in a slightly inconsistent bitmap (Error::Corrupt), NoteFreedBlock/BlockSet OutOfMemory, or FinishFrees' CommitBitmap write failing. InsertExtent returns the error with edit.committing == false, so WriteExtentFile runs FreeBlocks(edit.frees, physical, run) on the data run that the committed tree now maps, and FinishFrees writes that bitmap. If an earlier run of the same write succeeded (written > 0), WriteFile -> FinishWrite stores the inode and returns a short count as success, so on a journalled volume the step ends and commits (no AbortStep rollback, no NoteError); on ext4 without a journal everything is already on disk. Result: a file extent pointing at blocks marked free; the next allocation hands them to another file or to metadata, giving cross-linked files and silent data corruption. AppendExtentBlock has the same pattern for directories: it frees the linked block, sets inode.size back and stores the inode, leaving a mapped block past the directory's end that is also free in the bitmap (later appends then return Corrupt at line 810, and the block can be reallocated while the directory still maps it).

**Evidence.** ReplaceExtentNode (extent_write.cpp:303-312 and 275-283) clears edit.committing and fresh_count as soon as the commit write succeeds, then on the way back up does 'if (replaced) { if (const Status freed = FreeBlock(edit.frees, at.block); !freed) return freed; }' (373-378), so an error can be returned after the tree change is durable. InsertExtent (405-414) passes that error on, and also turns a failed FinishFrees into the result ('status = finished') after a successful commit. The callers use committing == false as proof that nothing was linked: WriteExtentFile 769-778 ('// Never linked, unless the commit was tried.' -> 'if (!edit.committing && FreeBlocks(edit.frees, physical, run))') and AppendExtentBlock 836-845 ('if (!status && !edit.committing) { inode.size = logical * block_size; if (FreeBlock(edit.frees, allocated->first)) ...; StoreInode(...) }'). committing is only true while a commit write is in flight or failed, never after it succeeded. The partial-success path that persists the damage is write.cpp:1057-1063 with FinishWrite at write.cpp:1155-1181 (returns 'written' when > 0), and Journalled() in ext2_filesystem.h:762-806 only aborts the step when the change returns an error. FreeBlock's failure sources are in allocation.cpp:578-621 (LoadBlockBitmap, '!TestBit(cursor.bitmap, bit)', NoteFreedBlock) and FinishFrees/CommitBitmap 635-645.

**Verifier.** Traced for WriteExtentFile; the AppendExtentBlock half does not hold in practice.

**Reproduction (2026-11-25).** reproduced. Test: `R1-03 a failure after the extent tree committed leaves no mapped block free` in `src/fs/core/tests/ext_repro_tests.cpp` (tag `[.repro][R1-03]`). With FreeBlock of the old node forced to fail after the tree commit, the file maps blocks the bitmap shows free: ext4-nojournal 5 extents, write of 2 blocks from 0: logical blocks 0 and 1 map to blocks 9796 and 9797, with CHECK(BlockMarkedInUse) false at :277. ext4-nojournal 83 extents, write of 5 blocks from 2: logical block 5 maps to 9797. Journalled ext4-extents, the same case: logical block 5 maps to 9829. AppendExtentBlock half untested (verifier found it unreachable). Root cause: edit.committing is false after a successful tree commit, so callers read a post-commit failure as 'never linked' and free blocks the tree already maps.

The path: ReplaceExtentNode clears edit.committing and fresh_count as soon as the commit write succeeds (src/fs/core/ext/extent_write.cpp:278-282 for the root, 305-311 for an in-place node). On the way back up, each level that replaced its node calls FreeBlock(edit.frees, at.block) and returns its error (373-378). InsertExtent passes that error on (405-414); ForgetFresh does nothing because fresh_count is already 0. WriteExtentFile then sees !edit.committing and runs FreeBlocks(edit.frees, physical, run) on the data run the committed tree now maps, and FinishFrees writes that bitmap (769-777). The comment 'Never linked, unless the commit was tried' is wrong for this case: committing is false after a successful commit as well as before one.

Nothing downstream undoes it:
- No journal (ext4 without one): the tree node, root and bitmap writes are already on disk. Journalled() only calls Noted(change()) (ext2_filesystem.h:768-771), and NoteError acts only on Error::Corrupt (write.cpp:234-239), so an EIO or OutOfMemory does not even stop writes.
- Journalled, with an earlier run of the same write done (written > 0): WriteFile goes to FinishWrite (write.cpp:1057-1063), which stores the inode and returns the short count as success (1155-1181). Journalled() then runs EndStep and never reaches FailStep/AbortStep (ext2_filesystem.h:779-796), so the step with the mapped-but-freed run commits.
- Journalled with written == 0: FinishWrite returns the failure, FailStep -> AbortStep rolls the step back (transaction.cpp:714-765), so that sub-case is safe.

FreeBlock can fail at that point through LoadBlockBitmap (read error, or a bitmap checksum mismatch, which only the write path checks) at allocation.cpp:598, the old node's bit already clear or the free count full (607-610), NoteFreedBlock's set growth failing (611, transaction.cpp:575-581), or FinishFrees' CommitBitmap when the cursor moves to another group (594).

Severity lowered to minor because it needs two things together: an ext4 tree of depth >= 1 with a node-replacing insert (a hole filled before the leftmost leaf's first extent, or a mid-leaf insert into a full leaf), and a fault exactly at the post-commit free (I/O error, inconsistent or bad-checksum bitmap, or out of memory). When both happen the result is real cross-linking: an extent pointing at blocks the bitmap marks free.

AppendExtentBlock (836-845) has the same wrong assumption, but a directory append always adds at the end of the rightmost leaf. That is either the in-place branch (303-313, no free) or the 'appended' split with replaced = false (333, 366), at every level, so no post-commit FreeBlock runs and FinishFrees has nothing dirty. I could not construct a reachable failure there short of an already damaged tree.

### R1-04: Truncate zeroes the tail of the new last block in place before the truncation is committed (or even known to succeed), so a failed or crashed truncate leaves the file at its old size with zeroed data

- **Slice:** write-orphan
- **Location:** `src/fs/core/ext/write.cpp:1229`
- **Severity:** minor (reviewer: minor, confidence medium)
- **Status:** open (reproduced)

**Failure scenario.** ext3/ext4 with a journal: a 4096-byte file full of data, Truncate(file, 100). TruncateFile calls ZeroFrom, which writes bytes 100..4095 of the data block as zeros straight to the device. (a) Crash: the size change sits in the running transaction for up to 5 s (or until the soft limit); power is lost before the commit; replay finds nothing, so the file is still 4096 bytes long but bytes 100..4095 are now zeros. The truncate was neither applied nor left undone. (b) No crash: after ZeroFrom, ShrinkExtents/ShrinkBlocks fails for a reason other than a splittable overflow (Buffers for the extent tree cannot be allocated -> OutOfMemory, a damaged extent node or indirect block -> Corrupt, an I/O error reading a tree block). Journalled rolls the metadata back and Truncate returns the error, but the zeroing is not rolled back: the file keeps its old size and has silently lost everything from the requested size to the end of that block. The same happens through ShrinkBlocks on a volume without a journal when ShrinkIndirect fails after ZeroFrom.

**Evidence.** write.cpp:1227-1232 (extent path) and write.cpp:649-655 (ShrinkBlocks, block maps) call ZeroFrom before any fallible mapping work and before the size is stored. ZeroFrom (write.cpp:403-427) reads with cache.ReadUncached and writes with WriteData, which is cache.Write straight to the device (transaction.cpp:500-503), outside the journal's layers, so AbortStep (transaction.cpp:714-758) cannot undo it. The new size only reaches the disk with the transaction's commit (CommitTransaction, transaction.cpp:913). TruncateSplit (orphan.cpp:692) has the same order but stores the size and the orphan entry in the same small step, so only the crash window applies there. CLAUDE.md's stated limit covers only 'overwrites inside a file are not atomic across a crash (ordered mode)'; a truncate that did not happen destroying data past the requested size is not listed. Linux has the same class of window in ordered mode, but only between the data write-out and the commit block of the same commit, not for the whole life of the running transaction, and never on a truncate that returned an error.

**Verifier.** Traced, nothing prevents it. Truncate (src/fs/core/ext/write.cpp:1347-1359) runs TruncateFile inside Journalled. On the extent path TruncateFile calls ZeroFrom (write.cpp:1229) before ShrinkExtents and before inode.size is changed; ShrinkBlocks does the same for block maps (write.cpp:649-655). ZeroFrom (write.cpp:403-427) reads with cache.ReadUncached and writes with WriteData, which is a plain cache.Write to the device (src/fs/core/ext/transaction.cpp:500-503), outside the step/running layers. AbortStep (transaction.cpp:714-758) only restores the superblock, the group descriptors and the step's journalled blocks, so it cannot undo the zeroing. The new size is stored with StoreInode into the transaction and reaches the disk only at commit. So: (a) a crash between the zeroing and the commit (up to the 5 s interval) replays to the old size with bytes size..end-of-block zeroed; (b) a non-overflow failure of ShrinkExtents/ShrinkIndirect (I/O error or Corrupt on a tree block, OutOfMemory) returns an error with the old size kept (write.cpp:1235-1243 only sets the size when shrunk) but the tail already zeroed. The overflow retry and TruncateSplit (src/fs/core/ext/orphan.cpp:692) just repeat the idempotent zeroing, so they add no harm beyond the crash window. Not covered by a documented limit: CLAUDE.md lists only 'overwrites inside a file are not atomic across a crash (ordered mode)', which is about writes, and no design doc or roadmap text mentions truncate zeroing. Kept at minor rather than important: the lost bytes are exactly those the caller asked to discard, the loss is limited to the tail of one block, case (a) needs a crash within the commit window right after a truncate, and case (b) needs an I/O error, a damaged tree or allocation failure. An ordering fix is cheap (zero after the mapping work succeeds, or journal the tail block).

**Reproduction (2026-11-25).** reproduced. Test: `R1-04 a truncate that did not commit leaves the old size and the old bytes` in `src/fs/core/tests/ext_repro_tests.cpp` (tag `[.repro][R1-04]`). After Truncate to 1.5 blocks with no commit, a device copy replayed by a mount matches neither the old file nor the truncated one: CHECK((untouched || done)) false at :337 for both ext4 and ext3 (1 KiB). Only the crash case (a) is covered; case (b), failure after zeroing, needs fault injection and was not built. Root cause: The tail of the new last block is zeroed in place on the device before the truncation is committed or known to succeed.

### R1-05: Renaming a directory onto an empty directory in a parent already at the link limit fails with Corrupt and puts the volume in the error state

- **Slice:** namespace
- **Location:** `src/fs/core/ext/namespace.cpp:950`
- **Severity:** minor (reviewer: minor, confidence high)
- **Status:** open (reproduced)

**Failure scenario.** ext2/ext3 volume (no dir_nlink). Directory P2 holds 31998 subdirectories, so its link count is 32000 (the most mkdir allows); one of them, P2/T, is empty. Rename a directory P1/S onto P2/T. This is a legal rename (T's '..' link is replaced by S's, the net count is unchanged; Linux ext2 does not raise the count when the target exists). Here step 1 calls UpdateDirectory(P2, +1) unconditionally: DirectoryLinks(32000, +1) computes 32001 > LinkLimit() and returns nullopt, so UpdateDirectory returns Error::Corrupt. Nothing was written yet, but the error goes through Noted()/FailStep() into NoteError(Corrupt), which sets StateErrors in the superblock and, unless s_errors is 'continue', makes the mount read-only ('no more writes until e2fsck has run'); the next mount is also refused for writing by WriteRefusal ('errors are recorded; run e2fsck'). The user gets EIO instead of success and a healthy volume is flagged damaged. Variant with dir_nlink: with P2 at 65000 the same +1 collapses the count to 1 permanently (DirectoryLinks returns 1 past the limit, and the later -1 for T keeps 1), although P2 still has only 64998 subdirectories.

**Evidence.** namespace.cpp:911 skips the TooManyLinks check when `replaced` is set (correct, since the count will not grow), but namespace.cpp:948-953 still does `UpdateDirectory(to_directory, 1, false, scratch)` for every reparented directory, relying on DropLink (namespace.cpp:378) to subtract T's link at step 6. DirectoryLinks (namespace.cpp:226-229) returns nullopt for links > LinkLimit() without dir_nlink, and UpdateDirectory (namespace.cpp:246-250) maps that to Error::Corrupt. CreateNode (namespace.cpp:423) allows a parent count to reach exactly MaximumLinks = 32000, so the state is reachable. Noted() (ext2_filesystem.h:519-526) and FailStep() (transaction.cpp:783) call NoteError, which sets StateErrors and read_only (write.cpp:234-249). The existing limit test (src/fs/core/tests/ext2_tree_tests.cpp:739-752) only covers link, mkdir and a rename without a replaced target.

**Verifier.** Traced in src/fs/core/ext/namespace.cpp. RenameNode skips the TooManyLinks pre-check when a target is replaced (line 911: `!replaced && !directory_links && link_count >= MaximumLinks`), and the only other pre-check for a replaced directory is HasSubdirectoryLink (count >= 3), which 32000 passes. After BeginChange, step 1 (lines 948-953) calls UpdateDirectory(to_directory, 1, ...) for every reparented directory, replaced or not. DirectoryLinks (lines 220-229) computes 32001 > LinkLimit() (32000 without dir_nlink, line 211) and returns nullopt, which UpdateDirectory (lines 246-250) turns into Error::Corrupt. Nothing prevents it: the state is reachable because CreateNode (line 423) refuses mkdir only at count >= 32000, so a parent can sit at exactly 32000. The error is then recorded as damage: Rename (lines 1144-1162) runs RenameNode through Journalled, which without a journal returns Noted(change()) (ext2_filesystem.h:519-526, ~771) and with one calls FailStep (transaction.cpp:760-784), whose last step is NoteError(error) (no overflow, so not converted to NoSpace). ### R1-06: FAT16 rename to another spelling of the same entry deletes the source before creating the new entry, so a crash or a failed CreateEntry loses the file

- **Slice:** fat-partition
- **Location:** `src/fs/core/fat/fat16.cpp:1760`
- **Severity:** important (reviewer: important, confidence high)
- **Status:** fixed (b25283e)

**Failure scenario.** `mv readme.txt Readme.txt` (or any rename whose target name resolves to the source's own entry: a case change, or the source's short alias). Rename finds `existing` in the same slot as `source`, so `same_entry` is true. It then marks every slot of the source deleted and only afterwards calls CreateEntry. (1) Crash or power loss between the two steps: the directory has no entry for the file at all and its cluster chain is leaked, so the source is lost. (2) No crash needed: CreateEntry fails after the delete. `readme.txt` is one short entry, `Readme.txt` has mixed case so it needs a long-name entry plus a short one (2 slots). In a full root directory (FindFreeRun -> GrowDirectory returns NoSpace for the root), in a 65536-entry subdirectory, in a subdirectory whose last cluster is full on a full disk, or on any I/O error in WriteRawEntry, Rename returns the error and the file is gone with its clusters still allocated. CLAUDE.md's stated limit is that a FAT16 rename can lose the target, never the source.

**Evidence.** fat16.cpp:1695-1696 computes `same_entry`; 1760-1770: `if (same_entry) { MarkDeleted(*from_cluster, source.first_slot, source.file.slot.index); ... return CreateEntry(*to_cluster, to_name, ...); }` with no rollback when CreateEntry fails. The comment at 1758-1759 admits the crash window ("a crash can leak the file's clusters"), which contradicts the documented limit. CreateEntry's failure paths: NameTooLong/InvalidArgument are pre-checked, but FindFreeRun (807-853) returns NoSpace via GrowDirectory (780-782 root, 797-800 size cap, AllocateCluster NoSpace) and WriteRawEntry can return I/O errors. The new name can need more slots than the old one because ToShortName (names.cpp:113-140) rejects mixed case within a part.

**Verifier.** Traced. src/fs/core/fat/fat16.cpp:1695-1696 sets same_entry when the target name resolves to the source's own slot (FindEntry at 710-742 matches long or short name ignoring case). At 1760-1769 the source's slots are marked deleted (MarkDeleted, 969-988) and only then CreateEntry runs, with no rollback. CreateEntry can still fail after the delete: FindFreeRun (807-853) returns NoSpace through GrowDirectory (780-782 for the root, 797-800 at the size cap, or no free cluster), the alias loop can return Exists (941-944), and WriteRawEntry can return I/O errors. The new spelling can need more slots than the old one (a one-case 8.3 name is one slot, a mixed-case one needs a long-name entry too, per the comment at 907-908). Nothing above the driver prevents it: Files::Rename (src/kernel/files.cpp:1934-2034) only short-circuits identical paths via IsWithin at 1978-1981, and VFS::Rename (vfs.cpp:1265-1289) and CoreDriver::Rename (core_driver.cpp:710-736) pass a case change straight through. This is not covered by the documented limit: CLAUDE.md and docs/posix.md:140 say a FAT16 rename 'can lose the target, never the source', and docs/design/M30-P2.md I10 says 'A crash leaves the source's name and data intact'; the code comment at 1758-1759 admits the opposite for this path. Caveats on likelihood: the crash window is the few sector writes between MarkDeleted and the short entry's write, the no-crash loss needs a full root directory, a full disk with a full last directory cluster, or an I/O error, and the data stays on disk as a lost chain that fsck.fat can recover. Kept at important because an ordinary operation (mv readme.txt Readme.txt) breaks an explicitly stated guarantee.

### R1-07: FAT16 replacing rename frees the target before knowing the new entry can be written, so an ordinary NoSpace error (no crash) destroys the target

- **Slice:** fat-partition
- **Location:** `src/fs/core/fat/fat16.cpp:1740`
- **Severity:** minor (reviewer: minor, confidence medium)
- **Status:** fixed (b25283e)

**Failure scenario.** Root directory with no free slot holds `README.TXT` (a plain short entry) and `new.txt`. `rename("new.txt", "Readme.txt")`: FindEntry matches the existing file case-insensitively, RemoveEntry deletes it and frees its chain (one slot freed). Rename returns the error: the old target's data is gone, the rename did not happen, and no crash was involved. The documented limit only allows losing the target across a crash.

**Evidence.** fat16.cpp:1740 `RemoveEntry(existing)` runs before 1771 `CreateEntry(*to_cluster, to_name, ...)`; on failure at 1773-1776 the function just returns the error. Nothing checks beforehand that `long_entries + 1` slots are available (CreateEntry 947-951) or that an alias exists (929-944). **Verifier.** Traced. src/fs/core/fat/fat16.cpp:1740 calls RemoveEntry(existing) (991-1000: MarkDeleted then FreeChain, irreversible) before CreateEntry at 1771; on failure 1773-1776 just returns. ### R1-08: FindFreeRun keeps scanning past the 0x00 end-of-directory marker while every reader stops there, so on a directory with non-zero bytes after the marker a new entry is written where it can never be found (or exposes garbage entries)

- **Slice:** fat-partition
- **Location:** `src/fs/core/fat/fat16.cpp:836`
- **Severity:** minor (reviewer: minor, confidence medium)
- **Status:** fixed (922d2eb)

**Failure scenario.** A foreign or damaged volume whose directory has stale non-zero entries after the first 0x00 slot (FAT only guarantees the first 0x00 ends the directory; this driver itself never produces that state). Layout: [A][0x00][stale X][0x00][0x00]... Creating a long-named file needs 2 slots: slot 1 starts a run, stale slot 2 resets it, slots 3-4 are chosen. Create returns success and a node ID, but ScanDirectory stops at slot 1, so Lookup/ReadDirectory never see the file: it is silently lost and its clusters leak, and creating it again 'succeeds' again. Conversely, a one-slot create claims slot 1, which makes stale X a live entry; removing X later frees whatever cluster chain its stale first-cluster field names, which may belong to a live file.

**Evidence.** ScanDirectory ends at the first marker: fat16.cpp:668-671 `if (entry[0] == EndOfDirectory) return false;`. FindFreeRun (813-851) treats EndOfDirectory and DeletedEntry alike at 837 and on any other marker merely resets `run_length` (846-849) and continues to `++index`, with no notion that slots after the first 0x00 are logically free (and must be zeroed / the marker preserved) regardless of content.

**Verifier.** Traced. ScanDirectory stops at the first 0x00 slot (src/fs/core/fat/fat16.cpp:668-671), and every reader (ScanNames, FindEntry, ShortNameTaken, IsEmptyDirectory) goes through it. FindFreeRun (813-851) has its own loop: it treats 0x00 and 0xE5 alike at 837, resets the run on any other marker at 846-849 and keeps going up to MaximumDirectoryEntries. With [A][0x00][stale][0x00][0x00], a two-slot create picks slots 3-4, CreateEntry writes there (956-966) and returns success, and the entry is unreachable afterwards because slot 1 is still 0x00; a one-slot create fills slot 1 and makes the stale entry visible. No mount-time check rejects such a directory. It cannot arise from this driver alone: MarkDeleted writes only 0xE5 (981) and new directory clusters are zeroed (GrowDirectory comment at 777), so it needs a volume written by another implementation or damaged, with non-zero bytes after the end marker. The FAT specification allows that content (slots after the first 0x00 are free but not required to be zero), so the disk is legitimate but unusual. Minor.

### R1-09: Subdirectory scans are quadratic in the directory's cluster count: SlotSector walks the FAT chain from the first cluster for every entry index

- **Slice:** fat-partition
- **Location:** `src/fs/core/fat/fat16.cpp:619`
- **Severity:** minor (reviewer: minor, confidence high)
- **Status:** fixed (922d2eb)

**Failure scenario.** A FAT16 volume with 1-sector clusters (valid for 2-32 MiB volumes, and trivial for a hostile USB stick) holding a subdirectory of 65536 entries = 4096 clusters. One full ScanDirectory pass calls SlotSector for each index, and each call does index/16 NextCluster reads: about 65536 * 2048 = 134 million FAT sector reads for a single failed Lookup, done under the volume lock. Create does three such passes (FindEntry, ShortNameTaken, FindFreeRun), and the alias loop in CreateEntry repeats ShortNameTaken up to 9999 times when the image holds entries FOO~1..FOO~9999, i.e. on the order of 10^12 sector reads: the calling task (and everything waiting on that volume) hangs. A cyclic directory chain reaches the same 65536-entry worst case. Even an honest directory of ~10000 long-named files on such a volume costs ~12 million FAT reads per lookup miss.

**Evidence.** fat16.cpp:618-631: `std::uint32_t cluster = slot.directory; for (step = 0; step < slot.index / EntriesPerCluster(); ++step) { NextCluster(cluster) ... }` restarts at the directory's first cluster on every call. ScanDirectory (643-645) and FindFreeRun (813-815) call SlotSector once per index with no cached (cluster, cluster-number) position; MarkDeleted/ReadSlot do the same per slot. CreateEntry 930-940 loops `number < MaximumTail` (10000) over ShortNameTaken, each a full ScanDirectory. The only bound is MaximumDirectoryEntries (65536) at 614.

**Verifier.** The code is as described. SlotSector (src/fs/core/fat/fat16.cpp:604-633) restarts at the directory's first cluster and calls NextCluster index / EntriesPerCluster() times on every call; ScanDirectory (643-645) and FindFreeRun (813-815) call it once per slot index with no remembered position, and they cache only the directory sector (loaded_sector), not the chain position. NextCluster -> ReadFatEntry (418-431) does a ReadSector each time with no FAT cache inside the driver. CreateEntry's alias loop (930-940) repeats a full ShortNameTaken scan per taken tail, up to MaximumTail. The only bound is MaximumDirectoryEntries (614). The cost is real but the worst-case numbers need a volume with 1-sector clusters and a directory of thousands of clusters (or a cyclic directory chain, which hits the 65536-slot cap), and in the kernel each FAT read is a page-cache hit and not device I/O, so 'sector reads' overstates it there; fscli and host tools have no cache. On ordinary volumes (4 KiB clusters, 128 entries per cluster) a directory of a few thousand entries walks a few dozen clusters and the effect is negligible. It is a slowdown or hang under the volume lock on an unusual or hostile disk, with no data corruption, so minor.

#### R2-01: CopyToUser/CopyFromUser dereference a re-translated user page without a lock, so a concurrent heap shrink or thread join in another thread makes the kernel write through a null pointer (panic), or through a freed frame on AArch64

- **Slice:** process (also reported by files)
- **Location:** `src/kernel/process.cpp:921`
- **Severity:** important (reviewer: important, confidence high)
- **Status:** fixed (c2757ae)

**Failure scenario.** A two-thread program: thread A loops read(fd, buf, 512) (or any syscall that copies out: Wait, Pipe, Stat, Poll, ReadDirectory...) with buf inside the top heap page; thread B, on another CPU, loops sbrk(+4096); sbrk(-4096) on that page (or the buffer is on a thread stack that ThreadJoin releases). A's UserRangeWritable passes, B's ShrinkHeap clears the PTE under program.memory_lock, then A executes `*UserByte(...) = bytes[index]` where UserByte now returns nullptr. The kernel writes to virtual address 0 in ring 0, which the x86-64 handler treats as a fatal exception (ReportFatalException), so an unprivileged program panics the kernel. On AArch64, ShootDownUserMappings is empty, so the frame is freed at once: a pointer UserByte returned just before the unmap is then written (CopyToUser) or memcpy'd from for up to a page (CopyFromUserPaged in PresentFramebuffer) after the frame may belong to another process or the kernel.

**Evidence.** CopyToUser (process.cpp:912-924) and CopyFromUser (898-910) first call UserRangeWritable/Readable, then per byte call UserByte() again and dereference the result unchecked; UserByte (853-864) returns nullptr when TranslateUserPage fails. None of these take program.memory_lock. ShrinkHeap (1302-1322) and ReleaseStackSlot (1337-1346) unmap pages under memory_lock only and then free the frames (1271-1282). Threads of a process run on different CPUs (docs/development.md 'Threads'). TranslateUserPage (arch/x86_64/virtual_memory.cpp:387) takes no lock. Kernel-mode faults fall through to ReportFatalException (arch/x86_64/exceptions.cpp:558-600, only ring-3 faults terminate the program). arch/aarch64/virtual_memory.cpp:491 `void ShootDownUserMappings(const AddressSpace&) {}` means nothing delays FreePageFrame there; on x86-64 the IPI wait happens to hold the free back while the copier has interrupts masked, but the null dereference remains.

**Verifier.** Traced. #### R3-01: AArch64: frames unmapped from a process are freed with no synchronization against another thread's in-kernel copy through the direct map

- **Slice:** futex-memory
- **Location:** `src/kernel/arch/aarch64/virtual_memory.cpp:491`
- **Severity:** important (reviewer: important, confidence medium)
- **Status:** fixed (c2757ae)

**Failure scenario.** AArch64, SMP, a two-thread process. Thread A is in a syscall that copies from or to user memory: UserByte translates the page with TranslateUserPage (no lock, no pin) and returns a direct-map pointer, then CopyFromUserPaged memcpy's up to 4 KiB through it (or CopyToUser stores a byte through it). Thread B on another CPU calls ExtendHeap with a negative increment (or joins a thread, ReleaseStackSlot) covering that page: UnmapUserPage clears the entry, ShootDownUserMappings returns at once, FreePageFrame releases the frame. Any CPU can now allocate the frame (another process's page, a page table, kernel heap or stack growth) while A is still reading or writing it through the direct map: A reads another owner's data into its syscall buffer (for example into a file it can read back), or writes a user-chosen byte into a frame the kernel now uses. The window is the length of one page memcpy for the paged read and a few instructions for the byte-wise copies, so it needs deliberate racing or a vCPU that is descheduled by the host in between, but nothing bounds it. On x86-64 the same sequence is held off only incidentally: syscalls run with IF=0 (interrupt gate 0xEE, exceptions.cpp:262) and the shootdown waits for an IPI acknowledgement from every CPU running the address space, so B cannot free until A leaves the syscall or blocks.

**Evidence.** aarch64/virtual_memory.cpp:489-491: 'void ShootDownUserMappings(const AddressSpace&) {}', justified by the broadcast TLBI, which only covers user-virtual translations. process.cpp:1271-1282 (FreeUnmappedFrames) frees right after it; callers ShrinkHeap (process.cpp:1287-1325) and ReleaseStackSlot (process.cpp:1330-1348) drop memory_lock first. process.cpp:853-864 (UserByte) and 954-971 (CopyFromUserPaged), 898-924 (CopyFromUser/CopyToUser) access user memory through PhysicalBytes of a TranslateUserPage result without memory_lock or any reference on the frame. virtual_memory.h:40-41 states the contract as 'another CPU running the address space may still reach it' until the shootdown, which does not hold for direct-map users on AArch64. The fix lies partly in process.cpp (outside this slice): either the copies or the free must be serialized.

**Verifier.** Traced on AArch64. src/kernel/arch/aarch64/virtual_memory.cpp:489-491 ShootDownUserMappings is empty; the broadcast TLBI in UnmapUserPage only removes user-virtual translations. FreeUnmappedFrames (process.cpp:1271-1282) frees the frames right after it, and ShrinkHeap (process.cpp:1287-1325) and ReleaseStackSlot (process.cpp:1330-1348) have already dropped memory_lock. The copy side holds nothing: UserByte (process.cpp:853-864) calls TranslateUserPage (aarch64/virtual_memory.cpp:405-433, lock-free walk) and returns a direct-map pointer; CopyFromUserPaged (process.cpp:954-971) memcpy's up to a page through it, CopyFromUser/CopyToUser (process.cpp:898-924) translate then dereference per byte. No memory_lock, no frame reference, no global syscall lock. So a second thread of the same process on another CPU can unmap and free the frame while the first still reads or writes it through the direct map; once reallocated, the reader copies another owner's data (it can write() it to a file and read it back) or CopyToUser stores a byte into a frame the kernel or another process now owns. The contract comment at src/kernel/memory/virtual_memory.h:40-45 does not cover direct-map users. On x86-64 the IPI-acknowledged shootdown (arch/x86_64/virtual_memory.cpp:511-536) holds the free off only if the copying CPU has interrupts disabled, so that side is incidental, as reported. Kept important: any two-thread user program on AArch64 can drive it (heap shrink via ExtendHeap is ordinary libc behaviour) and the result is an isolation break or kernel memory corruption; the window is narrow (one page memcpy, or a few instructions) so it needs deliberate racing, but nothing bounds it. Not a documented limit.

**Reproduction (2026-11-25).** Trace only. AArch64-only, in process.cpp and arch/aarch64/virtual_memory.cpp, neither in the host build. UserByte (process.cpp:853) or CopyFromUserPaged (954-971) holds a direct-map pointer; another CPU's ShrinkHeap or ReleaseStackSlot unmaps (1311, 1340); FreeUnmappedFrames (1271) calls Memory::ShootDownUserMappings, which is empty on AArch64 (virtual_memory.cpp:491), then FreePageFrame (1280). The frame can be reallocated while the copy still uses it. x86-64 is protected by IF=0 plus the acked IPI shootdown (arch/x86_64/virtual_memory.cpp:511-536). Needs a QEMU aarch64 SMP stress case. Root cause: User copies re-translate pages per byte with no lock or pin, racing an unmap in another thread of the process

#### R4-03: AbortCommand writes CRCR as two dwords, so the high-dword write can zero the command ring pointer once the ring has stopped

- **Slice:** xhci-usb
- **Location:** `src/kernel/usb/xhci/controller.cpp:787`
- **Severity:** minor (reviewer: minor, confidence low)
- **Status:** open (reproduced)

**Failure scenario.** Real hardware with a 64-bit capable controller (ac64_) and the command ring allocated above 4 GiB. A command times out after 5 s (for example Address Device to a flaky device) and AbortCommand runs. The low-dword write with CA aborts the command and the controller clears CRR. The high-dword write of 0 then arrives with CRR = 0, so the controller takes it as a new upper half of the Command Ring Pointer. On the next command doorbell the controller fetches TRBs from the wrong physical address: every later command times out or the controller raises a host system error, which costs the single permitted restart or disables USB. The same pointer overwrite, including the low half, happens if CRR was already 0 when the abort is written, for example when the completion event was lost. Linux hit this same race and now writes only the low dword when aborting.

**Evidence.** controller.cpp:787: `hardware_.Write64(operational_ + Op::CommandRing, CommandRingControl::CommandAbort);`. probe.cpp:61-65: Write64 is `Write32(offset, low); Write32(offset + 4, high);`. xHCI 5.4.5: the Command Ring Pointer field is ignored only while CRR = 1; written with CRR = 0, it is used for the next command fetch. controller.cpp:349-351: the command ring is allocated with `below = UINT64_MAX` when ac64_ is set, so it can lie above 4 GiB. controller.cpp:797-798: the code assumes the controller resumes after the aborted command and never rewrites the pointer.

**Verifier.** Traced. AbortCommand writes CRCR with hardware_.Write64(..., CommandAbort) (src/kernel/usb/xhci/controller.cpp:787), and Write64 is two 32-bit writes, low then high (src/kernel/usb/xhci/probe.cpp:61-65). The low write (0x4) aborts and the controller clears CRR; the high write of 0 can then arrive with CRR=0, when the Command Ring Pointer field is writable (xHCI 5.4.5), zeroing the upper half of the pointer. The command ring comes from AllocateDma with below=UINT64_MAX when ac64_ is set (controller.cpp:349-351), so it may sit above 4 GiB, and controller.cpp:797-798 never rewrites the pointer after an abort. Nothing in the code guards against this; the only other CRCR write is at setup (controller.cpp:401). This matches the known Linux bug fixed by writing only the low dword on abort. If the ring is below 4 GiB the high write is harmless, and if CRR was already 0 the low write also clears the low pointer bits. Minor: needs real hardware, a 64-bit controller with the ring above 4 GiB, and a 5 s command timeout; the result is failing commands or a controller error and restart, not memory corruption in the kernel.

**Reproduction (2026-11-25).** reproduced. Test: `R4-03: the command ring still works after a command was aborted` in `tests/unit/repro/usb_repro_tests.cpp` (tag `[.repro][R4-03]`). After fixing test setup (wrapper lifetime; AbortCount>=1 since the broken ring also causes a second abort during retries), REQUIRE( rig.fake.Addressed().size() == 1 ) failed: 0 == 1. The low-then-high Write64 of the CRCR abort zeroes the Command Ring Pointer high dword once CRR dropped, so the next Enable Slot TRB is not fetched. Caveat: the fake models CRR only through held_, and needs a low-first Write64 wrapper to match production probe.cpp:61-65. Root cause: AbortCommand writes CRCR with a two-dword Write64, so the high dword overwrites the Command Ring Pointer after CRR drops

**Verifier.** Traced and found nothing that prevents it. src/kernel/usb/hid/driver.cpp:451-453 sets transfer_length to the interrupt IN endpoint's max packet size (capped at MaxReportBytes = 64, report.h:13), and driver.cpp:475 uses it as every slot's transfer length. OnReport (driver.cpp:243-262) passes each completion straight to HandleReport with no reassembly. On the first piece, ExtractKeyboard/ExtractMouse return false as soon as ReadBits fails for a field past the end (report.cpp:703-707, 763-767, bounds check at 577), so the whole report is dropped when a relevant field of that report ID lies past the first packet; if all relevant fields fit in the first packet, that piece parses correctly. The tail is then parsed as a fresh report: with report IDs its first byte is taken as the ID (report.cpp:609-614), usually matching nothing but possibly another report; without IDs its bytes are read as the leading fields, giving phantom buttons or movement when it is long enough. The xHCI side only bounds length against the buffer (xhci/transfer.cpp:80-83) and the slot buffers are already 64 bytes (driver.cpp:458). Not a documented limit: neither CLAUDE.md's hard limits nor the HID paragraph at docs/development.md:342 mention single-packet reports. #### R4-05: x86-64 virtio-blk accepts a legacy queue larger than the 256 entries its ring layout assumes

- **Slice:** block-virtio
- **Location:** `src/kernel/arch/x86_64/block_device.cpp:226`
- **Severity:** minor (reviewer: minor, confidence medium)
- **Status:** open (trace only)

**Failure scenario.** QEMU is started with a legacy virtio-blk device whose queue is larger than 256, e.g. `-device virtio-blk-pci,queue-size=1024`. A legacy device fixes the queue size and derives the ring layout from it, so it expects the available ring at offset 16*1024 and the used ring at offset 20480 from the PFN. The driver allocated only 3 pages (12288 bytes) and laid the rings out for 256 entries. On the first request the device reads its available ring from memory past the allocation (whatever frame follows) and writes used-ring entries into frames the driver does not own. The driver polls its own used index at offset 8192+2, which never changes, so it spins 2^31 pause-polls with interrupts off and then marks the disk failed. Result: corruption of unrelated physical memory, a long boot stall, and no disk.

**Evidence.** block_device.cpp:226 refuses only `PortIo::Read16(device_io_base + VirtioQueueSize) < QueueSize`, so any size >= 256 passes. QueueSize = 256 is hard-coded into AvailableOffset, UsedOffset and QueuePageCount = 3 (lines 31-38). The PFN is written at line 253, and the legacy interface has no register to tell the device a smaller size. The virtio-net glue checks equality for the same register (arch/x86_64/virtio_net.cpp:96, `!= virtqueue.Size()`), which is the correct test. Not run: QEMU's default virtio-blk queue size is 256, so only a non-default `queue-size` reaches this.

**Verifier.** src/kernel/arch/x86_64/block_device.cpp:226 refuses only a device queue smaller than 256 (`Read16(VirtioQueueSize) < QueueSize`); the layout (lines 31-38: AvailableOffset 4096, UsedOffset 8192, QueuePageCount 3) and AllocateQueue (lines 91-113, 3 frames) are fixed for 256, and the legacy PFN write at line 253 gives the device no way to learn a smaller size, so the device uses its own size for the layout. Nothing else checks the size. With queue-size=512 the device's available ring is at offset 8192 (the driver's used ring, always zero) and its used ring starts at 12288, just past the allocation; with 1024 the available ring is at 16384, outside the 3 frames. In both cases the device never sees the driver's available index, so the first request polls to PollLimit (2^31, line 152-157) and the disk is marked failed: a long boot stall and no disk are certain. Writes into foreign frames are only possible for 1024 and only if the frame after the allocation holds a non-zero value at the device's available-index position, so the memory-corruption part is conditional, not guaranteed. Only reachable with a non-default QEMU `queue-size` (default is 256); the AArch64 MMIO driver is not affected because it writes its own size (aarch64/block_device.cpp:109, 150). Not a documented limit.

**Reproduction (2026-11-25).** Trace only. src/kernel/arch/x86_64/block_device.cpp is not in featheros_unit_tests. Trace at block_device.cpp: line 226 `Read16(VirtioQueueSize) < QueueSize` accepts 512 or 1024, but the ring layout is fixed at 256 entries (avail at 4096, used at 8192, 3 frames, lines 31-38 and 91-113). Trace is in the comment block of tests/unit/repro/block_repro_tests.cpp. Root cause: legacy virtio queue-size check uses `<` instead of `!=` while the ring layout is fixed at 256 entries

#### R4-07: NVMe controller keeps a dangling Disk pointer for a namespace removed at revalidation and passes it to Remove again when the controller dies

#### R5-01: Closing a socket while another thread is blocked in a call on it frees the socket under that thread (use-after-free, or a wait that never ends)

- **Slice:** sockets-dns
- **Location:** `src/kernel/network/socket.cpp:583`
- **Severity:** important (reviewer: important, confidence medium)
- **Status:** fixed (ab65465)

**Failure scenario.** A process with two threads (threads share ProcessRecord::files). Thread A calls recvfrom() on a UDP socket with no receive timeout and blocks. Thread B calls close() on the same descriptor. The descriptor held the only OpenFile reference, so Files::Close calls Sockets::Close, which unlinks the socket and frees both the Socket and its datagram queue without waking anyone. Thread A stays blocked on the address of the freed socket's wait queue. When it is woken later (a signal such as Ctrl+C, a receive timeout, or a WakeAll on a new object allocated at the same address), it re-takes socket_lock and reads socket->queue_length, pending_error and socket->queue from freed, possibly reused heap memory. It can then copy up to 1480 bytes of whatever now sits at the old queue address to user space and write queue_start/queue_length into a reused allocation. The same happens with accept() on a listener closed by another thread (socket.cpp:804), and with a blocking connect/send/recv on a TCP socket: Close orphans the socket and the TCP task frees it in ServiceTcp (socket.cpp:1237-1252) while the caller still waits on socket->waiters. The race also exists without blocking on SMP, between FindSocket returning and the call taking socket_lock.

**Evidence.** Files::FindSocket (src/kernel/files.cpp:1413-1430) returns the raw Socket* from the slot and drops table_lock without taking a reference. Every socket syscall in src/kernel/process.cpp (ReceiveFromSyscall 2557-2577, SendToSyscall, ConnectSyscall 2580-2594, AcceptSyscall 2604-2643, the read/write paths at 1693 and 1764) then uses that pointer for a call that can block. Files::Close (files.cpp:1490-1504) detaches the slot and DropReferenceLocked calls Network::Sockets::Close(file->socket) on the last reference (files.cpp:244-248). Sockets::Close (socket.cpp:583-621) does UnlinkLocked + Free (Memory::Deallocate of socket->queue and the socket, socket.cpp:120-132) with no ChangedLocked/WakeAll and no check for callers in progress. The blocked loops re-read the socket after WaitOn returns: socket.cpp:896-930 (datagram receive), 786-805 (Accept), 415-453 (SendStream), 461-502 (ReceiveStream), 728-737 (Connect). Scheduler::WaitOn (src/kernel/scheduler.cpp:560-585) only records the queue's address, so nothing keeps the socket alive. The same file already guards this case for another descriptor kind: FramebufferHold in process.cpp:1578-1597 ('so a racing close in another thread cannot free what the call owns', Files::HoldFramebuffer increments references at files.cpp:1367); sockets have no equivalent. Not run; found by reading the code.

**Verifier.** Traced, nothing prevents it. Files::FindSocket (src/kernel/files.cpp:1413-1430) copies slot->file->socket and releases table_lock without touching file->references; there is no socket counterpart to HoldFramebuffer (files.cpp:1355-1367, the only descriptor kind that pins for a blocking call, used via FramebufferHold at src/kernel/process.cpp:1582-1603). Threads use the process as the syscall context (process.cpp:662, ThreadRecord::process), so they share process->files. Files::Close (files.cpp:1490-1504) detaches the slot and the last reference reaches Network::Sockets::Close(file->socket) (files.cpp:244-248). Sockets::Close (src/kernel/network/socket.cpp:583-621) does UnlinkLocked + Free (socket.cpp:120-132, deallocating socket->queue and the socket) with no WakeAll and no in-use check; the comment at socket.cpp:119 ('The socket is unlinked, so nothing else can reach it') is the unmet assumption. A thread blocked in ReceiveFrom (socket.cpp:896-916) sleeps in Scheduler::WaitOn, which only stores &queue (src/kernel/scheduler.cpp:560-585); when woken by a signal or the SO_RCVTIMEO deadline it re-takes the global socket_lock and evaluates socket->queue_length / pending_error / read_shut from freed memory before it ever reaches the Interrupted check, and can go on to copy from socket->queue and write queue_start/queue_length (socket.cpp:917-929). socket_lock serialises the accesses but does not keep the object alive. The same pattern applies to every FindSocket caller in process.cpp (1696, 1767, 2514-2818). Reachable by any unprivileged two-thread program (16 threads per process are supported); effect is a kernel heap use-after-free with a possible read of reused kernel memory to user space and a write into a reused allocation. I did not verify the TCP orphan/ServiceTcp variant line by line, but the UDP path alone suffices. Not run, read-only trace.

**Reproduction (2026-11-25).** reproduced. Test: `R5-01 a socket stays allocated while a receive blocked on it has its descriptor closed` in `tests/unit/repro/process_lifetime_repro_tests.cpp` (tag `[R5-01]`). Root cause: Files::FindPipe/FindMaster/FindSocket return the raw object without pinning the OpenFile, so a close in another thread frees it under a blocked call

#### R5-02: With a closed receive window, every segment not at exactly receive_next is dropped before its ACK field is read, so our own sent data can never be acknowledged

- **Slice:** tcp
- **Location:** `src/kernel/network/tcp_connection.cpp:342`
- **Severity:** minor (reviewer: important, confidence medium)
- **Status:** open (reproduced)

**Failure scenario.** A guest program writes a large amount on a connection while not reading (for example it uploads to a peer that streams data back). The peer fills our 256 KiB receive ring exactly to the advertised edge, so ReceiveWindow() returns 0. The peer then starts zero-window probing with one byte past the edge, which advances its snd_nxt to receive_next+1 (FeatherOS itself does this, tcp_connection.cpp:756-776, and so do BSD-derived stacks such as QEMU's slirp). From then on every pure ACK the peer sends for our data, and every window update, carries seq = receive_next+1. Acceptable() returns false for them (window == 0 requires first == receive_next), Receive() only sets acknowledgment_pending and returns, and ProcessAcknowledgment is never reached. send_unacknowledged never advances, the send ring never drains, the writer stays blocked, and after DataRetries (8) timeouts OnTimer resets the connection with ETIMEDOUT although the peer is alive and acknowledged everything. A correct stack would keep sending while the peer keeps reading.

**Evidence.** tcp_connection.cpp:340-344: `if (length == 0) return window == 0 ? first == receive_next : in_window(first);` and `return window != 0 && (...)` for segments with data. tcp_connection.cpp:212-223: an unacceptable segment only sets acknowledgment_pending and returns, before the ACK processing at line 250. RFC 9293 3.10.7.4 requires that with RCV.WND zero 'special allowance should be made to accept valid ACKs, URGs, and RSTs'; there is no such allowance. The peer's sequence past the edge follows from NextSegment's probe path (lines 756-776: usable forced to 1, send_next += count) and line 813 (`WriteHeader(segment, send_next, TcpAck)` for pure ACKs). The retry limit that then kills the connection is at lines 677-685.

**Verifier.** Traced through src/kernel/network/tcp_connection.cpp. ReceiveWindow() (958-976) returns 0 once the peer has filled the ring to advertised_edge and the reader has not freed at least min(limit/2, send_mss). Acceptable() (340-344) then accepts a zero-length segment only at first == receive_next, and Receive() (212-223) returns for an unacceptable segment before ProcessAcknowledgment at line 250, so its ACK field and window are never read. Nothing else processes the ACK. A FeatherOS peer does send from receive_next+1: OnTimer's persist branch (664-670) sets send_next = send_unacknowledged, NextSegment sends the 1-byte probe and advances send_next (756-776), and pure ACKs use send_next (813). So between two FeatherOS endpoints (including the guest's own 127.0.0.1/::1 loopback) every ACK for our data is dropped while our window is closed, send_unacknowledged stalls, and after DataRetries = 8 (677-685) the connection is reset with ETIMEDOUT. RFC 9293 3.10.7.4's allowance for valid ACKs at zero window is missing. Downgraded to minor: it needs a program that writes more than the 256 KiB send ring while leaving more than 256 KiB unread for the whole retry period (poll-based relays like nc read and reopen the window, after which in_window(receive_next+1) holds), the effect is limited to that one connection, and the claim about slirp is doubtful: classic BSD tcp_output does not advance snd_nxt for a forced probe while the persist timer runs and sends pure ACKs from snd_nxt, so those would be at receive_next and accepted (I could not check slirp's source here). Linux probes from snd_una-1 and is unaffected.

**Reproduction (2026-11-25).** reproduced. Test: `R5-02 an ACK for our data is processed while our receive window is closed` in `tests/unit/repro/network_repro_tests.cpp` (tag `[.repro][R5-02]`). Real target run, failing at network_repro_tests.cpp:115: REQUIRE(Writable() == TcpMaximumBufferSize) with 262139 == 262144. A pure ACK at seq=receive_next+1 is dropped while the window is 0, so send_unacknowledged never advanced. Root cause: Acceptable() rejects zero-length segments at seq != receive_next when the receive window is 0, and Receive() returns before ProcessAcknowledgment, so valid ACKs are ignored with a closed window

#### R5-03: Zero-window probing never times out when the peer stops answering, so a connection (also an orphaned one) and its send ring live forever

- **Slice:** tcp
- **Location:** `src/kernel/network/tcp_connection.cpp:664`
- **Severity:** minor (reviewer: important, confidence medium)
- **Status:** open (reproduced)

**Failure scenario.** A remote peer connects to httpd (or any server), requests data, advertises a zero window (in its SYN or in an ACK) and then goes silent or disappears. The server writes up to 256 KiB into the send ring and closes the socket; socket.cpp:601-615 orphans the connection in FIN-WAIT-1 and waits for it to become Idle. On every timer expiry OnTimer takes the persist branch (send_window == 0 and send_buffer.length != 0), sets probe_pending and returns before `++retries`, so the retry limit is never reached; the probe is repeated every rto (capped at 60 s) forever. The Socket, the TcpConnection and up to 256 KiB of ring are never freed. Repeating this costs the attacker no ongoing state or traffic and exhausts kernel heap. The same path leaves a local writer blocked forever on a peer that crashed with its window closed.

**Evidence.** tcp_connection.cpp:663-670: the comment says the probe continues 'for as long as the peer answers', but the branch returns false without counting anything; `retries` is only incremented at line 677, after this return. Nothing else bounds the persist state: retries is reset at line 372 and deadline is re-armed at lines 781-791. Orphan() (lines 898-905) only bounds FIN-WAIT-2, and ServiceTcp (socket.cpp:1237) frees an orphaned socket only once the connection is Idle (state Closed).

**Verifier.** tcp_connection.cpp:664-670: the persist branch sets probe_pending and returns before `++retries` at 677, so an unanswered probe is never counted; NextSegment re-arms deadline (781-783 after the probe, 789-791 otherwise) and rto is capped at MaximumRto 60 s (658), so probing repeats forever. The comment at 663 ('for as long as the peer answers') is not what the code does. send_window can be 0 from the start (Accept line 189 takes the SYN's window; line 361 the ACK's). Orphan() (898-905) bounds only FinWait2, and ServiceTcp frees an orphaned socket only when connection->Idle() (socket.cpp:1237), which FinWait1 with a closed peer window never reaches; socket.cpp:601-615 orphans on close without any timeout, and I found no cap on the number of sockets or orphans in socket.cpp. So a peer that advertises a zero window and goes silent pins the Socket, TcpConnection and up to 256 KiB of send ring forever, and a local writer to a crashed peer with a closed window blocks indefinitely. Not listed in Known hard limits or docs (roadmap M10 Part 5 only says 'zero-window probes'). Downgraded to minor: the effect is a resource leak / denial of service rather than a crash, memory error or data loss, and a peer that merely keeps answering probes (which RFC 9293 requires us to tolerate indefinitely) can pin the same memory at one ACK per 60 s, so the missing unanswered-probe limit adds little to what a hostile peer can already do without a connection or orphan cap.

#### R5-04: The SYN adjustment in ACK processing fires again when send_unacknowledged wraps to the initial sequence number, leaving one acknowledged byte in the send ring

- **Slice:** tcp
- **Location:** `src/kernel/network/tcp_connection.cpp:378`
- **Severity:** minor (reviewer: minor, confidence low)
- **Status:** open (reproduced)

**Failure scenario.** A connection sends more than 4 GiB. If an ACK leaves send_unacknowledged exactly equal to initial_send_sequence (2^32-1 stream bytes acknowledged at a segment boundary; a peer can also choose to acknowledge exactly that point), the next ACK is treated as if it covered the SYN: `--acknowledged` drops one byte fewer from send_buffer than was acknowledged. send_unacknowledged still advances by the full amount, so every later offset into the ring (send_next - send_unacknowledged) is off by one: the stream sent from then on is shifted by one byte (silent corruption of the data the peer receives). If that ACK was the one covering our FIN, `acknowledged > send_buffer.length` is false, fin_acknowledged is never set and the close runs into the retransmission timeout.

**Evidence.** tcp_connection.cpp:376-387: `uint32_t acknowledged = acknowledgment - send_unacknowledged; if (send_unacknowledged == initial_send_sequence) { --acknowledged; } ... BufferDrop(&send_buffer, Smaller(acknowledged, send_buffer.length)); send_unacknowledged = acknowledgment;`. The test compares 32-bit sequence numbers, which repeat every 2^32 bytes, instead of checking the state (the SYN can only be outstanding in SynReceived, where this function is entered at line 351). In a full-MSS stream the boundary is rarely hit (2^32-1 is not a multiple of 1460 or 1440), so it needs irregular segment sizes or a peer that picks the ACK value.

**Verifier.** tcp_connection.cpp:376-387: the SYN adjustment tests `send_unacknowledged == initial_send_sequence` on 32-bit sequence numbers with no state check. Start() sets send_unacknowledged = initial_sequence (line 130) and only the SynReceived path (351-362) legitimately reaches this with the SYN outstanding (the SynSent path sets send_unacknowledged directly at 319). After 2^32 sequence numbers, an ACK that leaves send_unacknowledged exactly equal to initial_send_sequence makes the next ACK execute `--acknowledged`, so BufferDrop removes one byte fewer than acknowledged while send_unacknowledged advances by the full amount (387). From then on NextSegment's offset = send_next - send_unacknowledged (763) and the fast-retransmit copy from offset 0 (744) read the ring one byte early, so the peer receives a shifted stream; Unsent()/the FIN test at 795 and `acknowledged > send_buffer.length` (382) are off by one too, so the FIN is never seen as acknowledged. Nothing resets or guards the comparison. A peer may acknowledge any point up to send_maximum (363-371), so it can pick that value, but that only corrupts its own inbound data; with an honest peer it needs more than 4 GiB on one connection and a cumulative ACK landing on that exact byte. Rare and limited to one connection, so minor stays.

**Reproduction (2026-11-25).** reproduced. Test: `R5-04 the SYN adjustment does not fire again after the sequence space wraps` in `tests/unit/repro/network_repro_tests.cpp` (tag `[.repro][R5-04]`). After sending and acking 2^32-1 bytes so send_unacknowledged equals the ISS again, then acking 10 more bytes, :204 REQUIRE(Writable() == TcpMaximumBufferSize - (written_total - acked_total)) gives 262143 == 262144. One acked byte stays in the ring. The test needs 8.1M assertions and about 70 s in the real ASan target; the whole 4-test run took 71 s. Root cause: The SYN adjustment (tcp_connection.cpp:378) compares send_unacknowledged == initial_send_sequence on 32-bit sequence numbers with no state check, so it fires again after the sequence space wraps

#### R5-05: IPv4 input accepts packets from the wire whose source is a loopback address or our own address

- **Slice:** ip-layers
- **Location:** `src/kernel/network/ip.cpp:249`
- **Severity:** minor (reviewer: minor, confidence medium)
- **Status:** open (trace only)

**Failure scenario.** A host on the LAN sends an Ethernet frame to our MAC carrying an IPv4 UDP datagram with source 127.0.0.1 (or our own configured address) and destination our configured address. ParseIpv4Packet accepts it and HandleIpv4 sets to_us because the destination matches, then HandleUdp passes it to Sockets::DeliverUdp. Any UDP socket bound to the wildcard address on that port receives the datagram with a peer address of 127.0.0.1, so a program that treats loopback peers as local (recvfrom source check, or a socket connected to 127.0.0.1:port) is spoofed from the network. Replies the program sends then go to the local loopback path instead of the sender. TCP segments with such a source also reach DeliverTcp, and the SYN-ACK or RST they provoke is looped back locally.

**Evidence.** src/kernel/network/ip.cpp:244-277 (HandleIpv4) checks only the destination: to_us at 249-250, the drop test at 253-257, then dispatches to HandleIcmp/HandleUdp/HandleTcp with packet.source unchecked. src/kernel/network/ipv4.cpp:16-42 (ParseIpv4Packet) does not look at the source either. The only source check is IsUnicastIpv4Source at ip.cpp:234-241, which is used solely to decide whether to send a port-unreachable error (ip.cpp:266), and it does reject a loopback source from the wire there, which shows the case is known. The IPv6 path has the filter: ip.cpp:327-331 drops ::1 as source or destination when source_mac is not null. src/kernel/network/socket.cpp:1071-1092 (DeliverUdp) matches a wildcard-bound socket on the destination port and enqueues with the spoofed source.

**Verifier.** Traced, nothing prevents it. The wire path (src/kernel/network/ip.cpp:486-488) calls ParseIpv4Packet, which never inspects the source (src/kernel/network/ipv4.cpp:16-42), then HandleIpv4 with a non-null source_mac. HandleIpv4 (ip.cpp:244-277) computes to_us from the destination only (249-250) and its drop test (253-257) is also destination-only, so a frame with source 127.0.0.1 or our own address and destination our configured address reaches HandleUdp (ip.cpp:264) and HandleTcp (ip.cpp:273) with the source unchecked. Sockets::DeliverUdp (src/kernel/network/socket.cpp:1071-1092) matches a wildcard-bound socket on port and version, and a connected socket only on remote address and port, so a socket connected to 127.0.0.1:p with an unspecified local address accepts the spoofed datagram. The only loopback-source test, IsUnicastIpv4Source (ip.cpp:234-241), gates just the port-unreachable reply (ip.cpp:266). The IPv6 path does filter this (ip.cpp:327-331), so the IPv4 omission is an inconsistency, not a design choice; neither CLAUDE.md's hard limits nor docs/development.md lists it. It breaks RFC 1122 3.2.1.3 (a 127/8 address must not appear outside a host). Severity stays minor: it needs a hostile host on the same link, there is no crash or memory error, and the effect is limited to a spoofed peer address plus replies looped locally. #### R5-06: getaddrinfo's UDP wait restarts its timeout on every unrelated datagram, so a lookup can be held forever from the network

- **Slice:** sockets-dns
- **Location:** `src/libc/netdb.cpp:298`
- **Severity:** minor (reviewer: minor, confidence medium)
- **Status:** open (trace only)

**Failure scenario.** A program calls getaddrinfo("example.org", ...). AskOverUdp sends the query from an unconnected UDP socket on an ephemeral port; the kernel hands out ports sequentially from 49152 (PickPortLocked), so the port is predictable. Any host that can reach the machine sends one UDP datagram to that port at least every timeout_seconds (2 s by default). Each datagram fails the SameEndpoint check, or comes from the server with a different ID and parses as Unrelated, and the loop calls recvfrom again with a fresh full SO_RCVTIMEO. recvfrom never returns the timeout error, so AskOverUdp never returns and getaddrinfo (also getnameinfo) hangs for as long as the datagrams keep coming, instead of ending after attempts x servers x timeout.

**Evidence.** src/libc/netdb.cpp:293 sets SO_RCVTIMEO once; the for(;;) at 298-319 leaves only when recvfrom fails (305-308) or a response parses to something other than Unrelated (313-317). The '!SameEndpoint -> continue' branch (309-312) and the Unrelated branch (318) loop with no overall deadline and no count. In the kernel, the timeout is per call: ReceiveFrom computes ReceiveDeadline(socket) on entry (src/kernel/network/socket.cpp:894), and an unconnected UDP socket queues datagrams from any source (DeliverUdp, socket.cpp:1077-1088). Dns::ParseResponse returns Unrelated for a wrong ID or a non-response (src/libc/dns_message.cpp:123-132).

**Verifier.** The loop is as described. src/libc/netdb.cpp:293 sets SO_RCVTIMEO once; the for(;;) at 298-319 exits only when recvfrom returns < 0 (305-308) or Parse returns something other than Unrelated (313-317). A datagram from a different endpoint hits 'continue' (309-312) and an Unrelated one falls through to the next iteration (318), each time calling recvfrom again. The kernel timeout is per call: ReceiveFrom computes ReceiveDeadline(socket) on entry as TickCount() + timeout (src/kernel/network/socket.cpp:286-293, 894), so every stray datagram restarts the full wait. There is no overall deadline, iteration cap or alarm in netdb.cpp (no SIGALRM/alarm use). The socket is unconnected, so datagrams from any source to its port are queued, and PickPortLocked hands out ports sequentially from FirstDynamicPort (socket.cpp:184-198), making the port guessable. A host that can reach the machine with one UDP datagram per timeout period can therefore keep getaddrinfo/getnameinfo from returning. Not a documented limit. Effect is contained: one lookup hangs (still interruptible by a signal since recvfrom returns EINTR), no memory or isolation issue, and it needs an on-path or LAN sender to keep it up, so minor stands.

**Reproduction (2026-11-25).** Trace only. libc netdb.cpp is not in the host test target. Trace: AskOverUdp (netdb.cpp:285-325) sets SO_RCVTIMEO once (293). The for(;;) at 298-319 exits only on recvfrom failure or a result other than Unrelated. Foreign-endpoint datagrams `continue` (309-312) and Unrelated ones loop (318). Kernel ReceiveFrom restarts the deadline at now+timeout on every call (socket.cpp:286-293, 894), and an unconnected UDP socket queues datagrams from any source (1077-1088) on a sequential port (PickPortLocked, 184-198). Root cause: AskOverUdp has no overall deadline or iteration cap while the per-call receive timeout restarts on every stray datagram
