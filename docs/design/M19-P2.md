# M19 Part 2: removable USB drives (design)

**Scope.** Today the kernel has:
- **Its only disk driver is virtio-blk.** It is polled one sector at a time under a spinlock (`arch/{x86_64,aarch64}/block_device.cpp`) behind the free functions in `storage/block_device.h`. One static `VirtioDisk` (`storage/core_block_device.cpp`) is the `FeatherDisk::BlockDevice` the core sees.
- **The disk's volumes:** 16 static `CoreDriver`s indexed by partition number (`filesystem/drivers.cpp`). They are opened at boot by `VFS::MountBlockDevice` and registered in the `TypeRegistry` under `vda1`…`vda16`. Users mount them with `mount -t <type> vdaN <point>`.
- **The page cache** is write-through and keyed per `CachedDevice` (one per volume). It is created only when virtio-blk exists.
- **xHCI** does control transfers (Setup/Data/Status) and single-TRB Normal TDs of at most 16 KiB that must not cross 64 KiB. Interrupt endpoints use them. Stalls are recovered on the manager task (`RecoverEndpoint`: Reset Endpoint, Set TR Dequeue, `CLEAR_FEATURE(HALT)`). Blocking `HostController` calls belong to the manager. Only `Submit` may be called from any task.
- **The USB core** binds drivers by interface class. `MassStorageConfiguration()` already exists in `tests/unit/kernel/usb/fake_device.cpp`.

This part adds, in the roadmap's order:
1. xHCI bulk transfers.
2. USB mass storage: Bulk-Only Transport (BOT) carrying SCSI, with reset recovery.
3. A block-device layer for several disks: names, partitions and volumes per disk.
4. Mounting, writing (checked with mtools) and `eject`.
5. The stick's FAT16 log partition and the laptop checklist.

UAS (UASP), streams, multiple LUNs, auto-mount and a USB root are left out.

**Done when:**
1. `./build.sh unit-test` and `unit-test-tsan` pass.
2. `bash tools/quality.sh check` passes.
3. `tools/check.sh --arch both --modes "USB_STORAGE USB_STORAGE_HOTPLUG USB_STORAGE_LARGE STORAGE USB"` passes.
4. `tools/check.sh --arch both --matrix` passes. This includes `usb_stick_uefi` on x86-64 when edk2 firmware is found.
5. The laptop checklist (`docs/hardware.md`) has been run once and its log saved to the stick and recorded under "Runs". A failure there does not block the part.

## Decisions (user, 2026-11-22)

- M19 Part 2 comes before Part 1 (foreign filesystems) and before M16 (NVMe, AHCI).
- The log goes to a small FAT16 partition that `tools/make_usb_stick.sh` adds. FAT32 stays in Part 1.
- USB drives are mounted by hand with `mount`. Auto-mount at `/media/<label>` comes later.
- UAS comes later.
- The open questions of section 8 (answered 2026-11-22): every recommendation accepted. USB volumes mount read-write on request; a removable FAT16 volume with a dirty bit set mounts read-only (I27); `eject` is syscall 74 and a program; bare names with `/dev/` stripped, no block nodes.
- Order:
  - 0: this design.
  - 1: xHCI bulk.
  - 2: BOT with SCSI (INQUIRY, TEST UNIT READY, READ CAPACITY(10/16), READ(10), WRITE(10), REQUEST SENSE, SYNCHRONIZE CACHE) and reset recovery (Bulk-Only Mass Storage Reset, clear halt on both pipes, port reset as last resort).
  - 3: the block-device layer (`vda`, `sda`, …) that M16 reuses.
  - 4: mount, write, `eject`.
  - 5: the stick's log partition and the laptop.

**Additions to the planned command list** (open question 12):
- READ(16) and WRITE(16), only for LBAs at or above 2^32. Without them, more than 2 TiB of 512-byte sectors is out of reach.
- MODE SENSE(6), for the write-protect bit.
- START STOP UNIT, for `eject`.
- GET MAX LUN, a class request.

## 1. Design

### 1.1 xHCI bulk transfers (`usb/xhci/`)

**Normal TDs.** New pure functions in `usb/xhci/td.{h,cpp}` (host-tested):
- A transfer of `length` bytes from one contiguous `Dma::Buffer` becomes TRBs that each stay inside one 64 KiB-aligned window (xHCI 4.11.7.1), each at most 64 KiB.
  - First chunk = `min(length, 0x10000 - (physical & 0xFFFF))`, then 64 KiB chunks.
  - `MaxBulkTransferBytes` = 65536, so a TD has at most 2 TRBs. `MaxTdTrbs` = 3, so control and bulk TDs share one array.
  - Length 0 is one TRB of length 0 (a zero-length packet). BOT never sends one.
- Flags:
  - Every TRB but the last has CH.
  - Only the last has IOC.
  - Every TRB of an IN TD has ISP.
  - TD Size (bits 17–21 of the status word, xHCI 4.11.2.4) = `min(31, ceil(bytes after this TRB / max_packet))`, 0 on the last. 0.96 controllers use another formula, not supported.
- Stream ID is 0 and `MaxPStreams` 0 (UAS later).
- The ring's existing No-Op padding keeps a TD from straddling the Link TRB, so a TD's TRBs are consecutive in ring memory. TRB *i* of a TD is at `first + 16 i`.

**Residue.**
- `PendingTransfer` keeps `first_chunk` and `trbs`.
- An event naming TRB *i* gives `before(i) = i == 0 ? 0 : first_chunk + (i-1) * 64 KiB`.
- Short Packet on a TRB that is not the last: `actual = before(i) + len(i) - residue`, `short_seen`.
  - xHCI 1.1+ then posts the last TRB's IOC event (the M14 model, kept).
- Event on the last TRB:
  - Success: `length` unless `short_seen`.
  - Short Packet: `before(last) + len(last) - residue`.
- `actual` never exceeds `length`.
- The only multi-TRB TDs are READ/WRITE data, which is short only on error. Responses that may be short (INQUIRY, MODE SENSE, sense data, CSW) are single-TRB TDs in the drive's command page. So a 0.96 controller that never sends the second event costs a timeout and a reset only on an error path.

**Limits.** `SubmitTransfer` keeps 16 KiB for control. Non-control transfers allow up to 64 KiB and drop the 64 KiB-crossing refusal (the split handles it). The buffer must be one `Dma::Buffer`, physically contiguous below the controller's limit (`AllocateBuffer`: 4 GiB when AC64 = 0).

**Configure Endpoint for bulk.** The existing `ConfigureEndpoints`/`WriteEndpoint` already covers it:
- EP type 2 (OUT) or 6 (IN), CErr 3, Interval 0.
- MaxPacketSize from the descriptor: 64 at full speed, 512 at high speed, 1024 at SuperSpeed.
- Max Burst from the SuperSpeed companion.

Changed: average TRB length 3072 for bulk. `EndpointRing` gains `type` and `max_packet` for TD Size and the retry rule.

**Errors on bulk endpoints.**

| Event | Action |
|---|---|
| Stall | Unchanged `RecoverEndpoint` on the manager: Reset Endpoint (TSP=0), Set TR Dequeue past the TD, `CLEAR_FEATURE(ENDPOINT_HALT)`, *then* finish with `Stall`. The endpoint is usable when the driver sees the status. |
| USB Transaction Error, Babble, Split Transaction Error | Same recovery, but **no TD replay** on bulk endpoints (control and interrupt keep the three retries). Finishes `TransactionError`/`Babble`/`Stall`. |
| Timeout | The waiter (not the controller) decides. The drive asks the manager for `CancelEndpoint`. |

**New `HostController` calls** (manager task):
- `CancelEndpoint(slot, endpoint)`: `Quiesce(slot, dci, nullptr, Cancelled, resume=true)`, which is Stop Endpoint, then Set TR Dequeue to the enqueue pointer. Every pending transfer on the endpoint finishes `Cancelled`. The endpoint takes new transfers afterwards.
- `ClearHalt(slot, endpoint)`: resets the toggle or sequence number on **both** sides.
  - Halted endpoint: Reset Endpoint and Set TR Dequeue.
  - Otherwise: Stop Endpoint if running, then **Configure Endpoint with the endpoint's Drop and Add flags both set**. The endpoint context is rewritten with TR Dequeue = ring enqueue | cycle, which resets the xHC's toggle/sequence (xHCI 4.6.6/4.6.8).
  - Then `CLEAR_FEATURE(ENDPOINT_HALT)` to the device.
  - Pending transfers finish `Cancelled`.
  - Without the xHC half, the device restarts at DATA0 while the xHC keeps its toggle, and the next packet is silently dropped.
- `RecoveryHandler` gains the `Status` of the recovered error, so the manager can skip stalls of drivers whose `stalls_are_protocol` is set.

**DMA buffer ownership.**
- A drive owns two buffers from `host.AllocateBuffer`, both allocated at attach on the manager:
  - a command page: CBW at 0, CSW at 64, responses (INQUIRY, sense, capacity, mode) at 128;
  - a 64 KiB data bounce buffer.
- **Every READ/WRITE goes through the bounce buffer.** The data comes from page-cache frames, the core's host buffers or block cache, or whatever buffer the VFS passes down. The drive copies with plain `memcpy` under the same contract as virtio-blk, so no user page, SMAP window, alignment or AC64 limit reaches the controller. One 64 KiB copy per command is far below USB's throughput.
- From `Submit` until the transfer finished (its callback ran), the CPU does not touch a buffer. After a timeout the drive waits for the cancellation's completion, or for detach, before reusing it.
- Buffers are freed when the drive object is freed, which happens after its slot was destroyed (detach) and the disk's last reference is gone.
- AArch64 needs `dma-coherent` (M14 already refuses other nodes).

### 1.2 Mass storage: BOT and SCSI (`usb/storage/`)

**Binding.**
- The driver `usb-storage` matches interface class 08, subclass 06 (SCSI transparent), protocol 0x50 (BOT), alternate setting 0.
  - UAS drives usually offer BOT at alternate setting 0, which the core already picks.
  - Other subclasses or protocols (UFI/CBI, ATAPI, RBC) are logged once and left `unbound`.
- It takes the first bulk IN and the first bulk OUT endpoint. `stalls_are_protocol = true`.
- Attach (manager, under `topology_lock`):
  - Allocates the `Drive` and its buffers.
  - Sends GET MAX LUN (`0xA1 0xFE`, `wIndex` = interface, 1 byte):
    - a stall, a timeout or a value above 15 means 0;
    - a value above 0 logs `USB 1-1: 4 LUNs, only LUN 0 is used`.
  - Posts the probe to the storage worker and returns. **Attach never waits for a BOT command.**

**LUNs: only LUN 0.**
- Sticks and USB disk enclosures have one LUN.
- Multi-LUN devices are mostly card readers. BOT serializes every LUN over one pipe pair, so LUN support is a naming and registration matter for later, not a transport change.
- The CBW's LUN field is always 0.

**CBW** (31 bytes, little-endian): `dCBWSignature` 0x43425355, `dCBWTag`, `dCBWDataTransferLength`, `bmCBWFlags` (0x80 = IN), `bCBWLUN` 0, `bCBWCBLength` 6/10/12/16, `CBWCB[16]` zero-padded. Tags increase by one per command per drive, starting from a value derived from the slot.

**CSW** (13 bytes): `dCSWSignature` 0x53425355, `dCSWTag`, `dCSWDataResidue`, `bCSWStatus` (0 passed, 1 failed, 2 phase error).
- A CSW is *valid* only if:
  - 13 bytes arrived;
  - the signature and tag match;
  - the status is ≤ 2;
  - residue ≤ `dCBWDataTransferLength`.
- Anything else (including babble when the device sends more) leads to reset recovery.

**One command** (`Bot::Execute`, the same code on every task, over a `Pipe`):
1. **CBW** on bulk OUT, 5 s.
   - Not Success: reset recovery, then the command fails `TransportFailed`. The SCSI layer retries it.
2. **Data**, if the length is not 0, on the data bounce buffer.
   - IN or OUT, 20 s; 60 s for SYNCHRONIZE CACHE and START STOP UNIT (no data, but the CSW waits).
   - Success or Short Packet: `actual`.
   - `Stall`: the controller has cleared the halt, so go on to the CSW.
   - Anything else, or a timeout: reset recovery.
3. **CSW** on bulk IN, same timeout.
   - `Stall`: read the CSW once more (BOT 6.7.2).
   - A second stall, an error or a timeout: reset recovery.
4. Check the CSW.
   - Passed: success only if `residue == 0 && actual == length` for READ/WRITE. For other commands, the data is `length - residue` bytes (capped at `actual`).
   - Failed: CHECK CONDITION, REQUEST SENSE next.
   - Phase error or invalid: reset recovery.

**The 13 cases** (BOT 6.7) and what the host does. Each is scripted in T11.

| # | Host / device | Device behaviour | Host action and result |
|---|---|---|---|
| 1 | Hn = Dn | CSW passed, residue 0 | pass |
| 2, 3 | Hn < Di, Hn < Do | CSW phase error | reset recovery, `TransportFailed` |
| 4 | Hi > Dn | short or zero data, or a stall, then CSW with residue | stall: halt cleared, read CSW; result follows the CSW |
| 5 | Hi > Di | short data or a stall, residue = difference | same as 4; READ fails (short); INQUIRY/MODE SENSE use `length - residue` |
| 6 | Hi = Di | normal | pass |
| 7 | Hi < Di | Hi bytes, then phase error | reset recovery |
| 8 | Hi ≠ Do | a stall on IN, or phase error | stall then CSW; status 2 leads to reset recovery |
| 9 | Ho > Dn | a stall on OUT, or accept, CSW residue | stall: read CSW |
| 10 | Ho ≠ Di | phase error | reset recovery |
| 11 | Ho > Do | a stall on OUT or accept, residue | as 9; WRITE fails unless residue 0 |
| 12 | Ho = Do | normal | pass |
| 13 | Ho < Do | phase error | reset recovery |

**Reset recovery** (BOT 5.3.4) runs on the manager, requested through the drive's `service`:
1. `CancelEndpoint(IN)` and `CancelEndpoint(OUT)`. Every stale TD finishes `Cancelled`.
2. Bulk-Only Mass Storage Reset: `0x21 0xFF`, `wValue` 0, `wIndex` = interface, no data.
3. `ClearHalt(IN)`, then `ClearHalt(OUT)`.

If step 2 or 3 fails (stall, timeout or `NoDevice`), the last resort is a **port reset**:
- `service` returns true and the manager runs `Reenumerate(device)`: detach the device (the drive becomes gone), reset its port (`ResetRootPort`, or `SET_FEATURE(PORT_RESET)` through the hub's state machine), then enumerate it again.
- The device comes back as a **new** disk, so mounts on the old one are dead (open question 13).
- Logged: `Storage: sda: reset recovery after <stage> <status>`; `Storage: sda: port reset, the drive comes back as a new disk`.
- No other command is sent between a failure and the end of recovery.

**SCSI** (`usb/storage/scsi.{h,cpp}`, pure):
- INQUIRY (36 bytes):
  - qualifier 0;
  - device type 0x00 (direct access) or 0x0E (RBC);
  - others are refused: `Storage: USB 1-1: device type 05 is not a disk; ignored`.
  - RMB is kept as `removable`. Vendor, product and revision are trimmed.
- TEST UNIT READY: GOOD, or CHECK CONDITION handled by the sense table.
- READ CAPACITY(10): last LBA and block length. Last LBA 0xFFFFFFFF switches to READ CAPACITY(16) (`0x9E/0x10`, 32 bytes).
  - Accepted block lengths: 512, 1024, 2048, 4096. Others, or 0 blocks, refuse the disk with a log line.
  - A device that overstates its last LBA by one is not corrected (no quirk table).
- MODE SENSE(6) page 0x3F, 192 bytes (Linux's default): header byte 2 bit 7 = write-protected. A stall or CHECK CONDITION means writable, and DATA PROTECT is caught later.
- READ/WRITE: the (10) forms while `lba + blocks ≤ 2^32`, otherwise READ(16)/WRITE(16). At most 64 KiB per command (128 × 512 or 16 × 4096). Never past the last LBA.
- SYNCHRONIZE CACHE(10): LBA 0, 0 blocks (the whole medium).
- START STOP UNIT: Start = 0, LoEj = RMB.
- REQUEST SENSE (18 bytes): fixed format (0x70/0x71) or descriptor format (0x72/0x73) gives key/ASC/ASCQ.

**Sense table** (`Scsi::Classify`):

| Sense | Action |
|---|---|
| 0 NO SENSE, 1 RECOVERED ERROR | success |
| 2 NOT READY, ASC 04/01 (becoming ready) | wait 100 ms and retry, within the probe budget (10 s) or 5 s later |
| 2/3A (no medium) | probe: not registered (`no medium`); later: EIO |
| 2 other, 3 MEDIUM ERROR, 4 HARDWARE ERROR | EIO, no retry |
| 5 ILLEGAL REQUEST | EIO; for SYNCHRONIZE CACHE: unsupported, success, never sent again |
| 6 UNIT ATTENTION, ASC 29 (power on or reset) | retry up to 3 times |
| 6/28 (medium may have changed) | at probe: retry; with a volume open: the disk becomes gone (writes might hit another medium) |
| 7 DATA PROTECT | the disk becomes read-only; the write fails `ReadOnly` (EROFS) |
| 0xB ABORTED COMMAND | retry up to 3 times |
| other | EIO |

A command that ended `TransportFailed` (after recovery) is retried twice. READ, WRITE and SYNCHRONIZE CACHE are idempotent, so a retry rewrites the same data.

**Probe** (on the storage worker, through the normal pipe):
1. INQUIRY.
2. TEST UNIT READY until GOOD, within 10 s, handling UNIT ATTENTION and becoming-ready.
3. READ CAPACITY(10), then (16) if needed.
4. MODE SENSE(6).
5. `Storage::Register`.

Log line: `Storage: sda: USB 1-1, "QEMU" "QEMU HARDDISK", 65536 KiB, 512-byte sectors, removable[, write-protected]`. A drive unplugged during the probe logs once and registers nothing. Media change after a "no medium" probe is not watched; replug.

### 1.3 Tasks, waiting and locking

**Who runs what.**

| Task | USB-storage work |
|---|---|
| filesystem threads (syscalls), `Writeback`, the eject caller, **`StorageWorker`** (new, Normal priority, one) | run BOT commands through the drive's `TaskPipe`, holding `Drive::io_lock` |
| `UsbEvents` | completes transfers; runs the `DeviceTransfer` callback, which records status and wakes the drive's waiter |
| `UsbManager` | stall recovery (existing `ServiceEndpoints`); the drive's `service`: `CancelEndpoint`, reset recovery, port reset; attach (GET MAX LUN, posts the probe); detach (drive gone, `Storage::Remove`) |

**`StorageWorker`** runs jobs from a small spinlocked queue:
- `Probe(drive)`: the SCSI probe, then `Register`, then `Drivers::OpenDiskVolumes`.
- `Removed(disk)`: `Drivers::ForgetDiskVolumes`.

It is started by `Storage::Initialize()` before `Usb::Initialize`. It exists so that neither attach (under `topology_lock`) nor the manager ever waits for a BOT command. The manager cannot wait on a callback-completed transfer, because stall recovery needs the manager itself.

**`TaskPipe`** (any task but the manager):
- `Start` submits through `Device::Submit` under `state_lock`, with `device` checked non-null. The callback is `OnTransferDone`.
- `Finish` waits on the drive's wait queue (`Scheduler::WaitOn` with a deadline tick) until `done`, `gone` or the deadline.
- On timeout it posts `Recovery::Reset`: it sets `request` and `serial` under `state_lock`, then `Device::PostWork()`. It then waits for the reply with serial ≥ its own, or for `gone`, within 30 s.
- **It always waits until the timed-out transfer has finished** (the cancel completes it `Cancelled`), or until gone, before the buffers or the `DeviceTransfer` are reused.
- The callback is the last access to the transfer object. `Complete` then touches only `Device::in_flight`, and the `Device` array is permanent.
- The waits go through `usb/storage/environment.h` (`NowMilliseconds`, `WaitUntil`, `Wake`, `Sleep`). The kernel implements it with the scheduler; host tests implement it by pumping the `Rig` (single thread) or with real threads (TSan).

**One outstanding command per device.** BOT allows one, so there is no queue. `io_lock` serializes the volumes of one drive (`sda1` and `sda2` on two threads), the worker and `eject`.

**Lock order.** Add it to `docs/development.md` as "Storage locking", after "USB locking". Nothing takes an earlier lock while holding a later one.
1. `Files::namespace_lock`, `table_lock` (existing); the `/proc` volume lock.
2. Volume locks (`Driver::VolumeLock`): one per task, except `Files::Quiesce`.
3. `Usb::topology_lock`: manager and `/proc/usb` only. **Never taken by a task holding `io_lock`.**
4. `Drive::io_lock` (`Sync::Mutex`): held across a whole command, its waits and the recovery wait. **Never taken by `UsbEvents` or `UsbManager`.** Unordered against `topology_lock`, since never nested with it.
5. `Storage::registry_lock`, `Drivers::volumes_lock`, VFS `mount_lock` (spinlocks). None is held while another is taken, while calling the removal handler, or across I/O.
6. `Drive::state_lock` (spinlock, IRQ-save), then controller `ring_lock` (through `Device::Submit`), then Bus `work_lock` (through `PostWork`).
7. Controller spinlocks, the page cache's host lock (never held across a device call, existing), the heap.

**Why no deadlock.**
- The new blocking waits are:
  - a filesystem thread or the worker waiting for a completion (from `UsbEvents`, which takes no sleeping lock) or for the manager's recovery;
  - the manager waiting for controller commands and `Quiesce` (both completed by `UsbEvents`).
- The manager never waits for `io_lock`, a volume lock, the page cache lock or a filesystem thread.
- Detach under `topology_lock` only sets flags under `state_lock`, wakes waiters, and calls `Storage::Remove`. That takes `registry_lock`, marks volumes dead with atomics under `volumes_lock`, and queues a worker job. No volume lock.
- So a thread holding a volume lock and `io_lock` and waiting for recovery always gets an answer: the reply, or `gone` from detach. The deadline is the backstop for the "stuck" quiesce of `device.cpp:454-468`, where detach is skipped.
- `/proc/usb` keeps the order `/proc` volume lock, then `topology_lock`.
- `Files::Quiesce` at shutdown holds every volume lock while `Detach` runs BOT. The manager and event task are kernel tasks that keep running, and the worker blocks harmlessly on a volume lock.
- The `Writeback` task can stall up to a recovery's 30 s on a hung drive (its other volumes wait). Logged.

**Lifetimes.**
- `Usb::Storage::Drive` is reference-counted, with one reference from the USB binding and one from the `Storage::Disk`.
- In `detach`, under `state_lock`, the drive sets `device = nullptr`, `gone = true` and the reply `NoDevice`, wakes everyone, calls `Storage::Remove(disk)` if registered, and drops the binding's reference.
- `Storage::Disk` is counted by:
  - the registry, until `Remove`;
  - each open volume slot, until it is released;
  - each in-progress `Acquire`r.
- The last `Release` frees the disk and calls `DiskDriver::Release()` once. The drive frees its DMA buffers and itself when both references are gone.

### 1.4 The block-device layer (`storage/`)

- **`Storage::DiskDriver`** (`storage/disk_driver.h`, step 2b) is what a transport implements:
  - `Info()`: kind, sector size, count, max transfer, removable, read-only, model, location;
  - synchronous `Read(sector, count, buffer)`, `Write`, `Flush`;
  - `Stop()` (eject) and `Release()`.
  - virtio-blk (`vd`), USB/SCSI (`sd`), and later AHCI (`sd`) and NVMe (`nvme0n1`) implement it.
  - Serialization is the driver's job, so NVMe can queue later.
- **`Storage::Disk`** is a `FeatherDisk::BlockDevice`:
  - It checks bounds (`InvalidArgument` past the end, which signals a core bug).
  - It splits calls into chunks of at most `max_transfer_bytes`, in order.
  - `gone` or ejected gives `Io`. Read-only gives `ReadOnly` on writes.
  - It keeps per-disk counters, which replace `DeviceStatistics()`.
- **Names:**
  - virtio disks `vda`, `vdb`… by probe order;
  - SCSI disks `sda`, `sdb`… at the lowest letter not held by any allocated `Disk`. A dead mount keeps its letter until `umount`, so a replug meanwhile comes back as `sdb` (open question 7).
  - Partitions are `<disk><number>`, or `<disk>p<number>` when the disk name ends in a digit (`nvme0n1p1`, for M16).
  - A disk with a filesystem on its whole device (superfloppy: common on sticks) is the volume `sda` itself.
  - `MaxDisks` = 8.
- **Registration:** `Register(driver)` takes `registry_lock`. It refuses the disk if the drive is already gone, which `detach` sets before calling `Remove` (I17). Then the worker opens the volumes:
  1. Probe FAT16, ext2, ext3 and ext4 on the whole disk first, because a FAT boot sector also carries 0x55AA.
  2. Otherwise, `Partition::Find` (up to 16) and probe each.
  3. Each accepted volume is opened **read-only in the core** in a slot and registered under its type and name. This is today's boot-disk behaviour, and the future `/media/<label>` needs it.
  4. Log `Storage: sda1: fat16, 32768 KiB` or `Storage: sda2: no supported filesystem`.
- **Volume slots** (`filesystem/drivers.cpp`):
  - 32 permanent `CoreDriver`s, so a `Driver*` never dangles.
  - Slots 1–16 are the boot disk's, by partition number. `Drivers::Volume(number)`, `MountBlockDevice` and `ChooseRoot` are unchanged.
  - Slots 17–32 are allocated to other disks' volumes, each holding a disk reference, a partition number, `source[16]` and an atomic `dead`.
  - `TypeRegistry::Capacity` becomes 48 and the static assert at `vfs.cpp:52` follows.
- **Page cache:**
  - Already keyed by volume (`CachedDevice` id), so several disks need no change.
  - `Overlaps` compares ranges only on the same disk.
  - A released slot `Detach`es its `CachedDevice`, which drops its pages.
  - `InitializeCache` moves ahead of the virtio check, so a disk-less laptop caches USB reads too.
- **`/dev`:** no block-device nodes in this part. `mount` takes the bare name, `mount -t fat16 sda1 /mnt`. The kernel's `VFS::Mount` strips a leading `/dev/` (open question 1).
- **`/proc/partitions`** (new), one line per disk and per volume, in registry order:

  ```
  vda    262144 512 virtio
  vda1   130048 512 ext4
  sda     65536 512 usb removable rw
  sda1    32768 512 fat16
  sda2    16384 512 -
  ```

  As built in step 3b, only volumes that opened are listed; a partition with no supported filesystem is logged but gets no `-` line (that needs per-disk partition records).
  A disk line ends `ro` when write-protected and `ejected` after `eject`. Gone disks are not listed. `/proc/usb` shows the driver: `1-1 dev 2 super 46f4:0001 class 08/06/50 usb-storage`.
- **Root:** `root=vdaN` stays the rule. USB enumeration starts after the root mount (`kernel_runtime.cpp:499` vs `:560`), so `root=sdaN` is reported as malformed and the default root is used (open question 8).
- **Fit for M16:** an AHCI port or NVMe namespace implements `DiskDriver` and calls `Register`. The worker's partition scan, the slots, `/proc/partitions`, `eject` (refused for non-removable) and `FlushAll` apply unchanged.

### 1.5 Hot-unplug and eject

**Unplug while mounted or mid-I/O:**
1. The manager's `Bus::Detach` sets `detaching`; `StopEndpoints` finishes the pending BOT transfer `Cancelled`; the callback wakes the thread.
2. Driver detach (under `topology_lock`): `gone`, wake, `Storage::Remove`.
   - `Remove` marks the disk gone and unlisted, drops the registry's reference, and calls the removal handler.
   - The handler (`Drivers`) marks each of the disk's slots `dead`, sets its driver's mount mode read-only at once (`/proc/mounts` shows `ro`), and queues `Removed(disk)` to the worker.
3. The waiting thread gets `NoDevice`. The command, and any further one, fails `Io`, and the syscall gives EIO.
4. Every `CoreDriver` operation on a dead slot fails EIO before reaching the core, and `RefusesWrites()` is true. `Close` works.
5. The worker forgets every *unmounted* dead volume: under its volume lock, `Discard` (no I/O), unregister, release the slot. A *mounted* one stays until `umount`.
6. `umount`: `Detach()` on a dead slot calls `Discard` and returns true; then `Drivers::Unmounted` releases the slot. With files still open: EBUSY until they are closed.
7. The last reference frees the disk, the letter and the drive.

No code touches the `Device` after detach (I15).

**`eject sda`**: new syscall 74 `Eject(name)`, `Files::Eject` under `namespace_lock`, then `VFS::EjectDisk`.
1. Unknown or gone: ENOENT. Not removable (`vda`): ENOTSUP. Already ejected: 0.
2. Mark the disk `ejecting`. New mounts of its volumes fail ENODEV.
3. **All or nothing:** `BeginUnmount` on every mount of the disk's volumes, with the working-directory check as `umount` does. If any is busy, cancel the begun ones, clear `ejecting`, and return EBUSY.
4. `Detach` each (sync, then SYNCHRONIZE CACHE), then `FinishUnmount`. An I/O failure returns EIO; the mounts already finished stay unmounted, the rest are cancelled.
5. Forget every volume of the disk, then `disk.Flush()`, then `driver.Stop()` (START STOP UNIT; a refusal is logged, not fatal).
6. The disk is `ejected`: I/O fails `Io`, and the listing shows `ejected` until unplug.
7. Log `Storage: sda: ejected, safe to unplug`.

PREVENT ALLOW MEDIUM REMOVAL is never sent: FeatherOS never locks a medium, so there is nothing to allow.

### 1.6 Write path and durability

**Order of one FAT16 change.**
- The core writes each sector through at once (write-through, no write-back), in the core's own order, as on `vda`.
- Each `Disk::Write` becomes WRITE commands of at most 64 KiB, in LBA order. It returns only after every CSW passed (I23).
- Commands are never merged or reordered across calls.
- A failed write drops the page from the cache (existing).

**Durability points:**

| Event | What is sent |
|---|---|
| `sync` | `SyncAll`, then each volume's `Sync`, then FAT16 `volume.Flush()`, then `Disk::Flush`, then SYNCHRONIZE CACHE(10) |
| `umount` | `Detach`, which syncs as above |
| `eject` | 1.5 |
| shutdown | `Files::Quiesce` runs `DetachAll` (SYNCHRONIZE CACHE per volume), then `Storage::FlushAll()` (once more per disk) |

ext3/ext4 also commit every 5 s through `Writeback`, unchanged. A failed flush gives EIO to `sync`, makes `umount` fail (the mount stays), and gives EIO to `eject`.

**What a crash or unplug leaves:**

| Point | On the medium |
|---|---|
| before a command's CBW | nothing of that command |
| during its data stage | any prefix of the command's sectors; a torn sector is possible on cheap flash |
| after data, before the CSW | possibly all of it (the host reports EIO; a retry rewrites the same bytes) |
| after the CSW passed | in the drive's volatile cache: lost if power goes before a flush |
| after SYNCHRONIZE CACHE passed | durable, if the drive honours it (out of FeatherOS's control) |

- At the filesystem level, FAT16 has no journal. An interrupted change can leave lost clusters or a file shorter than what was written, and `fsck.fat -a` repairs it. A rename onto an existing file can lose the target (existing limit).
- ext3/ext4 are journalled in ordered mode and replay at the next read-write mount, as on `vda`.
- **Unplugging after `sync` or `eject` returned is safe. Before that, it is not.**

## 3. Invariants

**xHCI bulk (step 1)**
- **I1.** A Normal TD's TRBs each lie inside one 64 KiB window and are at most 64 KiB. Every TRB but the last has CH. IOC is only on the last, ISP on every IN TRB, and TD Size is the packets left (0 on the last). A TD never straddles the Link TRB. **Riskiest.**
- **I2.** A bulk transfer's `actual` = bytes before the short TRB + (its length − residue), or `length` on Success without an earlier short event, never more than `length`.
- **I3.** The controller never replays a bulk TD. A stalled bulk endpoint is reset (Reset Endpoint, Set TR Dequeue past the TD, `CLEAR_FEATURE`) before the transfer finishes `Stall`.
- **I4.** `ClearHalt` resets the xHC's toggle/sequence (Reset Endpoint if halted, else Stop and Configure Endpoint with drop and add at enqueue | cycle) before `CLEAR_FEATURE(ENDPOINT_HALT)`. **Riskiest.**
- **I5.** The CPU does not touch a submitted buffer, or reuse its `DeviceTransfer`, until the transfer has finished or the drive is gone, timeouts included. DMA buffers are freed only after the slot is destroyed. **Riskiest.**

**BOT and SCSI (step 2)**
- **I6.** A CBW is exactly 31 bytes: signature 0x43425355, LUN 0, a CB length matching the CDB, flags 0x80 only for IN. Consecutive tags differ.
- **I7.** A CSW is accepted only with 13 bytes, signature 0x53425355, the CBW's tag, status ≤ 2 and residue ≤ the requested length. **Riskiest.**
- **I8.** These always lead to reset recovery before any further command, in the order cancel IN and OUT, BOMS reset, `ClearHalt(IN)`, `ClearHalt(OUT)`, and a recovery failure leads to a port reset:
  - phase error, invalid CSW, CBW failure, a second CSW stall;
  - any data or CSW error other than a stall;
  - a timeout.
- **I9.** A data-stage stall is followed by reading the CSW. READ/WRITE succeed only with status 0, residue 0 and `actual == length`.
- **I10.** CHECK CONDITION is followed by REQUEST SENSE before any other command, and the sense table decides. UNIT ATTENTION 28/00 with a volume open makes the disk gone.
- **I11.** Only LUN 0 is ever addressed.
- **I12.** READ/WRITE use the (10) forms while `lba + blocks ≤ 2^32`, else (16), never past the last LBA, and at most 64 KiB per command.
- **I13.** A write-protected disk (WP bit or DATA PROTECT) gets no WRITE, and its volumes open read-only.

**Concurrency and lifetime (steps 2–3)**
- **I14.** At most one BOT command per drive. `UsbEvents` never takes `io_lock`, `topology_lock`, a volume lock or `registry_lock`. `UsbManager` never takes `io_lock` or a volume lock. Attach never waits for a BOT command. **Riskiest.**
- **I15.** After the driver's `detach`, nothing dereferences the drive's `Device`; submits see `device == nullptr` under `state_lock`.
- **I16.** A `Disk` is freed exactly once, after the registry, every slot and every `Acquire`r released it. Its `DiskDriver::Release` runs exactly once, after that. A drive frees its buffers once both its references are gone. **Riskiest.**
- **I17.** A disk whose drive is gone is never registered.
- **I18.** Every wait has a deadline, and detach wakes every waiter. I/O on a gone disk fails within the command timeout.

**Block layer and volumes (step 3)**
- **I19.** Names follow 1.4: `vdX` by probe order, `sdX` at the lowest letter not allocated, `p` before a number after a digit. A letter is reused only after its `Disk` was freed.
- **I20.** Overlap checks compare ranges on one disk only. A released slot's pages are dropped.
- **I21.** A dead volume refuses writes and shows `ro`. Every operation reaching the core fails EIO. `umount` succeeds with no device I/O once no file is open.
- **I22.** The boot disk keeps slots 1–16 by partition number, and `root=` still takes only `vdaN`.

**Writes (step 4)**
- **I23.** `Disk::Write` returns only after every covered sector's WRITE passed. Commands keep call order and are never merged across calls.
- **I24.** Every `Flush` (sync, unmount, eject, shutdown) sends SYNCHRONIZE CACHE, unless the drive answered ILLEGAL REQUEST once. A failed flush is reported.
- **I25.** `eject` unmounts every mount of the disk or, if one is busy, none.
- **I27.** A FAT16 volume on a removable disk whose FAT[1] has bit 15 (clean shutdown) or bit 14 (no hard error) clear mounts read-only, logging `VFS: sda1 was not cleanly unmounted (FAT16 dirty bits); mounted read-only, run fsck.fat`; `remount,rw` gives EROFS. FeatherOS never writes these bits in this part (Part 1 sets and clears them with FAT32). Non-removable disks (`vda`) are unchanged.

**Stick (step 5)**
- **I26.** The stick's GPT holds the ESP unchanged as entry 1 and a basic-data FAT16 volume (4085–65524 clusters) as entry 2.

## 4. Edge cases

| Case | Result |
|---|---|
| Interface subclass other than 06 or protocol other than 0x50 | `unbound`; `USB 1-1: mass storage subclass 04 protocol 00 not supported` |
| GET MAX LUN stalls or hangs | LUN 0 (a hang costs 5 s) |
| Device type not 0x00 or 0x0E (CD-ROM) | not registered, logged |
| No medium (card reader) | not registered: `Storage: USB 1-1: no medium` |
| Not ready after 10 s | not registered, logged |
| Block size 520 or 0 blocks | not registered, logged |
| FAT16 on a 4096-byte-sector drive | `Storage: sdb6: no supported filesystem` (GPT entry 6 in the test image) (the FAT16 core needs 512) |
| Partition types 0x0B/0x0C/0x07 (FAT32, exFAT) | not listed (Part 1) |
| `mount -t fat16 sdz1 /mnt` | ENOENT |
| `mount -t ext4 sda1 …` on FAT16 | as today (`TypeRegistry` lookup) |
| `mount` on a write-protected drive | mounted read-only, `VFS: sdc1 is write-protected, mounted read-only`; writes EROFS |
| `mount -o remount,rw` there | EROFS |
| `mount` of a dead or ejected volume | ENXIO (as built: the kernel's "no device" maps to ENXIO, since ENODEV already means an unknown filesystem type) |
| Read or write after unplug | EIO; `/proc/mounts` shows `ro` |
| `umount` of a dead volume with no open file | 0, no I/O |
| `umount` of a dead volume with an open file | EBUSY; `close` works, then `umount` |
| `sync` with a dead USB volume mounted | EIO; the other volumes are synced |
| Unplug during the probe | nothing registered, one log line |
| Unplug during attach (GET MAX LUN) | attach fails, no state kept |
| A drive hangs (no CSW) | 20 s, reset recovery, retried twice, EIO; the next command works if recovery did |
| BOMS reset stalls | port reset; the drive returns as a new disk; old mounts dead |
| SYNCHRONIZE CACHE unsupported | success; never sent again for that drive |
| DATA PROTECT on a write (switch flipped) | EROFS; the disk becomes read-only |
| Medium changed (UNIT ATTENTION 28) with a volume open | the disk becomes gone; EIO |
| Replug while a dead mount holds `sda` | comes back as `sdb` |
| A ninth disk | not registered: `Storage: no disk slot left` |
| A disk with more than 16 partitions, or 16 non-boot volumes in use | the extra ones are not opened, logged |
| `eject vda` | ENOTSUP |
| `eject sda` with a file open on `sda1` | EBUSY, nothing unmounted |

## 6. Tests

**Host** (`tests/unit/kernel/usb/`, `tests/unit/kernel/storage/`, `tests/unit/kernel/filesystem/`, `src/fs/core/tests/`; T14, T15 and T22 run under ASan and TSan)

- **T1** `BuildNormalTd`:
  - lengths 0, 1, 512, 4095, 4096, 65535, 65536 at physical offsets 0, 0x0FFF, 0xFFFF;
  - checks TRB count and lengths (no 64 KiB crossing), CH, IOC, ISP and TD Size for MPS 64, 512 and 1024;
  - 65537 is refused.
- **T2** Two-TRB TDs over 3 ring laps: No-Op padding before a TD that would straddle the link, link chain bit, cycle toggling.
- **T3** Residue: short on TRB 0 of 2 (then the second event), short on TRB 1, Success, Success after short; `actual` each time.
- **T4** Bulk stall: commands in order Reset Endpoint, Set TR Dequeue past the TD, `CLEAR_FEATURE(HALT, 0x81)`, then `Stall`. The next transfer works.
- **T5** Bulk Transaction Error: one OUT delivery, no replay, `TransactionError`. An interrupt endpoint still retries 3 times.
- **T6** `ClearHalt` on a running and on a stopped endpoint: Stop, then Configure Endpoint with drop and add (the fake checks the flags, DCS and dequeue), then `CLEAR_FEATURE`. On a halted one: Reset Endpoint. The fake's toggle model loses the next packet if the xHC half is skipped.
- **T7** `CancelEndpoint`: a pending IN finishes `Cancelled`; the fake records no DMA write into the buffer afterwards.
- **T8** SCSI: every CDB byte-exact. INQUIRY, READ CAPACITY(10/16), MODE SENSE and sense (fixed and descriptor) parsing; truncated or invalid responses refused; the (10)/(16) switch at 2^32.
- **T9** Sense table: every row of 1.2 to its action.
- **T10** CBW byte layout. CSW checks: bad signature, wrong tag, 12 bytes, babble, status 3, residue above length.
- **T11** The 13 cases over a model pipe: the scripted device behaviour, the host's stage sequence and the `Result`.
- **T12** Recovery order in the command log: cancel IN, cancel OUT, `0x21 0xFF`, `CLEAR_FEATURE` IN, then OUT, with nothing in between. A failed BOMS reset leads to `Reenumerate`: detach, port reset, a new device, a new disk name.

## 8. Open questions (answered by the user, 2026-11-22)

The user accepted every recommendation below.

1. **Names users see.** Bare `sda`/`sda1` in `mount`, with the kernel also accepting `/dev/sda1` by stripping `/dev/`. The alternatives are real `/dev` block nodes (a device-file kind, raw access) or bare names only. **Recommended:** bare names plus the stripped prefix; `/dev` nodes later with a reason (raw tools).
2. **`eject` as a new program and syscall 74**, versus `umount -a sda` or a userspace loop over `/proc/mounts`. **Recommended:** the program and syscall, because the kernel can make the unmount all-or-nothing and stop the drive.
3. **Read-only by default for USB drives** under the Safety rules. The FAT16 and ext write paths already passed the matrix on `vda`. **Recommended:** no. Mount read-write on request as `vda` does; write-protected and journal-needs-recovery volumes follow the existing rules.
4. **The FAT16 dirty bits** (FAT[1] bits 15/14: clean shutdown, no hard error). FeatherOS neither reads nor writes them today. **Recommended:** on removable disks, honour them by mounting read-only with a warning when dirty, so `fsck.fat` on another machine goes first. Setting and clearing them ourselves comes with FAT32 in Part 1.
5. **Probe filesystems at plug-in** (opened read-only in the core, as `vda` is at boot), versus only at `mount` time. **Recommended:** at plug-in. `/proc/partitions` can then show types and the later `/media/<label>` needs it. A read-only probe writes nothing.
6. **Multi-LUN devices** (card readers with several slots). **Recommended:** LUN 0 only in this part, logged; more LUNs later if wanted.
7. **Name reuse.** A dead mount keeps `sda` until `umount`, so a replug meanwhile becomes `sdb`. Linux reuses the name at once and the dead mount points at a different kernel object. **Recommended:** as designed (simpler lifetimes, no confusion in `/proc/mounts`).
8. **A USB root** (`root=sda2`, or a persistent root on the stick for the laptop). This needs waiting for enumeration before the root mount. **Recommended:** out of scope; root stays `vdaN` or tmpfs.
9. **How the log gets to the stick.** By hand (7), or a boot option such as `savelog=sda2` / an init service that mounts it and writes `dmesg` at boot and shutdown. **Recommended:** by hand for the first laptop run; revisit after it.
10. **`/proc/partitions` format.** FeatherOS columns (name, KiB, sector size, kind or type, flags) versus Linux's `major minor #blocks name`; we have no device numbers. **Recommended:** FeatherOS columns, documented in `docs/development.md`.
11. **Log partition size.** **Recommended:** 32 MiB (many logs of 64 KiB, a comfortable FAT16 cluster count, a small image).
12. **Additions to the planned command list:** READ(16)/WRITE(16) (only above 2^32 LBAs), MODE SENSE(6) (write protect), START STOP UNIT (eject). **Recommended:** accept all three.
13. **Port reset as last resort** re-enumerates the drive as a new disk, so its mounts die. The alternative keeps the device's identity (xHCI Reset Device, re-address, reconfigure, much more code). **Recommended:** re-enumerate.
14. **A 3 TiB sparse image in the matrix** (needs a host filesystem with sparse files; APFS and ext4 have them). **Recommended:** yes, skipped with a message if the image cannot be created.
15. **An `lsblk`-style program.** **Recommended:** none for now; `cat /proc/partitions`.
16. **What unplug does to a mount.** It stays mounted, dead and `ro`, until `umount`, as the roadmap says. The alternative is a kernel-side lazy unmount at once. **Recommended:** keep it until `umount`.
