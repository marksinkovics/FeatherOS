# M30 Part 6: a page cache (design)

**Scope.** Today every read of file contents goes to the virtio disk. `CoreDriver::Read` calls the core, which calls `BlockCache::ReadUncached`, then `Partition::Volume::Read`, then `VirtioDisk::Read`, one sector at a time under `device_lock`. Only metadata is cached, in each mount's core `BlockCache`: 32 slots, write-through, per volume. This part adds one page cache below every block-device filesystem. Recently read 4 KiB pages of a volume stay in kernel memory. Writes go through to the device before they return, and flushes pass straight through. So the device sees exactly today's writes and flushes, and every crash outcome is unchanged. The cache grows from free memory and shrinks under memory pressure.

**Done when:**
1. `./build.sh unit-test` and `./build.sh unit-test-tsan`;
2. `bash tools/quality.sh check`;
3. `tools/check.sh --arch both --modes "SHELL STORAGE"`;
4. `tools/check.sh --arch both --matrix`. The crash tests and every `e2fsck -fn`/`-fy` check pass unchanged.

## Decisions (taken 2026-11-20; see section 9)

- **D1. Place.** The cache is a `BlockDevice` decorator, `FeatherDisk::CachedDevice`. Each `CoreDriver` puts one between its `Partition::Volume` and the core. Probe, mount, journal replay, ext and FAT16 all see the decorator. The partition scan (`Drivers::FindPartitions` over `CoreDevice()`) and the kernel test's raw scratch sector 2047 stay uncached. Both lie outside every volume.
- **D2. The page cache replaces the core `BlockCache` in the kernel.**
  - `BlockDevice` gains `virtual bool CachesBlocks() const { return false; }`. `CachedDevice` returns true while it is attached to a cache.
  - `Ext2Filesystem::Initialize` sets its `BlockCache` up with 0 slots when `volume.CachesBlocks()`, and 32 KiB worth otherwise, as today.
  - A 0-slot `BlockCache` is a pass-through:
    - `Read` reads the whole block into `scratch` with one `device->Read` and copies the asked part;
    - `ReadUncached` is unchanged;
    - `Write` is one `device->Write` with the same arguments;
    - it holds no copies and creates no lock.
  - So in the kernel the page cache is the only cache below the core.
  - The jbd2 `step`, `running` and `committed` layers are not a cache below the core. They hold the transaction's own blocks and order them, and they stay.
  - `fscli`, host tools and the existing core tests use plain devices (`CachesBlocks()` false), so they keep today's 32 KiB `BlockCache`.
  - A kernel volume left uncached (D9's overlap rule, or no cache) also keeps it.
  - Today only ext uses `BlockCache` (`Ext2Filesystem::cache`); it hands out no pointers, pins nothing and has no dirty or ordering role (`Write` is one `device->Write`, then its copies are updated or dropped). FAT16 reads `volume` directly.
- **D3. Code in the core.** `include/fs/page_cache.h` and `common/page_cache.cpp` include nothing outside `src/fs/core/`. Pages come from an abstract `PageSource`. The kernel's source hands out physical frames through the HHDM, not heap memory, because the heap never unmaps and could not shrink. `fscli` does not use the page cache.
- **D4. Unit: a 4 KiB page of a volume.** It holds 4096/sector-size sectors, counted from the volume's sector 0. The volume's last page may be short. A device with sectors over 4096 bytes is left uncached.
- **D5. Keys: (volume id, page index).** `CachedDevice::Attach` takes a fresh 64-bit id that is never reused.
- **D6. Write-through, no write-allocate.** A write goes to the lower device first. If it succeeds, its bytes are copied into the pages already cached; if it fails, those pages are dropped. Pages are filled only by reads.
- **D7. Sizing.** The limit is a quarter of the free frames when the cache is set up, before `MountBlockDevice`. The cache grows only while free frames stay above a low watermark of max(total/32, 1024 frames).
- **D8. Shrinking.** Three triggers:
  - admission: with no headroom, a fill recycles the cache's own least recently used page, or reads uncached;
  - `Balance()`, which the writeback task calls every 5 s, trims to the watermark plus half of it;
  - a failed `AllocatePageFrame` calls the registered reclaimer, then retries once. Contiguous allocations don't reclaim.
- **D9. Lock and overlap.**
  - One cache-wide `Host::Lock` (in the kernel an interrupt-saving spinlock). It is a leaf in D15's level 5 (`docs/design/M30-P5.md`), never held across a device call, an allocation, a free or a log.
  - A volume whose range overlaps another open volume is attached with no cache, and a warning is logged.
- **D10. Exposure.** `/proc/meminfo` gains `Cached:\t<kB>`. No other /proc file.
  - `BlockDevice::DeviceStatistics()` (read and written sectors, flushes, counted in `VirtioDisk`, below the cache) and `PageCache::Statistics()` are kernel APIs. The kernel test uses them as its oracle.
  - `CoreDriver::InvalidateCache()` exists for the kernel test only. There is no drop-caches control.

```cpp
namespace FeatherDisk {
inline constexpr std::size_t CachePageSize = 4096;

class PageSource {
public:
    virtual std::uint8_t* AllocatePage() = 0;       // CachePageSize bytes, or null
    virtual void FreePage(std::uint8_t* page) = 0;  // any context; never takes the cache lock
    virtual std::size_t Headroom() const = 0;       // pages the cache may still add
protected:
    ~PageSource() = default;
};

struct PageCacheStatistics {
    std::uint64_t pages, limit, hits, misses, bypasses, evictions, reclaimed, invalidated;
};

class PageCache {
public:
    constexpr PageCache() = default;
    ~PageCache();
    Status Initialize(PageSource& source, std::size_t page_limit);  // allocates the tables once
    std::size_t Shrink(std::size_t pages);   // frees up to pages LRU pages; never blocks
    std::size_t Balance();                   // shrinks while Headroom() is 0
    void InvalidateAll();
    PageCacheStatistics Statistics() const;
private:
    friend class CachedDevice;
    struct Entry;   // see section 2
    ...
};

class CachedDevice final : public BlockDevice {
public:
    constexpr CachedDevice() = default;
    // Only while no filesystem uses it. A null cache passes everything through.
    void Attach(PageCache* cache, BlockDevice& lower);
    void Invalidate();   // drops this volume's pages; stays attached
    void Detach();       // Invalidate, then passes through
    std::uint32_t SectorSize() const override;
    std::uint64_t SectorCount() const override;
    Status Read(std::uint64_t first_sector, std::span<std::uint8_t> buffer) override;
    Status Write(std::uint64_t first_sector, std::span<const std::uint8_t> data) override;
    Status Flush() override;
private:
    PageCache* cache = nullptr;
    BlockDevice* lower = nullptr;
    std::uint64_t id = 0;
    std::uint64_t epoch = 0;   // guarded by the cache lock
};
}
```

## 2. In-memory layout

- **`PageCache` tables, set up once in `Initialize`:**
  - `Entry entries[limit]`, about 32 bytes each: `volume` (u64), `page` (u64), `data` (u8*) (no `sectors` field: a page's length follows from the volume), and `lru_prev`, `lru_next`, `hash_next` as u32 indexes;
  - `uint32_t buckets[pow2 >= limit]`;
  - a free-entry list;
  - one LRU list, most recent at the head;
  - `pages`, `limit` and the statistics;
  - `next_id`;
  - `lock` (`Host::Lock*`).
- **The tables are the only heap memory, and only `Initialize` allocates it.** Page data comes from the `PageSource`.
- **`CachedDevice`:** `cache`, `lower`, `id` and `epoch`. `epoch` changes only under the cache lock.
- **Read path, for each page the request touches:**
  1. Under the lock, look up `(id, page)`. A hit copies the asked sectors and moves the entry to the LRU head.
  2. On a miss, remember `e0 = epoch` and release the lock.
  3. Take a frame: allocate one while `pages < limit` and `Headroom() > 0`. Otherwise, under the lock, unlink the LRU tail and reuse its frame.
  4. Read the page's sectors inside the volume into the frame, without the lock.
  5. Copy the asked part to the caller.
  6. Under the lock, insert the page only if `epoch == e0` and the page is still absent. Otherwise free the frame after releasing the lock.
- **Write path:** take the lock, `++epoch`, release it; then `lower.Write(first, data)`; then take the lock, `++epoch`, and copy into present pages on success or unlink them on failure; release, then free the unlinked frames.
- **`Balance`** frees one page per lock hold and stops as soon as `Headroom()` is above 0. `Attach` detaches first, so a second attach drops the old pages. After a write, pages are updated or dropped one per lock hold.
- **`Shrink`:** unlinks up to 32 LRU-tail entries per lock hold into a local array, releases the lock, frees their frames, and repeats.
- **`Invalidate`:** `++epoch`, then walks `entries` for its id in batches of 32, in the same way.
- **`BlockCache` over a caching device** has `slot_count == 0`, `data == nullptr` and `lock == nullptr`. Its `Read` and `Write` touch only the device and the caller's buffers.
- An ext mount in the kernel thus holds, below the VFS:
  - the jbd2 layers (the transaction's blocks, unchanged);
  - the page cache's pages (shared by all volumes);
  - nothing else.

## 3. Invariants

- **I1. Coherence with the device.** Take a page while the cache lock is free and no write to it is in flight. Its bytes equal the lower device's bytes for its sectors. So a read through a `CachedDevice` returns what the uncached device would return.
- **I2. One path, one cache.**
  - In the kernel, every read and write of a volume's sectors passes its `CachedDevice`.
  - Only the partition scan and the kernel test's sector 2047 use `CoreDevice()` raw, and both lie outside every volume.
  - Over an attached `CachedDevice` the core's `BlockCache` has no slots. So no copy of a disk block lives below the core except in the page cache.
  - The jbd2 layers are the transaction's own blocks, not copies of the disk, and are unchanged.
  - The cache lock never nests with another lock.
- **I3. Write-through and ordering.**
  - `CachedDevice::Write` returns only after `lower.Write` returned, and returns its status.
  - `Flush` is `lower.Flush()` with no work of its own; the cache holds no dirty data.
  - The lower device receives exactly the sequence of `Write` and `Flush` calls the `CachedDevice` received, with the same arguments, in the same order.
  - The cache never writes on its own. **Riskiest.**
- **I4. Errors.**
  - A failed lower read inserts nothing.
  - A failed lower write drops every cached page it touched.
  - A page fill that fails retries just the asked sectors uncached, so the cache never reports an error the uncached request would not.
  - The cache never adds `ENOMEM`: when it has no frame it reads uncached.
  - **Riskiest.**
- **I5. Fill epoch.** A fill is inserted only if its volume's `epoch` has not changed since before its lower read. `Write` bumps the epoch before and after the lower write; `Invalidate` and `Detach` bump it too. So no fill that overlapped a write or an invalidation is ever cached. A cache-wide `generation`, bumped by `InvalidateAll`, is checked the same way (step 1: the epoch lives in `CachedDevice`, so `InvalidateAll` needs its own counter). **Riskiest.**
- **I6. Per-volume keys.** The key is (volume id, volume-relative page). Ids come from a counter that is never reused, and every `Attach` takes a new one. No lookup by one volume finds another volume's page, or a page from an earlier attach of the same slot.
- **I7. Invalidation.**
  - `Forget` (a vanished partition or a rescan that reopens a slot) detaches before `volume.Assign`.
  - An unmount (`Driver::Detach`) invalidates.
  - A volume `MountBlockDevice` keeps (I14 of Part 5) keeps its pages.
  - A remount keeps its pages, because it doesn't change the disk behind the cache.
- **I8. No overlap.** Two open volumes whose ranges overlap are not both cached. The later one passes through.
- **I9. Locking.**
  - The cache lock is a leaf (D15 level 5). It is taken only for index, LRU, epoch and statistics work and copies of at most 4 KiB.
  - Nothing under it blocks or calls a lower device, `PageSource::AllocatePage` or `FreePage`, `Host::Allocate` or `Host::Free`, or `Host::Log`.
  - Lower reads and writes run under the caller's volume mutex as today, never under a spinlock of the cache.
- **I10. Frame ownership.** A page frame is either free in the source, owned by one fill in flight, or linked in the index. Only linked frames are reachable under the lock. A frame is unlinked under the lock before it is reused or freed.
- **I11. Accounting.**
  - `pages <= limit`.
  - `pages` equals the source's outstanding frames, minus the frames of fills in flight (at most one per running read).
  - The cache grows only while `Headroom() > 0`.
  - After `InvalidateAll` and destruction, the source has no outstanding frames.
- **I12. Reclaim.**
  - `Shrink` and `Balance` may run in any context that does not hold the cache lock, including inside `AllocatePageFrame` with `heap_lock` or a page-table lock held.
  - They never allocate or touch the heap, and they free frames only after releasing the cache lock.
  - The allocator calls the reclaimer without `allocator_lock`, and retries once.
  - The cache never allocates under its own lock, so reclaim never re-enters it.
- **I13. Sizing.** `limit = CacheLimit(free, total)` at startup. `Balance` leaves `FreeFrameCount() >= watermark` or an empty cache.
- **I14. Pass-through.**
  - A 0-slot `BlockCache` issues exactly one lower call per call it receives:
    - `Read` becomes one `Read` of the whole block;
    - `ReadUncached` and `Write` keep the same arguments.
  - It keeps no state between calls.
  - `CachesBlocks()` is fixed while a filesystem is mounted on the device. `Attach` and `Detach` happen only in `OpenPartition` and `Forget`, around the core's mount.
  - **Riskiest.**

## 4. Write paths and crashes

**Claim.** In the kernel, the device receives exactly today's sequence of `Write` and `Flush` calls, with the same arguments, in the same order. So every crash outcome is unchanged.

**The stack, top to bottom: today and now.**

| Layer | Today | Now (kernel) | Writes and flushes it sends down |
|---|---|---|---|
| jbd2 `step`/`running`/`committed` | ordering, the transaction's blocks | unchanged | unchanged |
| `BlockCache` | 32 KiB of copies, write-through | 0 slots, pass-through (D2) | one `device->Write` per `Write`, same arguments, today and now (I14) |
| `CachedDevice` | none | write-through page cache | one `lower.Write` per `Write`, `Flush` is `lower.Flush` (I3) |
| `Partition::Volume`, `VirtioDisk` | unchanged | unchanged | unchanged |

- **Writes.** `BlockCache::Write` always issued exactly one device write with its arguments, before touching its copies. Pass-through keeps that call and drops only the copies. `CachedDevice` forwards it unchanged. Neither layer writes on its own, defers, merges or splits. Flushes are never handled by either layer: ext2 (`write.cpp`), jbd2 (`transaction.cpp`, `recovery.cpp`) and FAT16 call `volume.Flush()`, which reaches the device through `CachedDevice::Flush` unchanged. So the ordering stays as today:
  - ext2's write-through: data, then metadata, flushed at `Sync`;
  - jbd2's ordered mode:
    1. data blocks, `Flush`;
    2. descriptor and journal blocks, `Flush`;
    3. commit block, `Flush`;
    4. checkpoint writes, `Flush`;
    5. superblock.
- **One `CachedDevice::Write` and a crash.** The cache holds no dirty data and is lost in a crash, so the disk is what the lower calls made it:

| Crash point | Device | Same as today? |
|---|---|---|
| Before `lower.Write` (epoch bumped) | old bytes | yes: the write was never issued |
| During `lower.Write` (sector by sector in virtio) | some sectors new | yes: the same sectors in the same order |
| After `lower.Write`, before or after the cache update | new | yes |

- **Reads change, and change nothing on the device.**
  - Metadata hits move from the `BlockCache` to the page cache.
  - Some data reads are served from memory.
  - Fills read a whole 4 KiB page.
  - A fill that fails on a sector nobody asked for falls back to the exact request (I4), so no new read error appears.
  - Replay at mount reads the journal through the page cache. That is coherent by I1, and empty after a reboot.
- **Core tests.** The existing suites run unchanged over plain devices, still with a 32 KiB `BlockCache`. Three tests are new:
  - T14 compares today's configuration with the kernel's, byte for byte, at every cut;
  - T28 runs the ext suites in the kernel's configuration;
  - T26 checks the pass-through.

  The comment at `ext2_write_tests.cpp:436` ("The cache may hold the block's old bytes") still holds there. In T28 that test still remounts, and the remount runs over a new attach, so it reads the change.

## 5. Edge cases and errno

| Case | Result |
|---|---|
| Second read of a cached range | the bytes from memory; no device read |
| Lower read error on a miss, inside the asked sectors | `Error::Io` → `EIO`; nothing cached; the next read tries the device again |
| Lower read error only in the page's other sectors | the asked sectors are read uncached; success; the page is not cached |
| Read error after the page was evicted or invalidated | `EIO`, as today |
| Lower write error | `EIO` (as today: ext2 stays `rw` and each change fails, a journal aborts and goes `ro`); the touched pages are dropped, so the next read sees the device |
| Write to a read-only lower device | `EROFS` from the device; pages dropped (harmless) |
| `Flush` error | `EIO`, as today; the cache is unaffected |
| Request not a whole number of sectors, or past the volume | the lower device's error (`EINVAL`), as today; nothing cached |
| Short last page | the page holds only the volume's sectors; nothing past the volume is read |
| No frame (limit 0, no headroom, empty LRU, allocation failure) | read uncached; never `ENOMEM` |
| Sector size above 4096 | volume uncached |
| Overlapping partitions | the later volume is uncached and a warning is logged; I/O unchanged |
| Write racing a fill on the same volume | the fill is not cached (I5); the read returns old or new bytes, as an uncached read could |
| Invalidate or Detach racing a fill | the fill is not cached |
| Rescan: the partition moved or vanished | `Forget` drops its pages; a new attach gets a new id |
| Unmount, then mount again | pages dropped at unmount; the first read refills |
| Memory exhausted by programs | `AllocatePageFrame` reclaims cache pages before failing; the program gets the frame |
| Shutdown or reboot | nothing to write back; `Quiesce` is unchanged |
| An ext mount over an attached `CachedDevice` | its `BlockCache` has 0 slots; repeated metadata reads hit the page cache |
| A kernel volume left uncached (overlap, no cache) | its `BlockCache` keeps 32 KiB, as today; I/O unchanged |
| Metadata read error, block in the page cache | served from memory, as a `BlockCache` hit was today |
| Metadata read error after the page was evicted | `EIO`, as today after a `BlockCache` eviction |
| `Attach` or `Detach` while a filesystem is mounted | not done: only `OpenPartition` and `Forget` call them, around the core's mount (I14) |

## 6. Sizing and memory pressure in this kernel

- **No memory-pressure hook exists today.** `AllocatePageFrame` fails at once. The heap (`GrowHeap`) never unmaps. Nothing reclaims memory.
- **Sizing.** `InitializeCache` reads `GetPageAllocatorStats` after the heap is up. It sets `limit = free/4` and `watermark = max(total/32, 1024)`. For QEMU's 2 GiB that is about 120,000 pages, which needs 3.8 MiB of descriptors and 0.5 MiB of buckets from the heap, once. The whole 166 MiB test disk fits.
- **Admission.** A fill allocates only while `pages < limit` and the free frames are above the watermark. Otherwise it recycles the LRU tail. So the cache never takes the last 1/32 of memory from programs.
- **Periodic trim.** The writeback task (5 s) calls `BalanceCache()`. Below the watermark, it shrinks until the free frames reach 1.5 times the watermark, or the cache is empty.
- **On allocation failure.** `AllocatePageFrame` calls the registered reclaimer (`Cache().Shrink(32)`) with no allocator lock, then retries once. This covers user page faults, `process.cpp` frames, kernel stacks, page tables and heap growth, since they all go through `AllocatePageFrame`. The reclaimer is null until `InitializeCache`.

## 7. Tests

### Step 1: the page cache (core; `page_cache_tests.cpp` over `MemoryDevice` and `Partition::Volume`; the oracle is the device's read counter and bytes)

- **T1 Hit.** Read a range twice. The second read makes no device read, and the bytes equal the device's.
- **T2 Pages and the tail.** A volume of 8k+3 sectors inside a larger device with sentinel sectors around it. Reads at the end give the right bytes, and no device read touches a sector outside the volume.
- **T3 Eviction.** With limit N, an access sequence is checked against an LRU model: which reads go to the device, and how many.
- **T4 Model.** Random reads, writes, `Invalidate`, `Shrink` and reattaches over three volumes with limit 4. Each read equals a byte-array model, and the device equals the model after every write.
- **T5 Write-through.** A recording device below the cache. The call log (writes with bytes, and flushes) equals the calls made. After each `Write` returns, the device holds the bytes.
- **T6 Failed write.** `FailWritesAfter`: the next read of the touched page goes to the device and returns the device's bytes.
- **T7 Read errors.** `FailReadsAt` outside the asked sectors: the read succeeds and nothing is cached. Inside them: `Io`, then `RestoreReads` and success with a device read.
- **T8 After eviction.** Cache a page, `Shrink`, `FailReadsAt`: `Io`.
- **T9 Invalidation.** `Invalidate` drops only its own volume (the other still hits). After `Detach` and `Attach`, bytes changed behind the cache are seen.
- **T10 Epoch.** `MemoryDevice::on_read`, during a fill, writes through the cache, or invalidates. That fill is not cached, and the next read returns the new bytes.
- **T11 Keys.** Two volumes with different bytes at the same relative page each read their own.
- **T12 Accounting.** `Statistics().pages` equals the source's outstanding pages. `Shrink(n)` frees n. With `Headroom()` 0 the cache recycles and never allocates. With a failing source, reads still succeed (`bypasses`). After destruction nothing is outstanding (ASan).
- **T13 Threads (`[concurrency]`, TSan).** Four threads on separate volumes plus a shrinking thread, each checked against its model.

### Step 2: the core's metadata path (core)

- **T14 Crash identity, today versus the kernel.** Run each scenario of `ext_transaction_crash_tests.cpp` and `ext_rename_crash_tests.cpp` (ext3, ext4, ext4-64bit and ext2) twice:
  - (a) today's configuration: a 32 KiB `BlockCache` over the `MemoryDevice`;
  - (b) the kernel's: a 0-slot `BlockCache` over a `CachedDevice` with limit 4, over the `MemoryDevice`.

  The checks:
  - the `Reference` write counts, `flushes`, a write log with bytes and the final device are equal;
  - for every cut, the crashed device and every `CopyKeeping` loss pattern are byte-equal;
  - `RequireCommittedState` and `RequireLossyRecovery` pass on both.

  The existing crash suites run unchanged.
- **T15 e2fsck.** A random ext4 and ext2 write workload through the cache with limit 8. `e2fsck -fn` is clean, and the image is byte-equal to the uncached run.
- **T26 Pass-through `BlockCache`** (`block_cache_tests.cpp`, with a recording `MemoryDevice`).
  - With 0 slots:
    - every `Read` is one device read of the whole block, even when repeated;
    - `Write` is one device write with the same arguments, and its error is returned;
    - `ReadUncached` is unchanged;
    - no lock is created;
    - `SlotCount()` is 0.
  - A device with `CachesBlocks()` true gives an ext mount a 0-slot cache; a plain device gives it 32 KiB.
- **T27 One cache** (`page_cache_metadata_tests.cpp`). A counting device sits between the ext mount and an attached `CachedDevice`.

### Step 5: QEMU (both architectures, MBR and GPT)

- **T23 `CheckPageCache` (STORAGE).** It runs during startup, before `Writeback::Start`, so nothing else reads the disk. For `/samples/extents.bin` (2 MiB, ext4 root), `/big.txt` (ext2 `vda6`, mounted by the test) and a FAT16 file:
  1. `InvalidateCache()` on the volume;
  2. record `DeviceStatistics().read_sectors`;
  3. read the file and compare it with its pattern; the counter must grow by at least the file's non-hole sectors;
  4. read it again and compare; the counter must not change, and `hits` must grow.

  It prints `KERN/STORAGE: second read of a large file did no disk reads; boot N`, and `storage.py` expects it on both boots.
- **T24 `CheckCacheReclaim` (STORAGE).**
  1. With the cache holding P pages, allocate frames until `AllocatePageFrame` fails.
  2. The count must be at least `free_before + P - 32`, and the cache must end empty.
  3. Free all the frames, and re-read `/samples/extents.bin` correctly.

## 9. Decisions taken (2026-11-20)

1. **The core `BlockCache` in the kernel: replaced.** Over an attached `CachedDevice` it is a 0-slot pass-through (D2, I14), so the page cache is the only cache below the core. `fscli`, host tools and the plain core tests keep it.
2. **The code lives in the core,** with a `PageSource`.
3. **One cache per volume,** over `Partition::Volume`.
4. **4 KiB pages,** counted from the start of the volume.
5. **Size: a quarter of the free frames at boot,** with no fixed cap. Watermark: max(1/32 of RAM, 4 MiB).
6. **No write-allocate:** writes only update pages already cached.
7. **Pages are dropped on unmount.**
8. **`fscli` and host tools don't use the page cache.**
9. **Only `Cached:` in `/proc/meminfo`.** The device counters stay in the kernel test.
10. **Reclaim triggers:** admission, the writeback task's 5 s `Balance`, and a failed `AllocatePageFrame`. Contiguous allocations don't reclaim.
11. **No read-ahead past one page,** and no batching of misses.
12. **Overlapping partitions stay uncached,** with a warning.
13. **No drop-caches control,** only a kernel-test hook.

## 10. Risks for the implementer

- **Host filesystem tests that change the disk below the cache.** `filesystem_tests.cpp` sets `reads_fail` (for example in `CheckFailedReopen`) and has about 40 direct `disk[...]` accesses. A test that does this while a volume is open must call the test-only `Cache().InvalidateAll()`, or run with the cache off.
- **Frame-leak checks in `kernel_test.cpp`.** `RunTaskScalingTests` and the user-space test (around lines 464–495 and 777–820) compare `free_frames`. If they span disk reads, they must run before the disk is mounted or add back the cached pages.
- **Reclaim runs inside the allocator.** It runs with `heap_lock` or page-table locks held. Any heap use or logging in `Shrink` deadlocks. Review this; T24 is the only kernel-side check.
- **Latency.** Copies under an interrupt-saving spinlock and page-wide fills (8 virtio round trips for one FAT16 sector) add latency; measure them with `benchmark` if needed.
- **The descriptor array is permanent heap**, about 32 bytes per page of the limit.
- **When `CachesBlocks()` is read.** It must be read at the core's mount, after `Attach`. A `CachedDevice` attached after the mount would leave a 32 KiB `BlockCache` over the page cache. T26 and T27 catch that.
- **The superblock read in `ext2.cpp:64`** goes to `volume` directly, as today. It is now cached by the page cache like everything else. No change is needed.
