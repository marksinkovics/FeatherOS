# M35: screen and input foundations (design)

**Scope.** The first of the desktop milestones in `docs/plans/gui-plan.md`. It changes nothing a user sees except the console's size. Checked against the code on `main` at `8b9ba14`:

- **Screen.** `Config::Width` and `Height` (`kernel/config.h`) are 1024 and 768. `Framebuffer` holds a static back buffer of that size and `init` refuses a larger mode. `TermConfig::Row` and `Column` size three static cell arrays in every `Term`. `Term::Init` already computes its grid from the framebuffer and clamps it to those constants. Both Limine configs ask for 1024x768.
- **Present.** `PresentFramebuffer` (`process.cpp`) checks every row's pages, then for each row copies it from the program into a bounce row (`CopyFromUserPaged`) and calls `Console::PresentRow`. That takes `display_lock`, converts the row into the back buffer (`PackRow`, a plain copy when the screen is XRGB8888), and calls `Framebuffer::draw(y, 1)`, which copies the **whole row** to the screen, however narrow the rectangle is.
- **Keys.** `Keyboard::Modifiers()` knows Shift, Control, Alt and Caps Lock. Codes 125 and 126 (`KeyCode::LeftMeta`, `RightMeta`) arrive from USB and virtio keyboards as ordinary keys. The PS/2 path's `ExtendedKeyCode` has no case for `E0 5B` and `E0 5C`, so those keys are dropped. `Console::TakeKey` sends `SIGINT` for `Ctrl+C` before it queues the key. `AcquireFramebuffer` refuses a non-zero argument, and `Term::SetGraphics(true)` blanks the screen.
- **Pointer.** The HID parser (`usb/hid/report.cpp`) takes X and Y fields only when their Input item is relative, so an absolute device such as QEMU's `usb-tablet` reports buttons and wheel but no position.
- **Time.** `Time::UptimeMilliseconds()` is `ticks * 1000 / ticks_per_second` at 100 Hz. `clock_gettime(CLOCK_MONOTONIC)` reads it through `ReadUptime`, so it moves in 10 ms steps. `ticks` is advanced by CPU 0 only.

This milestone adds, in order:
1. A screen size taken from Limine at run time, with the console grid following it.
2. What a compositor needs from the framebuffer device: a Super modifier, raw keys, taking the screen without blanking it, and absolute pointer positions.
3. A monotonic clock finer than a tick, a benchmark for `FB_PRESENT`, and a present that copies only the rectangle it was given.

Left out: changing the mode at run time, EDID, a different resolution for the USB stick image (`tools/make_usb_stick.sh` keeps its config), sleeps and `poll` timeouts finer than a tick, PS/2 mice, mapping the back buffer into a program (`FB_MAP`, M36 Part D), and any real-hardware step.

**Done when:**
1. `./build.sh unit-test` passes.
2. `bash tools/quality.sh check` passes.
3. `tools/check.sh --arch both --modes "SCREEN_SIZE GRAPHICS FONTS DUNGEON USB USB_TABLET TIMER SHELL"` passes.
4. `tools/check.sh --arch both --matrix` passes, including the new cases.
5. The measurement table in section 7 is filled in.

## Decisions

**User, 2026-11-25:** any screen resolution early, tested at 1024x768 and 1920x1080 in QEMU on both architectures. Real hardware is not part of this milestone.

**Design:**

- **D1. The back buffer is the caller's.** `Framebuffer::init` takes the buffer and its capacity, and refuses a mode that does not fit. The kernel allocates it in `InitializeDisplay`, which already runs after the memory and process set-up, as contiguous frames reached through the higher-half direct map. The host tests pass a vector. The 3 MiB static array goes away.
- **D2. The console grid has a static maximum of 320 columns by 100 rows** (2560x1600 at the 8x16 cell). `TermConfig::Row` and `Column` become that maximum, and `Term::Init`'s existing clamp does the rest: a larger screen shows the console in its top-left 2560x1600 pixels. The three cell arrays grow to 384 KiB per console, 1.5 MiB for the four, which is half of what the static back buffer used. No allocation enters the console, so panic and early logging keep their rule.
- **D3. `SCREEN=WxH`** (default `1024x768`) is a build option like `LIMINE_TIMEOUT`: `build.sh` rewrites both resolution lines when it writes the ISO's `limine.conf`. The smoke harness takes `--screen` and the matrix a `SCREEN` setting per case.
- **D4. Super is a fifth modifier bit, 16.** `KEY_LEFTMETA` (125) and `KEY_RIGHTMETA` (126) join the header. On a text console the Super keys still send no bytes, and a letter typed with Super held is still typed.
- **D5. `FB_ACQUIRE` takes flags in its argument.** `FB_ACQUIRE_RAW_KEYS` (1): `Ctrl+C` is only queued, with no `SIGINT`. `FB_ACQUIRE_KEEP_SCREEN` (2): the screen is not blanked, and keeps its pixels until the first present. 0 is today's behaviour; any other bit is `EINVAL`. `Alt+F1` to `Alt+F4` still switch consoles in every mode.
- **D6. Absolute positions are `EV_ABS` records on `/dev/mouse`,** with `ABS_X` and `ABS_Y` scaled to 0..32767 whatever the device's own range. The range is part of the ABI; there is no ioctl to ask for it, which differs from Linux and goes into `docs/posix.md`. Relative and absolute devices share the one stream, as devices do today.
- **D7. The fine clock interpolates between ticks.** Monotonic time is `ticks * tick_length` plus the time since CPU 0's last tick, read from the TSC or the AArch64 virtual counter and capped just below one tick length. It can never run ahead of, or drift from, the tick clock that sleeps use, and it needs the counter's frequency only to be right over 10 ms. A new syscall returns it in nanoseconds; `ReadUptime` and `fb_event.time_ms` keep their meaning.
- **D8. On x86-64 the TSC is used only when it can be trusted:** CPUID reports an invariant TSC, or the hypervisor bit is set (QEMU). Otherwise the clock stays at tick resolution, as it is today. AArch64 always has its counter.
- **D9. The present is shortened where it is certain to help.** `PresentRow` copies only the presented span to the screen. Whether to also drop the bounce row is decided from the benchmark and written into section 7; it is not done on a guess.

## ABI numbers reserved for M35 to M38

## 1. Design

### 1.1 Screen size (Part A)

- `Framebuffer::init(limine_framebuffer*, uint8_t* back_buffer, size_t capacity)` keeps today's checks on the pixel format and replaces the size checks with: width and height at most `User::MaximumFramebufferDimension`, and `pitch * height <= capacity`.
- `Framebuffer::RequiredBytes(const limine_framebuffer*)` returns `pitch * height`, or 0 for a mode `init` would refuse, so the kernel knows how much to allocate.
- `InitializeDisplay` asks for `RequiredBytes`, allocates that many whole pages with `Memory::AllocateContiguousPageFrames`, and passes their direct-map address. If the mode is refused or the frames cannot be had, it logs the reason and the kernel runs on serial only, exactly as it does today without a framebuffer.
- It logs one line for the tests: `Display: <W>x<H>, console <columns>x<rows>`.
- `config.h` loses `Config`; `Color` stays. `PresentFramebuffer` sizes its bounce row from the screen width it already reads.
- `TermConfig`: `Row` = 100, `Column` = 320 (D2). Nothing else in `Term` changes.

### 1.2 Build option and harness (Part A)

- `build.sh`: `SCREEN` must match `^[0-9]+x[0-9]+$`, each number 320 to 16384. The existing `sed` that writes `limine.conf` also rewrites `interface_resolution:` and `resolution:`.
- `tools/smoke_test.py --screen WxH` (default 1024x768) is stored on the case; `ScreenCase` takes its width and height from it instead of constants. `tools/matrix.py` passes a case's `SCREEN` setting to the build of its ISO and to the smoke test.
- QEMU needs no new device on x86-64 (the default VGA has 16 MiB). On AArch64 the mode comes from the firmware's list for `ramfb`. **The first act of step A2 is to boot AArch64 with `SCREEN=1920x1080` and read the `Display:` line.** If the firmware does not offer that mode, the AArch64 cases use the largest listed mode at least 1280 wide, and the mode is recorded in section 7.

### 1.3 Super and acquire flags (Part B)

- `Input::Modifier::Super` = 16. `Keyboard` gains `m_left_meta` and `m_right_meta`, set where the other modifier keys are. `Modifiers()` reports the bit. The `static_assert` in `graphics_mode.h` covers it.
- `arch/x86_64/keyboard.cpp`: `ExtendedKeyCode` maps `0x5B` and `0x5C` to the Meta codes.
- `GraphicsMode::Owners::Acquire` takes the flags and keeps `raw_keys` in the slot. `Owners::RawKeys(console)` reads it.
- `Console::AcquireDisplay(console, owner, flags)` passes them on and calls `Term::SetGraphics(true, keep_screen)`, which skips `Blank()` when asked.
- `Console::TakeKey` reads `RawKeys` in its first locked section and skips `SignalForeground` when it is set.
- `AcquireFramebuffer` accepts the two flags and refuses any other bit.
- `Graphics::Display` gets `Status Open(uint32_t acquire_flags)` beside `Open()`.

### 1.4 Absolute pointers (Part B)

- `Hid::Field` gains `bool relative`. The parser accepts `UsageX` and `UsageY` in both forms.
- `Hid::MouseReport` gains `bool has_position`, `x`, `y`: the absolute fields scaled to 0..32767 with 64-bit arithmetic, `(value - minimum) * 32767 / (maximum - minimum)`, clamped. A field whose maximum is not above its minimum is ignored.
- `usb/hid/driver.cpp`: a report with a position emits `EV_ABS` records for the axes that changed since the port's last report (both on the first one), then buttons, wheel and the sync record as today. `MaxMouseEvents` grows by 2.
- `user/syscall_abi.h` and `<featheros/input.h>` get the constants. `mousetest` prints `abs <x> <y>`.

### 1.5 The fine clock (Part C)

- `kernel/arch/fine_counter.h`, namespace `FeatherOS::Arch::FineCounter`, implemented in `arch/x86_64/fine_counter.cpp` and `arch/aarch64/fine_counter.cpp`:
  - `bool Initialize()`: true when the counter is usable (D8). On x86-64 it measures the frequency against 10 timer ticks, as `LocalApic::CalibrateTimer` does; on AArch64 it reads `CNTFRQ_EL0`.
  - `uint64_t Read()`: `rdtsc`, or `CNTVCT_EL0` after an `isb`.
  - `uint64_t Frequency()`.
- `kernel/time/monotonic.{h,cpp}`: the arithmetic, with no hardware in it, so it is host-tested:
  - `struct Sample { uint64_t ticks; uint64_t counter; }`
  - `uint64_t Interpolate(Sample sample, uint64_t counter_now, uint64_t frequency, uint64_t tick_nanoseconds)`
- `Time::MonotonicNanoseconds()` in `timer.cpp`: reads a consistent `Sample` through a sequence counter that CPU 0's tick handler writes, interpolates, and returns the larger of the result and the last value returned (an atomic maximum), so it never goes back on any CPU.
- Without a usable counter it returns `ticks * tick_nanoseconds`.
- Syscall 75 `ReadMonotonic` and `User::ReadMonotonic()`; libc's `clock_gettime(CLOCK_MONOTONIC)` reads it. `time.h`'s comment about 10 ms steps is corrected.

### 1.6 Benchmark and present (Part C)

- `fbbench` (C++, `FEATHEROS_PROGRAMS`): takes the console's screen and times `FB_PRESENT` with `CLOCK_MONOTONIC` for three rectangles: the whole screen, 640x480, and 32x32. It prints one line each, `fbbench: <W>x<H> <count> presents <microseconds> us each`, and `fbbench: done`. `--quick` does 3 presents of each for the smoke test.
- `Framebuffer::draw(uint32_t x, uint32_t y, uint32_t width, uint32_t height)` copies a span of rows. `Console::PresentRow` calls it with the presented span. The console's own callers keep the whole-row form.
- After that change, `fbbench` is run again. If the bounce pass is at least a fifth of a full-screen present in Release, a follow-up step copies XRGB8888 rows from the program straight into the back buffer; otherwise the bounce stays. Either way the numbers and the choice go into section 7.

## 3. Invariants

**Screen**
- **I1.** Nothing is written past the back buffer or the screen: `init` succeeds only when `pitch * height <= capacity`, and every draw clips to the width and height `init` stored.
- **I2.** A boot whose mode is refused, or whose back buffer cannot be allocated, still reaches the shell on the serial console.
- **I3.** At 1024x768 the console is 128 columns by 48 rows, as before, and every existing test's output is unchanged.

**Keys**
- **I4.** A raw owner never causes a signal: with `FB_ACQUIRE_RAW_KEYS`, `Ctrl+C` arrives as two key events and the foreground group receives nothing. **Riskiest,** because a missed case kills the future compositor.
- **I5.** Raw mode ends with the owner: after release, close or exit, `Ctrl+C` on that console signals again.
- **I6.** The event queue stays well formed per key (press, repeats, release) for the Meta keys as for any other.
- **I7.** With `FB_ACQUIRE_KEEP_SCREEN`, no pixel changes between the acquire and the first present.

**Pointer**
- **I8.** An absolute value is always within 0..32767, whatever the device reports, including values outside its own logical range.

**Time**
- **I9.** `MonotonicNanoseconds()` never decreases, on one CPU or across CPUs. **Riskiest.**
- **I10.** It agrees with the tick clock: `UptimeMilliseconds() <= MonotonicNanoseconds() / 1000000 < UptimeMilliseconds() + 10`, when both are read without a tick in between.
- **I11.** A reader never uses half of a sample: the tick count and its counter value come from the same tick.

**Present**
- **I12.** The span copy changes which bytes are copied, not which pixels end up on the screen: every existing `screendump` check passes unchanged.

## 4. Edge cases

| Case | Result |
|---|---|
| Mode larger than 2560x1600 | The console uses the top-left 2560x1600; `FB_GET_INFO` and `FB_PRESENT` use the whole screen |
| Mode smaller than 1024x768 | The console grid shrinks; nothing else changes |
| `SCREEN` not `WxH`, or out of range | `build.sh` stops with an error before building |
| `FB_ACQUIRE` with an unknown flag bit | `EINVAL`, nothing acquired |
| Acquire with keep-screen on a console that is not shown | Succeeds; nothing is drawn, as today |
| A second acquire by the owner with different flags | Returns 0 and keeps the first flags, as a repeated acquire does today |
| Super held during a console switch | The owner gets the releases and `Hidden` as for any held key |
| Absolute field with maximum not above minimum | The field is ignored; the device still reports buttons and wheel |
| A device with both relative and absolute axes | Both kinds of record are sent |
| Counter not usable (x86-64 without a trusted TSC) | The clock has tick resolution; `ReadMonotonic` still works |
| A tick is late (interrupts off for more than 10 ms) | The clock stops just below the next tick's time until the tick arrives, then continues; it never goes back |
| The counter reads lower than the sample (CPUs slightly apart) | The elapsed part is taken as 0 |
| A present rectangle of width 0, or wholly off screen | Nothing is copied, as today |

**Unit (host).**

- **T7** `hid_report_tests.cpp`: QEMU's tablet descriptor parses with absolute X and Y; scaling at the minimum, the maximum, the middle, and a value outside the range (I8); a field with maximum equal to minimum is ignored; the boot mouse is unchanged.

- **T9** `monotonic_tests.cpp`: `Interpolate` at the sample, in the middle of a tick, at and beyond a whole tick (capped one nanosecond below), with a counter below the sample (0 elapsed), and with frequencies from 1 MHz to 5 GHz without overflow (I10).
- **T10** `monotonic_tests.cpp`, tagged `[concurrency]`: one writer advancing samples and several readers; no reader sees a decrease or a mixed sample (I9, I11). It also runs under `./build.sh unit-test-tsan`.
- **T11** `framebuffer_tests.cpp`: `draw(x, y, width, height)` copies exactly that span, for 32-bit and 24-bit formats, and clips at the right and bottom edges.
- **T12** `framebuffer_tests.cpp`: a present followed by the span draw leaves the screen equal to a present followed by a whole-row draw, for random rectangles (I12).

**QEMU (both architectures).**

- **T13** `SCREEN_SIZE_TEST` with `SCREEN=1920x1080`: the `Display:` line gives the size; the `screendump` has that size; the status bar and the shell prompt are found at their cells by the `FONTS` reference renderer; `fbdemo` prints `tty1 1920x1080` and its pattern matches, computed for that size; the console returns after it exits.

**Mutation checks** (each must fail the named test, then be reverted): `init` accepting `pitch * height` one byte over the capacity (T1); `TakeKey` signalling a raw owner (T16); `SetGraphics` blanking with keep-screen set (T17); the absolute scale without its clamp (T7); `Interpolate` without its cap (T9); the reader ignoring the sequence counter (T10); the span draw using the whole row's offset (T11).

## 7. Measurements

Filled in by steps A2, C2 and C3. Microseconds per `FB_PRESENT`, QEMU with TCG.

**AArch64 mode used for the 1920x1080 cases:** none. Booted with `SCREEN=1920x1080` (also 2560x1440, 1280x720, 1280x1024, 1600x1200, 4096x2160) the kernel logged `Display: 800x600, console 98x35`: the firmware's `ramfb` offers only 640x480, 800x600 and 1024x768 (`1024x768` gave `1024x768`), and Limine falls back to 800x600. No listed mode is 1280 wide, so the AArch64 `screen_size` case runs at 800x600, below the default; the design's "tested at 1920x1080 on both architectures" holds on x86-64 only. Neither `bochs-display`, `VGA` nor `virtio-gpu` gives Limine a linear framebuffer with this firmware; a kernel virtio-gpu driver was deferred by the user (2026-11-26, `docs/ideas.md`). ## 8. Open questions

None for the user. Two are settled by measurement inside the milestone: the AArch64 mode (A2) and the bounce row (C3).
