# M32 Part 2: key events (design)

**Scope.** While a console is acquired and shown, its owner reads key presses, repeats and releases from the `/dev/fb0` descriptor it acquired with, as whole 8-byte events. It also gets `Shown`/`Hidden` when consoles switch (D8). The rules for a key event:
- A second press of a held key is a repeat (D10).
- Ctrl+C also sends `SIGINT` (D11); Ctrl+Z is only queued.
- The queue holds 64 events and drops and counts the newest when full (D9).
- Timing is unchanged (D12).

Part 1's invariants I1–I12 (`M32-P1.md`) still hold; this part adds I13–I23.

**Done when:**
1. `./build.sh unit-test`;
2. `bash tools/quality.sh check`;
3. `tools/check.sh --arch both --modes "SHELL GRAPHICS"`;
4. matrix cases 47 and 48 pass (`GRAPHICS_TEST`, extended; no new case).

## 0. What exists and what this builds on

- **`Input::SubmitKey(keyboard, code, pressed)`** (`src/kernel/input/input.cpp`) runs in IRQ context.
  - Both drivers call it the same way. The x86-64 PS/2 driver (`OnKeyboardScanCode`) passes `pressed = !(scan & 0x80)`. The AArch64 virtio-input driver (`HandleKeyEvent`) passes `value != 0`, so a repeat (value 2) arrives as another press.
  - `Keyboard::Press` keeps the modifiers and Caps Lock, and returns VT100 bytes (none for a release).
  - `TakeConsoleSwitch` then routes Alt+F1–F4 to `Console::Show`.
  - Releases reach no one. Nothing tracks which keys are held.
- **Serial input** goes straight to `serial_target` (tty1's terminal), not through `SubmitKey`. So `fbdemo` can still be driven from serial while it owns the screen.
- **Ctrl+C today** becomes byte 0x03, then `Terminal::Receive`, then `DeliverJobSignal`, then the `interrupt_group` hook (`Process::InterruptGroup`, which takes `process_lock`, a spinlock). This already runs in IRQ context and only if `TerminalSignals` (ISIG) is set. Session leaders are never signalled.
- **`console.cpp`:**
  - `display_lock` (a spinlock, held with IRQs off) guards `shown_console` and `GraphicsMode::Owners owners`.
  - `Show` runs from the keyboard IRQ.
  - `AcquireDisplay`, `ReleaseDisplay` and `PresentRow` are the owner API. `Files::SetFramebufferRelease(ReleaseOwner)` releases on the last close.
- **Blocking and waking.**
  - `Scheduler::WaitOn(queue, spinlock, deadline)` is the condition-variable pattern `Terminal::WaitForInput` and `Pipes::Read` use: check under the lock, then `WaitOn`.
  - Signal delivery calls `WakeTask`. `CallerInterrupted()` (`process.cpp`) tells a woken reader to return `EINTR`.
  - `poll` loops on `Poll::Generation()` and `Poll::WaitForChange`; `Poll::Notify()` wakes it, from any context.
- **`Files`:**
  - `OpenFile::nonblocking` is set at open only for `PseudoTerminalMaster`.
  - `StatusFlags` (`F_SETFL`) already sets it for any kind that is not a terminal, `Framebuffer` included.
  - `Files::PollEvents` returns 0 for `Framebuffer`. `ReadSyscall` returns `EINVAL` for it.
- **`ReadUptimeSyscall`** is `TickCount() * 1000 / TicksPerSecond()`; that is libc's `CLOCK_MONOTONIC`.
- **QEMU does not auto-repeat** keys injected over QMP (PS/2 and virtio alike); repeats come from the host UI. The harness therefore sends a second `down` for a held key to simulate a repeat, which is what a real keyboard does.

## 1. Files, types, signatures

### 1.1 ABI: `src/user/syscall_abi.h`

struct FramebufferEvent { uint16_t code; uint8_t kind; uint8_t modifiers; uint32_t time_ms; };  // 8 B

- `FramebufferInfo::dropped_events` is the calling file's count since it acquired; it is 0 if the file owns no console.

### 1.3 Kernel

**`src/kernel/input/keyboard.{h,cpp}`: held keys (D10)**

```cpp
enum class KeyTransition : uint8_t { None, Press, Repeat, Release };
namespace KeyCode { constexpr uint16_t Z = 44, C = 46; ... }
namespace Modifier { constexpr uint8_t Shift = 1, Control = 2, Alt = 4, CapsLock = 8; }
// Keyboard:
static constexpr uint32_t TrackedKeys = 256;
// Press for a key not held, Repeat for one held, Release for one held; None for a release of a key
// not held and for codes >= TrackedKeys.
KeyTransition Track(uint16_t code, bool pressed);
uint8_t Modifiers() const;
uint64_t m_held[TrackedKeys / 64] = {};
```

- The held set follows the hardware whatever the console or mode. Only the drivers' press and release calls change it.

**`src/kernel/input/input.{h,cpp}`: routing**

```cpp
struct KeyEvent { uint16_t code; KeyTransition transition; uint8_t modifiers; };
// Called for every key but a console switch, perhaps in interrupt context; true if it took the
// key, so its bytes do not go to the terminal.
void SetGraphicsKeys(bool (*take_key)(const KeyEvent& event));
bool IsInterruptKey(const KeyEvent& event);   // a Press of C with Control
```

`SubmitKey` does the following, in order:
1. `transition = keyboard.Track(code, pressed)`.
2. `length = keyboard.Press(...)`.
3. If `TakeConsoleSwitch` is true, switch and return.
4. If `transition != None` and the hook takes the key, return.
5. Otherwise, if `length > 0`, call `SubmitBytes`.

**Decision: an Alt+F1–F4 press is never queued.** The kernel consumes it and the program cannot act on it. Its release arrives later on whichever console is shown and is dropped by the seen-set rule below, so the owner's stream stays well formed with no special case. Alt's own press is queued, and the `Hidden` that follows releases it.

**`src/kernel/framebuffer/graphics_mode.{h,cpp}`: the queue (still without locks or kernel dependencies, host-tested)**

```cpp
constexpr uint32_t KeyEventLimit = User::FramebufferEventCapacity - 2;   // 2 slots kept for Shown/Hidden
class EventQueue {
public:
    bool Push(const User::FramebufferEvent& event, uint32_t limit);  // false and ++dropped at limit
    uint32_t Pop(User::FramebufferEvent* events, uint32_t capacity);
    uint32_t Size() const; uint32_t Dropped() const; void Clear();
private:
    User::FramebufferEvent m_events[User::FramebufferEventCapacity]; uint32_t m_head = 0, m_size = 0, m_dropped = 0;
};
// Owners (changed and added):
uint64_t Acquire(uint32_t console, const void* owner, bool shown, uint32_t time_ms);
uint32_t Release(const void* owner);                  // also discards the queue, seen keys, dropped
bool DeliverKey(uint32_t console, const Input::KeyEvent& event, uint32_t time_ms); // false: no owner
void Hide(uint32_t console, uint8_t modifiers, uint32_t time_ms);   // no-op without an owner
void Show(uint32_t console, uint32_t time_ms);
uint64_t TakeEvents(const void* owner, User::FramebufferEvent* events, uint32_t capacity); // InvalidArgument if none
uint32_t PendingEvents(const void* owner) const;
uint32_t DroppedEvents(const void* owner) const;
private:
struct Slot { const void* owner; EventQueue queue; uint64_t seen[Input::Keyboard::TrackedKeys / 64]; };
Slot m_slots[Console::Count] = {};
```

- **A fresh acquire** clears the slot and queues `Shown` if `shown`, else `Hidden`, so the program's first event states its visibility. An acquire by the file that already owns the console changes nothing.
- **`DeliverKey`'s rules** use the per-owner `seen` set (the keys the owner was told are down):
  - A Press or Repeat of a key in `seen` is queued as `Repeat`.
  - A Press or Repeat of a key not in `seen` is queued as `Press`, and the key joins `seen` only if the push succeeded. A key held across `Shown` or across the acquire thus starts with a Press.
  - A Release of a key in `seen` is queued, and the key leaves `seen` only if the push succeeded (an owed release).
  - A Release of a key not in `seen` is ignored and not counted as dropped.
  - Key events use `limit = KeyEventLimit`.
- **`Hide`** queues a `Release` for each `seen` key in ascending code order, with the current modifiers. It then queues `Hidden` with the full limit and clears `seen`. Releases that do not fit count as dropped. **`Show`** queues `Shown` with the full limit.
- `static_assert` that the `Input::Modifier` bits equal the `User::FramebufferModifier*` bits.
- The wait queues stay out of `Owners` (unlike the sketch in P1 §1.4), so this file keeps no scheduler dependency.

**`src/kernel/console.{h,cpp}`**

```cpp
uint64_t TakeEvents(const void* owner, User::FramebufferEvent* events, uint32_t capacity);
void WaitForEvents(const void* owner);   // returns at once if events wait or owner holds none
int16_t PollEvents(const void* owner);   // PollReadable, PollError if owner holds none, else 0
uint32_t DroppedEvents(const void* owner);
```

- **New state.** `constinit Scheduler::WaitQueue event_waiters[Count]` sits next to `owners`. A file-local `bool TakeKey(const Input::KeyEvent&)` is installed by `Initialize` through `Input::SetGraphicsKeys`, only when there is a framebuffer.
- **`TakeKey`:**
  1. Under `display_lock`, read `console = shown_console`. If `!owners.Acquired(console)`, return false.
  2. Unlock. If `Input::IsInterruptKey(event)`, call `console_terminals[console].SignalForeground(User::SignalInterrupt)`.
  3. Lock again. If the console is still shown and acquired, `DeliverKey`, then `WakeAll(event_waiters[console])`.
  4. Unlock, then `Poll::Notify()`.
  5. Return true if the key was delivered or a signal was sent. Otherwise return false, and the bytes go to the terminal (the owner released between the two locks).
- **`Show`**, under its existing lock:
  - If the old console is acquired: `owners.Hide(old, modifiers, now)` and `WakeAll`.
  - Then `SetShown` as before.
  - If the new console is acquired: `owners.Show(new, now)` and `WakeAll`.
  - After unlocking: `Poll::Notify()`, then `NotifyStatusChanged()` as now.
  - The modifiers come from a new `Input::CurrentModifiers()`, which reads the keyboard that called the switch: `SubmitKey` stores them before it calls the switch hook.
- **`AcquireDisplay`** passes `console == shown_console` and the time.
- **`ReleaseDisplay`** (both `FB_RELEASE` and the last-close hook) calls `WakeAll(event_waiters[console])` before unlocking and `Poll::Notify()` after.
- **`WaitForEvents`:** `flags = display_lock.LockIrqSave()`; if the owner still holds a console and `PendingEvents == 0`, `Scheduler::WaitOn(event_waiters[console], display_lock)`; then `UnlockIrqRestore`.
- **The time** is `Time::UptimeMilliseconds()` truncated to 32 bits. It is a new function in `time/timer.{h,cpp}`, also used by `ReadUptimeSyscall`, so `time_ms` is `CLOCK_MONOTONIC` by construction.

**`src/kernel/terminal/terminal.{h,cpp}`:** `void SignalForeground(int signal)` calls `process_hooks.interrupt_group(ForegroundGroup(), signal)`. It ignores ISIG, because D11 exists to stop a stuck program even when it turned ISIG off, and it echoes no `^C`, because the key never reached the terminal.

**`src/kernel/files.{h,cpp}`**
- At open, `nonblocking` is also honored for `Kind::Framebuffer`.
- `HoldFramebuffer(table, descriptor, const void** owner, bool* nonblocking = nullptr)` reports the flag under `file_system_lock`.

**`src/kernel/process.cpp`**
- **`ReadSyscall`:** the `Framebuffer` branch calls the new `ReadFramebufferEvents(process, descriptor, buffer, length)`:
  1. `FramebufferHold` (with `nonblocking`).
  2. `!Console::OwnsDisplay` gives `EINVAL`.
  3. `length == 0` gives 0; `length < 8` gives `EINVAL`.
  4. `wanted = min(length / 8, 64)`; an unwritable range gives `EFAULT`.
  5. Loop:
     1. `TakeEvents` into a stack array of 64 (512 B).
     2. If there are events, `CopyToUser` and return `n * 8` (`EFAULT` if the copy fails; those events are lost).
     3. If nonblocking, return `SyscallErrorWouldBlock`.
     4. If `CallerInterrupted()`, return `SyscallErrorInterrupted`.
     5. `Console::WaitForEvents(owner)`.
- **`PollSyscall`:** a `Kind::Framebuffer` entry calls `FramebufferPollEvents`, which takes a hold and returns `Console::PollEvents(owner)`.
- **`ReportFramebufferInfo`** takes the owner and fills `dropped_events = Console::DroppedEvents(owner)`.
- **No background check on read.** Keys go to the owner whatever its group, since the owner of the shown console is what the user sees.

## 2. Invariants (continuing from I12)

- **I13. One destination per key.** While the shown console is acquired, every tracked key goes to its owner's queue and never to the terminal. Otherwise keys go to the terminal exactly as before. Alt+F1–F4 presses go to neither. Ctrl+C is the only key with a second effect, its `SIGINT`.
- **I14. The stream is well formed per key: `Press (Repeat)* Release`.** **(mutation)** A `Repeat` or `Release` is never delivered for a key whose `Press` the owner did not get. The `seen` set enforces this, including across drops, `Shown` and acquiring while a key is held.
- **I15. Switching away releases first.** **(mutation)** `Hidden` follows a `Release` for every key in `seen` (ascending codes). No key event follows `Hidden` until `Shown`. After the first event, `Shown` and `Hidden` alternate, unless the reserved slots overflow, which is counted.
- **I16. The queue is bounded and never overwrites.**
  - It holds at most 64 events. Key events never take the last 2 slots.
  - A push that does not fit is dropped and counted.
  - `dropped_events` counts drops since the acquire.
  - The order of queued events is the order of the calls.
- **I17. No lost wakeups from events.** **(mutation)**
  - The empty check and `WaitOn` happen under `display_lock`.
  - Every push and every release calls `WakeAll(event_waiters[c])` under that same lock, and `Poll::Notify()` after it.
  - For Ctrl+C, the signal is sent before the event is pushed, so a reader that misses the signal's `WakeTask` is woken by the push.
  - Other signals keep the window `Pipes::Read` already has; it is not widened.
- **I18. A read returns whole events only.**
  - It returns `8·n` bytes with `1 ≤ n ≤ min(length / 8, 64)`.
  - `EAGAIN` with `O_NONBLOCK`; `EINTR` only when it took no event; `EINVAL` for `1 ≤ length < 8`.
  - A blocked read never returns 0.
- **I19. Release discards.** `Owners::Release` clears the queue, `seen` and the dropped count, and wakes readers, which then fail with `EINVAL`. A later acquire starts with only its state event.
- **I20. D11.**
  - Ctrl+C sends `SIGINT` to the console's foreground group, outside `display_lock`, whatever ISIG says, on `Press` only (not `Repeat`).
  - It is then queued like any key.
  - Ctrl+Z is only queued.
- **I21. D10 is identical on both targets.** The transition depends only on `Keyboard::Track` over the hardware's press and release calls, and both drivers feed `SubmitKey` the same way.
- **I22. Lock order.**
  - `file_system_lock` → `display_lock` → `scheduler_lock`.
  - `process_lock` and `poll_lock` are never taken while `display_lock` is held.
  - The IRQ path holds `display_lock` at most once at a time.
- **I23. Times.** `time_ms` is `CLOCK_MONOTONIC` in milliseconds, modulo 2^32, and never decreases within one queue.

## 3. Edge cases and errno

| Case | Result |
|---|---|
| `read` on fb before acquire, after `FB_RELEASE`, or by a non-owner dup's file | `EINVAL` (the file is the owner; a `dup` shares it, so it reads the same queue) |
| `read` with length 0 (owner) | 0 |
| `read` with length 1–7 | `EINVAL` |
| `read` with length 12 | one event, 8 |
| `read` empty, `O_NONBLOCK` (from `open` or `F_SETFL`) | `EAGAIN` |
| `read` empty, a signal arrives | `EINTR` (`SA_RESTART` is not honored, as elsewhere) |
| a reader blocked while another thread `FB_RELEASE`s | wakes, `EINVAL` |
| a reader blocked while another thread `close`s the descriptor | stays blocked; its hold keeps the file and ownership (as Linux's `close` does not wake `read`) |
| unwritable buffer | `EFAULT`, nothing taken |
| `poll` on an owner | `POLLIN` iff events wait |
| `poll` on a non-owner fb | `POLLERR` (a read would fail at once) |
| first event after acquire | `Shown` if the console is shown, else `Hidden` |
| key code ≥ 256 | not tracked, not queued; goes to the terminal path (no bytes) |
| release of a key the owner never saw pressed | ignored, not counted |
| 70 events without a read | 62 key events queued, the rest counted; `Shown`/`Hidden` still fit twice |
| Ctrl+C with only the shell in the group (session leader) | no signal (as the terminal); still queued |
| owner released between `TakeKey`'s two locks | the key goes to the terminal as bytes |

### QEMU, step 1 (SHELL session, both architectures): `fbtest` additions (T17)

The checks run in order. 1–3 come before acquire; 4 and 5 drain the state event and run the blocking checks; 6 and 7 come after the parent's release; 8 is two child modes started like Part 1's.

1. `read` before acquire gives `EINVAL` (as now).
2. `poll` on the unacquired fb gives `POLLERR`.
3. Acquire.
4. Poll, then read the state event:
   1. `poll(POLLIN, 0)` gives 1.
   2. `read(8)` gives one event, `kind == FB_EVENT_SHOWN`, `code == 0`.
   3. `poll(POLLIN, 30)` gives 0.
5. Short reads and `O_NONBLOCK`:
   1. `read(4)` gives `EINVAL`; `read(0)` gives 0.
   2. `F_SETFL O_NONBLOCK`, then `read(8)` gives `EAGAIN`; clear it again.
   3. A second `open("/dev/fb0", O_RDWR | O_NONBLOCK)` has the flag in `F_GETFL`.
   4. `FB_GET_INFO` gives `dropped_events == 0`.
6. A thread blocks in `read`; the main thread `FB_RELEASE`s; the thread gets `EINVAL`.
7. A child `eintr` acquires, drains, reports `r`, then blocks in `read`. The parent sends `SIGUSR1` (the handler is installed without `SA_RESTART`). The child reports `i` for `EINTR`.
8. A child `nonblockopen` acquires through an `O_NONBLOCK` open and reads twice: `Shown`, then `EAGAIN`.

### QEMU, step 2 (`GRAPHICS_TEST=ON`, both architectures)

**`fbdemo --keys [seconds]`.**
- Acquires and presents the pattern, then polls stdin and the fb.
- Each event prints `fbdemo: event <press|repeat|release|shown|hidden> <code> <modifiers>`.
- On `shown` it presents again and prints `fbdemo: presented`. It checks that `time_ms` never decreases and prints `fbdemo: time went backwards` if it does.
- Serial commands:
  - `p` stops reading the fb for 3 s (`fbdemo: paused` / `fbdemo: resumed`);
  - `q` quits.
- A `SIGINT` handler sets a flag. fbdemo then reads events until 200 ms pass without one, prints `fbdemo: interrupted`, releases and exits 130.
- At the end it prints `fbdemo: dropped N` from `FB_GET_INFO`.

The harness sends each event as its own QMP `input-send-event` (`{"type":"key","data":{"down":…,"key":{"type":"qcode","data":…}}}`) and waits for the expected serial lines, up to 3 s each.

## 6. Risks for the implementer

- **Repeated `down` over QMP.** Confirm early, on both targets, that QEMU passes repeated `down`s to PS/2 (as make codes) and to virtio-input (value 1). If one deduplicates, T18.4 needs a different oracle.
- **PS/2 buffer.** The PS/2 controller's small queue makes T19 lossy, so only "62 queued, dropped ≥ 1" is asserted.
- **`Show` and `TakeKey` share the IRQ path.** Keep `SignalForeground` and `Poll::Notify` outside `display_lock`.

## Settled here (by the design and the coordinator)

1. **Alt+F1–F4 presses are never queued** (§1.3); their releases fall to the `seen` rule.
2. **The first event after an acquire is `Shown` or `Hidden`,** so a program on a hidden console knows to wait.
3. **Ctrl+C signals regardless of ISIG and without a `^C` echo.**
4. **`dropped_events` is cumulative since the acquire.** Programs compare it with the last value they saw.
5. **`poll` on a non-owner fb reports `POLLERR`** rather than `POLLIN` (both make a read fail at once).
6. **Codes ≥ 256 are ignored** rather than widening the held set.
