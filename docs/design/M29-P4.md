# M29 Part 4: mount state, with remount and an honest `/proc/mounts` (design)

**Scope.** This part touches the core (one new `Filesystem` call), the kernel's VFS, `Files`, the mount syscall, libc, the `mount` program, and the harness. After it:

- `mount -o remount,ro <point>` and `mount -o remount,rw <point>` (libc `MS_REMOUNT`, 32) change the mode of a mounted ext2, ext3, ext4, FAT16 or tmpfs filesystem, the root included.
- A read-write remount follows a fresh read-write mount's rules.
- A read-only remount leaves the volume clean on disk while it stays mounted: for ext3/ext4 the journal is closed and `needs_recovery` is clear; ext2 is marked clean.
- `/proc/mounts` says `ro` from the moment a mounted filesystem starts refusing writes, for example after a journal abort. This removes M22-P6-s5's D3.

**Done when:** `./build.sh unit-test`, `bash tools/quality.sh check`, `tools/check.sh --arch both --modes "STORAGE SHELL"`, then `tools/check.sh --arch both --matrix`.

## Decisions (confirmed by the user, 2026-11-19)

- **P1.** A remount to read-only fails with `EBUSY` while any file on that mount is open for writing, as on Linux.
- **P2.** A remount to read-write that the core refuses fails with `EROFS`, and the mount stays `ro`. Refusals include errors recorded, an unclean ext2 volume, unknown features and a `Corrupt` replay. A fresh mount in the same situation still returns 0 and mounts `ro` (D5).
- **P3.** Refusal after mount is sticky. Once a mount asked for read-write starts refusing writes (journal abort, an ext2 error with `s_errors` remount-ro, a failed close):
  - `remount,rw` gives `EROFS` and writes nothing;
  - `remount,ro` gives 0 and writes nothing;
  - only `umount` followed by `mount` brings it back, and that replays the journal.

  Linux's ext4 refuses `remount,rw` after an abort in the same way.
- **P4.** Read-only properties (`initramfs`, `procfs`): `remount,ro` gives 0 and changes nothing; `remount,rw` gives `EROFS`. `devfs` gives `EINVAL` for both. tmpfs (`tmp`, `etc`) supports both directions.
- **P5.** A remount to read-write that would replay a journal fails with `EBUSY` while any file on the mount is open.
- **P6.** In the `mount` program, `-o remount` must come with `ro` or `rw` (or `-r`). `remount` alone prints the usage line.
- **P7.** "A remount to read-write replays nothing a read-only one could not" means: a read-write remount replays a journal exactly when a fresh read-write mount would. Our read-only remount closes the journal, so the root never replays on its way back.
- **P8.** ext2 without a journal keeps showing `rw` after an I/O error, and each failing change gives `EIO` (Linux's `errors=continue` default). Only `Corrupt` with `s_errors` remount-ro makes it refuse writes.
- **P9.** `/proc/mounts` showing `ro` after an I/O error is checked in host tests only. There is no QEMU fault injection.

## 0. What exists and what is missing

- **Fresh mounts already have the right rules.** `Driver::PrepareMount` → `OpenForMount` (`filesystem.cpp`, `core_driver.cpp`) reopens the core. For read-write it unmounts the core and mounts it writable (replay, `WriteRefusal`, `CheckOrphans`, `StartJournal`, `MarkMounted`, `ProcessOrphans`), falling back to read-only. A read-write remount reuses this path.
- **No call makes a running mount read-only in place.** Doing it as `type->Unmount` + `type->Mount(ro)`, as `CoreDriver::Detach` does, has two problems:
  - a reopen that fails after a clean close leaves a mount in the table with no filesystem behind it;
  - after an abort, the reopen drops the committed-but-not-checkpointed view.
- **The core already knows when it refuses writes.** `AbortJournal` (`transaction.cpp`), `NoteError` (`write.cpp`) and `CloseJournal` set `Ext2Filesystem::read_only`, so `GetCapabilities().writable` becomes false.
- **The VFS doesn't see that refusal.** It shows the cached `Driver::mounted_read_only`, which only `PrepareMount` sets. This is the D3 limit.
- **The ABI has no remount.** `User::MountRequest.flags` takes only `MountReadOnly`, `sys/mount.h` only `MS_RDONLY`, and the `mount` program only `-r`, `-o ro` and `-o rw`.

## 1. Files, types, signatures

### 1.1 Core: `src/fs/core/include/fs/filesystem.h`, `filesystem.cpp`

```cpp
// In class Filesystem. Makes everything durable, leaves the medium as an unmounted volume would be,
// and refuses writes from then on; reads go on. On an instance that writes nothing (mounted
// read-only, fallen back, aborted) it writes nothing and succeeds. On failure the filesystem is as
// Sync or the journal's close left it. Default: Error::Unsupported.
virtual Status MakeReadOnly();
```

**ext** (declared in `ext2_filesystem.h`, defined in `ext2.cpp` beside `ExtFilesystemType::Unmount`):

1. If `!writable_mount`: set `read_only = true` and return `{}`.
2. `Sync()`. On failure, return its error.
3. With a journal: `CloseJournal()`. It commits, checkpoints, clears `needs_recovery` and flushes. It already sets `writable_mount = false` and `read_only = true`, and calls `DestroyJournal()`.
4. Without a journal: `Sync()` has already written the groups, flushed, set `StateClean` and flushed again (I12 of s5). Set `writable_mount = false` and `read_only = true`.

An aborted journal has `journal->aborted` set, so `Sync` and `CloseJournal` return `{}`. `MakeReadOnly` then succeeds and writes nothing, and `needs_recovery` stays set on disk.

**FAT16** (`fat16.cpp`): `Sync()` (a device flush), then `read_only = true`.

`ExtFilesystemType::Unmount` and `Fat16FilesystemType::Unmount` work unchanged after `MakeReadOnly`: `Sync` returns at once, and `CloseJournal` sees a null journal.

### 1.2 `src/kernel/filesystem/filesystem.{h,cpp}` (class `Driver`)

```cpp
// Changes a mounted driver's mode as a fresh mount of that mode would set it. Callers (VFS::Remount)
// handle read-only properties and devices first. false: LastError says why; SyscallErrorReadOnly
// when read-write was asked of a medium that refuses writes, which leaves it mounted read-only.
bool Remount(MountMode mode);
// After any call that may have made the medium refuse writes: the mount is read-only from then on.
void RefreshMode();                       // if (RefusesWrites()) mounted_read_only = true;
// A read-write Remount would replay a journal, changing what open files read.
virtual bool RemountReplays();            // default: false
protected:
// Reopens or switches the medium for a remount to mode and sets *writable. Default: *writable = true.
virtual bool ReopenForRemount(MountMode mode, bool* writable);
// The medium was asked to take writes and no longer does. Default: false.
virtual bool RefusesWrites() const;
```

`Driver::Remount`:

```cpp
bool writable = false;
if (!ReopenForRemount(mode, &writable)) { RefreshMode(); return false; }
mounted_read_only = mode == MountMode::ReadOnly || !writable;
return mode == MountMode::ReadOnly || writable;
```

### 1.3 `core_driver.{h,cpp}`

```cpp
bool RemountReplays() override;
protected:
bool ReopenForRemount(MountMode mode, bool* writable) override;
bool RefusesWrites() const override;  // filesystem != nullptr && !core_read_only &&
                                      // !filesystem->GetCapabilities().writable
```

**`ReopenForRemount(mode, writable)`:**

1. If `filesystem == nullptr`: `Fail(Io)`.
2. Let `refusing = RefusesWrites()`.
3. **ReadOnly:**
   - If `core_read_only || refusing`: set `*writable = false` and return true. Nothing is written (P3).
   - Otherwise call `filesystem->MakeReadOnly()`. On failure, `Fail(error)`. The core may now refuse writes, which `RefreshMode` shows.
   - On success: `core_read_only = true`, `*writable = false`, return true.
4. **ReadWrite:**
   - If `refusing`: `last_error = SyscallErrorReadOnly`, `*writable = false`, return true (P3).
   - If `!core_read_only`: `*writable = true`, return true.
   - Otherwise `if (!OpenForMount(MountMode::ReadWrite, writable)) return false;`, then set `last_error = SyscallErrorReadOnly` if `!*writable`, and return true.

**`RemountReplays()`:** true when `core_read_only && filesystem != nullptr` and `FeatherDisk::Ext::DescribeFeatures(volume)` succeeds with incompatible bit `0x4` (`needs_recovery`, a named constant). FAT16 gives `Unsupported`, which counts as false.

`Detach`, `SyncsInBackground` and `OpenForMount` do not change. After a read-only remount `core_read_only` is true, so the writeback task skips the mount and `Detach` writes nothing.

### 1.4 `mount_table.h`, `vfs.{h,cpp}`

```cpp
enum class MountResult : uint8_t { ..., ReadOnly };   // read-write asked of what refuses writes

struct OpenFiles { bool any; bool writer; };
// NotFound: no mount at point. Invalid: devfs. ReadOnly: P2/P3/P4. Busy: being unmounted, a writer
// open (to read-only), or any file open when the remount would replay (P5). Failed: the medium could
// not be made read-only; the mount stays (read-only if it now refuses writes). Changes only this
// mount, not those inside it.
MountResult Remount(const char* point, Filesystem::MountMode mode, OpenFiles open = {});
// The driver mounted exactly at point, for comparing only; null if none.
const Filesystem::Driver* MountedAt(const char* point);
```

**`Remount`, in order:**

1. Under `mount_lock`: `driver = mounts.AcquirePoint(point)`. If that gives null, return `Busy` when `mounts.Find(point)` is non-null, else `NotFound`.
2. Outside the lock, in this order:
   - `Attributes().devices` → `Invalid`;
   - `Attributes().read_only` → `Done` for ReadOnly, `ReadOnly` for ReadWrite;
   - ReadOnly with `open.writer` → `Busy`;
   - ReadWrite with `open.any && driver->RemountReplays()` → `Busy`;
   - otherwise `driver->Remount(mode)`. On false, the result is `ReadOnly` if `LastError()` is `SyscallErrorReadOnly`, else `Failed`.
3. `Release(driver)`.

**`RefreshMode` call sites:**

- `Changed(driver, done)` calls `driver->RefreshMode()` on both success and failure. That covers Create, Write, Truncate, Remove, MakeDirectory, RemoveDirectory, Rename, SymbolicLink and Link.
- The lambdas in `SyncAll`, `SyncPeriodic` and `DetachAll` call it after their call.

### 1.5 `files.{h,cpp}`

```cpp
// EINVAL when point exists but is not a mount point, ENOENT when it does not exist.
uint64_t Remount(const char* point, Filesystem::MountMode mode);
```

Under `file_system_lock`:

1. `Resolved::Walk(point, Follow::All)`.
2. If `!VFS::IsMountPoint`, return `ExistsLocked ? EINVAL : ENOENT`, as `Unmount` does.
3. `const Driver* d = VFS::MountedAt(point)`. Scan `disk_files` for entries with `key.filesystem == d`: `any` means any entry, `writer` means any entry with `writer` set.
4. Return `MountError(VFS::Remount(point, mode, open))`, with `NotFound` mapped to `EINVAL`.

`MountError` gains `ReadOnly` → `SyscallErrorReadOnly`.

### 1.6 ABI and syscall: `src/user/syscall_abi.h`, `src/kernel/process.cpp`

```cpp
constexpr uint64_t MountReadOnly = 1U << 0;   // Linux's MS_RDONLY
constexpr uint64_t MountRemount = 1U << 5;    // Linux's MS_REMOUNT (32): only the target and
                                              // MountReadOnly count; source and type are ignored
```

`MountSyscall`:

- rejects any bit outside `MountReadOnly | MountRemount` with `EINVAL`;
- with `MountRemount`, copies only the target (source and type may be null) and returns `Files::Remount(target_text->resolved, mode)`.

The syscall number stays 64.

### 1.7 libc: `src/libc/include/sys/mount.h`, `src/libc/mount.cpp`

- `#define MS_REMOUNT 32`.
- `mount` accepts flags within `MS_RDONLY | MS_REMOUNT`, and `data` must still be null.
- With `MS_REMOUNT`, `source` and `filesystemtype` may be null. Without it, a null argument is `EINVAL`.
- Header comment: a remount may give `EINVAL` (not a mount point, `/dev`), `EBUSY` (P1/P5) or `EROFS` (P2–P4).

### 1.8 Program: `src/user/mount.cpp`

- Usage:
  - `mount [-r] [-o <options>] [-t <type> <source> <target>]`
  - `mount -o remount,ro|remount,rw <target>`
- `-o` takes a comma list of `ro`, `rw` and `remount` in any order. Of `ro` and `rw`, the last one wins.
- With `remount`, there is exactly one operand and no `-t`. The call is `mount(nullptr, target, nullptr, MS_REMOUNT | ro, nullptr)`.
- Errors print `mount: <target>: <strerror>`. Update the help text.

## 2. Remount semantics

| From → to | ext3/ext4 | ext2 | FAT16 | tmpfs | initramfs/procfs | devfs |
|---|---|---|---|---|---|---|
| rw → ro | commit, checkpoint, clear `needs_recovery`; instance kept | `Sync` marks clean; instance kept | flush | mode only | 0, no change | `EINVAL` |
| ro → rw | core reopened writable: replay if needed, orphans, `MarkMounted` | reopened writable: unclean or errors → `EROFS` | reopened | mode only | `EROFS` | `EINVAL` |
| same mode | 0, nothing written | 0 | 0 | 0 | 0 / `EROFS` | `EINVAL` |

**Open handles.** A file cannot be removed while it is open (`AddUse`), so there are no open-but-unlinked orphans to keep a mount busy. Handles and working directories survive a remount that does not replay: a core `Node` holds no per-instance state, and FAT16 node IDs come from on-disk positions.

**The writeback task.** It takes `file_system_lock`, so each of its passes runs wholly before or wholly after a remount. After a read-only remount `SyncsInBackground()` is false.

**Locking.** `Files::Remount` holds `file_system_lock`. `VFS::Remount` takes `mount_lock` only around `AcquirePoint` and `Release`. The order stays `file_system_lock` → `mount_lock` → the core's `Host::Lock`.

**The root.** A remount changes only the root's own mode. `/system`, `/dev`, `/proc` and `/tmp` keep theirs, as does `/etc` when it is the tmpfs copy.

- After `UseRootEtc`, `/etc` is the root's own directory. It stays so after `remount,ro`, now read-only.
- The shell's working directory does not make `/` busy.
- Shutdown (`DetachAll`) writes nothing to a root remounted `ro`.

**State.** `mounted_read_only` is set by `PrepareMount`, set by `Remount`, and raised by `RefreshMode`. It changes only under `file_system_lock`, or on the boot thread before `Writeback::Start`.

## 3. Read-write remount

The read-write remount runs `OpenForMount(ReadWrite)`, which is the fresh-mount code:

- It replays a journal that needs it, under P5.
- It processes orphans.
- It runs `MarkMounted`.
- It keeps the core's fallbacks and their log line `ext2: mounted read-only: <reason>`, and the remount then gives `EROFS` (P2).

A fallback writes nothing, except a replay that succeeded before the refusal.

## 4. Read-only remount: clean while mounted

- **ext3/ext4:** `Sync` (commit), then `CloseJournal` (commit of the rest, checkpoint, log emptied, `needs_recovery` cleared, flush). The volume is then exactly as after `umount`.
- **ext2:** `Sync` marks the volume clean and flushes.
- **FAT16:** a flush.

The instance keeps its block cache and goes on serving reads.

## 5. `/proc/mounts` after an I/O error or a journal abort

The state lives in `Ext2Filesystem::read_only`. Three paths set it:

- `AbortJournal`, after a commit, checkpoint, flush or superblock write fails, or a group descriptor read-back fails;
- `NoteError`, for `Corrupt` with `s_errors` not continue;
- a failed `CloseJournal`, through `AbortJournal`.

`CoreDriver::RefusesWrites()` is true when the core was asked for writes and refuses them. `Driver::RefreshMode()` then raises `mounted_read_only` after every change, every sync pass and every remount, so the syscall that hit the error already leaves `/proc/mounts` saying `ro`. ext2 without a journal keeps `rw` after an I/O error (P8).

## 6. Invariants

- **I1. Fresh-mount rules.** A successful read-write remount leaves the core in the state a fresh `mount` of that mode would: replay, refusals, orphans, `MarkMounted`.
- **I2. Clean after a read-only remount.** When a read-only remount of a healthy writable mount returns 0:
  - ext3/ext4: the log is empty on disk and `needs_recovery` is clear;
  - ext2: the volume is marked clean;
  - all: the device has been flushed.

  `e2fsck -fn` on a raw copy exits 0.
- **I3. No writes while read-only.** From a successful read-only remount until the next successful read-write remount or mount, nothing writes to the partition: not the writeback task, `sync`, `DetachAll`/`Quiesce`, a refused `remount,rw` or a repeated `remount,ro`. A flush is allowed.
- **I4. `/proc/mounts` tells the truth.** A mount shows `rw` exactly when the VFS would let a change reach a driver that takes writes, and `ro` from the end of the call in which the core started refusing writes.
- **I5. Refusal is sticky (P3).** After a mount starts refusing writes, `remount,rw` gives `EROFS` and `remount,ro` gives 0, and neither writes anything.
- **I6. Failures change nothing.** `EINVAL`, `ENOENT`, `EBUSY` and `EROFS` write nothing and leave the mode as it was. `EIO` from a read-only remount leaves the mount in the table, refusing writes and shown `ro` if the journal aborted.
- **I7. Busy rules.** A read-only remount is refused while a file on the mount is open for writing. A replaying read-write remount is refused while any file on the mount is open.
- **I8. Locking.** Every remount runs under `file_system_lock`, and `mount_lock` is never held across a driver call.
- **I9. Handles survive.** Open read handles and working directories still read the same files after a remount that does not replay.
- **I10. One mount only.** A remount changes exactly one mount. On the root, the root's own `/etc` follows the root's mode.

## 7. Write order and what a stop leaves

### Read-only remount, ext3/ext4

| Point | On disk | `e2fsck -fy` then `-fn` | Our next writable mount |
|---|---|---|---|
| Inside the commit (commit block not flushed) | torn tail | the change is dropped | same |
| Commit flushed | log holds T, `needs_recovery` set | replays T; `-fn` 0 | replays T |
| Inside the checkpoint | log still valid | replays again | same |
| Log emptied, superblock not yet written | empty log, flag set | clears the flag | an empty replay clears it |
| Superblock written and flushed | clean, flag clear | `-fn` 0 directly | nothing to do |

### Read-only remount, ext2

- A stop before the final flush leaves the volume not clean, so it mounts read-only until `e2fsck -fy`.
- After the final flush it is clean.

### Read-write remount

- A replay follows `recovery.cpp`'s order: the log stays valid until its home blocks are flushed.
- After `MarkMounted`, ext3/ext4 have the flag set over an empty log, and ext2 has `StateClean` cleared until the next 5 s pass.

## 8. Edge cases and errno

| Case | Result |
|---|---|
| `remount,ro` / `remount,rw` of a healthy mount | 0; `/proc/mounts` `ro` / `rw` |
| The same mode again | 0, no write (only a flush) |
| `remount,ro` with a file on the mount open for writing | `EBUSY`, nothing written |
| `remount,ro` with read-only files open or working directories inside | 0 |
| `remount,rw` that would replay, with any file open on the mount | `EBUSY` |
| `remount,rw` refused by the core | `EROFS`, core log line, stays `ro` |
| `remount,rw` after an abort or an ext2 remount-ro error | `EROFS`, nothing written |
| `remount,ro` after an abort | 0, nothing written; the flag is still set |
| I/O error during a `remount,ro` close | `EIO`; journal aborted; mount stays, shown `ro`; a second `remount,ro` gives 0 |
| An existing path that is not a mount point | `EINVAL` |
| A path that does not exist | `ENOENT` |
| A symbolic link to a mount point | followed |
| `/system`, `/proc`: `ro` / `rw` | 0 / `EROFS` |
| `/dev` | `EINVAL` |
| A mount being unmounted (kernel tests only) | `EBUSY` |
| Unknown flags, or `data` not null | `EINVAL` |
| `MS_REMOUNT` with null `source`/`filesystemtype` | allowed |
| A write through a handle opened before a refusal | `EROFS` |
| `sync` on a read-only mount | 0 |
| Shutdown with the root remounted `ro` | writes nothing |

## 10. Acceptance tests

### Core host tests (`src/fs/core/tests/ext_remount_tests.cpp`)

The variants are `ext2`, `ext3`, `ext4` and `ext4-4k`. The oracles are `CheckClean` (`e2fsck -fn`), `RunDebugfs`, and the raw superblock (incompat bit `0x4` at +0x60, `s_state` at +0x3A).

- **T1. MakeReadOnly leaves a written volume clean while it stays mounted.**
  1. Mount rw. Write `/a.txt` and a 3-block file without a `Sync`.
  2. Call `MakeReadOnly`.
  3. Check: `writable` is false; `needs_recovery` is clear (ext3/4) or `s_state & 1` is set (ext2); `CheckClean` passes on a byte copy; `debugfs cat /a.txt` matches.
  4. Read every file back through the same instance.
  5. A `Write` gives `ReadOnly`.
  6. `write_count` is unchanged by reads, `Sync`, a second `MakeReadOnly` and `Unmount`.
- **T2. rw → ro → rw replays nothing and keeps both changes.**
  1. After T1, `Unmount` and `Mount` rw. There is no `ext2: journal recovered` line, and `Activity()->transactions == 0`.
  2. Write `/b.txt`, then `MakeReadOnly`.
  3. `CheckClean` passes, and debugfs shows `/a.txt` and `/b.txt`.
- **T3. A stop anywhere inside MakeReadOnly leaves a volume that recovers** (ext3 and ext4).
  1. Write, then `TrackUnflushed`, and count the writes `MakeReadOnly` makes.
  2. For each prefix `n`, take `FailWritesAfter(n)` / `CopyKeeping`.
  3. On each copy: our rw mount replays, `/a.txt` is absent or whole, `Unmount`, `CheckClean` passes.
  4. The last prefix has the flag clear and passes `CheckClean` without a mount.
- **T4. An aborted journal refuses writes, and MakeReadOnly then writes nothing.**
  1. Mount ext4 rw and write. `FailWritesAfter(0)`; `Sync` fails.
  2. `writable` is false.
  3. Restore writes. `MakeReadOnly` returns `{}`, `write_count` is unchanged, and the flag is still set.
  4. A copy mounted rw replays the earlier commits.
- **T5. A read-only instance's MakeReadOnly writes nothing** (all variants, plus an unclean ext2 that fell back).
- **T6. FAT16** (`fat_tests.cpp`).
  1. Mount rw, write, `MakeReadOnly`: `flush_count + 1`; writes give `ReadOnly`; reads work.
  2. `Unmount` + `Mount` rw, then write again.
  3. `mtype` reads both files.

### Kernel host tests (`filesystem_tests.cpp`, `virtual_files_tests.cpp`; fake disk with `writes_fail`)

- **T7. Remount switches an ext4 mount between read-only and read-write.**
  1. Write, then `Files::Remount("/mnt", ReadOnly)` gives 0.
  2. `/proc/mounts` shows `vda4 /mnt ext4 ro 0 0`, and the flag is clear in the disk bytes.
  3. `Create` gives `EROFS`.
  4. Take a snapshot. Three `Files::SyncPeriodic()`, then `Files::SyncAll()` and `VFS::DetachAll()`: the bytes are unchanged.
  5. `Remount(ReadWrite)` gives 0 and `rw`. Write, `Unmount`, and read the contents back.
- **T8. The root remounts read-only and back, and `/etc` follows it** (an ext2 root, and an ext4 root if the fixtures allow).
  1. `Remount("/", RO)`: `s_state` is 1; `/etc` (after `UseRootEtc`) and `/` give `EROFS`; `/tmp` still takes writes.
  2. `Remount("/", RW)`: a write works.
- **T9. Remount refuses while a file is open for writing.**
  1. With `/mnt/f` open for writing, `Remount(RO)` gives `EBUSY` and the bytes are unchanged.
  2. Close it and open it read-only: `Remount(RO)` gives 0, and the handle still reads.
- **T10. Remount errno.**
  - `/home` gives `EINVAL`; `/no/such` gives `ENOENT`.
  - `/system`: ro gives 0, rw gives `EROFS`. `/proc` rw gives `EROFS`. `/dev` gives `EINVAL`.
  - `/tmp` ro: a write gives `EROFS`; after rw, the files are kept.
  - The same mode twice gives 0 with no byte changed.
- **T11. A remount to read-write that the core refuses gives `EROFS` and writes nothing.**
  1. ext4 with `s_state |= 2` mounted rw falls back to `ro`. `Remount(RW)` gives `EROFS`, it stays `ro`, and the bytes are unchanged.
  2. The same for an unclean ext2.
  3. A clean ext4 mounted `-r`, then `Remount(RW)`, gives `rw`.
- **T12. A journal abort shows `ro` in `/proc/mounts` and is sticky.**
  1. Mount ext4 rw, write, and set `writes_fail`. A `Write` gives `EIO`.
  2. `/proc/mounts` shows `ro`, `MayChange` gives `EROFS`, and `Files::SyncPeriodic()` changes no `flush_count`.
  3. `Remount(RW)` gives `EROFS`; `Remount(RO)` gives 0 with no byte changed.
  4. Clear `writes_fail`. `Unmount` and `Mount` rw: it replays and shows `rw`.
  5. Repeat with the abort coming from `Files::SyncPeriodic()`.
- **T13. A failed close keeps the mount and shows it read-only.**

## 11. Risks for the implementer

- **Reads after `CloseJournal` are new.** Check that an instance with `journal == nullptr` and `writable_mount == false` reads through the cache correctly. T1's full read-back covers this.
- **A change can succeed while its commit aborts.** `RefreshMode` runs on success too, so `/proc/mounts` still catches it.
- **`mounts.py`'s regex** matches `vda1 / ext4 rw 0 0` anywhere in the output (T19).
- **`VerifyJournalled` boot 2** replays the root on a copy today. It must now insist on a clean root.
- **No writer may be open on `/`** when T19 runs. Keep the part before `jobs`.
