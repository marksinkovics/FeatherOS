# M32: graphics for user programs and a falling-block puzzle (design)

**Scope.** User programs today only reach the screen through a terminal. The kernel owns the framebuffer (`src/kernel/framebuffer/framebuffer.{h,cpp}`: one static 1024x768 back buffer, `packColor` for the hardware's pixel format, `draw(y, height)`), four virtual consoles draw into it through `Term` (`src/kernel/console.cpp`, `Show`, `SetShown`), and keys become VT100 bytes in `Input::SubmitKey` (`src/kernel/input/input.cpp`) before reaching the shown console's terminal; key releases are dropped there. QEMU gives both targets a framebuffer (`ramfb` on AArch64) and a keyboard (PS/2 on x86-64, `virtio-keyboard-device` on AArch64).

This milestone:

1. Lets a program on a virtual console take over that console's screen and present pixels it drew in its own memory (`/dev/fb0`).
2. Gives that program raw key presses, repeats and releases on the same descriptor.
3. Adds a C++ graphics library with a Swift interface to it.
4. Adds `featherfall`, a falling-block puzzle of our own written in Embedded Swift.

**Done when:**

1. `./build.sh unit-test`;
2. `bash tools/quality.sh check`;
3. `tools/check.sh --arch both --modes "GRAPHICS SHELL"`;
4. `tools/check.sh --arch both --matrix`.

## Decisions (confirmed by the user, 2026-11-20)

- **D1. Copy-present, no mapping.** A program draws into its own heap buffer and asks the kernel to copy a rectangle of it to the screen. There is no `mmap`, and none is added: the kernel keeps sole access to the hardware framebuffer, so console switching and panics need no help from the program.
- **D2. A C++ library, a Swift game.** The graphics library is C++ (`featheros_user_support`, host-tested). The game is Embedded Swift and imports the library through C++ interoperability (`FEATHEROS_SWIFT_CXX_PROGRAMS`). A small C++ program, `fbdemo`, tests the kernel interface on its own, so the API is checked even in a build without `deps/swift`.
- **D3. Its own milestone and branch.** M32 is worked on `feat/graphics`, cut by the user, separate from M30 on `feat/disk`.

## Detailed decisions (left to Claude by the user, 2026-11-20)

### The device

- **D4. `/dev/fb0`.** A new `Devices::Device::Framebuffer`, listed only when the kernel has a framebuffer. Opening it takes nothing over; `FB_GET_INFO` works at any time, while reads, `FB_PRESENT` and `FB_RELEASE` before an acquire fail with `EINVAL` (amended in `M32-P1.md`).
- **D5. A new syscall 73 `DeviceControl(descriptor, request, argument)`** for requests to non-terminal devices. libc's `ioctl` sends the `FB_*` requests there and the terminal ones to `TerminalControl` (63) as now. Requests and structures are in the new header `<featheros/framebuffer.h>`, documented in `docs/posix.md` under the FeatherOS extensions, with `featheros_ioctl` for Swift as before.
- **D6. Requests.**
  - `FB_GET_INFO` → `{width, height, console}`: the screen size and the number of the caller's console. The format is always XRGB8888 (`0x00RRGGBB`) for the program, whatever the hardware's is.
  - `FB_ACQUIRE`: the caller's controlling terminal must be a virtual console (`ENOTTY` for a pseudo-terminal or none); one owner per console (`EBUSY`); a background process gets `SIGTTOU` as `tcsetattr` does.
  - `FB_PRESENT` `{const uint32_t* pixels, uint32_t stride, x, y, width, height}`: copies the rectangle, clipped to the screen, from user memory (`EFAULT` on a bad page) into the back buffer, converting the format (a row copy when the hardware is XRGB8888), then `draw(y, height)`. Nothing is drawn while the console is not shown, and the call still succeeds.
  - `FB_RELEASE`. The last close of the descriptor, `exec` and process exit release as well.

### Consoles

- **D7. Graphics mode per console.** While a console is acquired, its `Term` keeps taking terminal output into its cell grid but never draws it, and its status bar is not drawn: the program gets all 1024x768 pixels. On release the console redraws (`Term::Redraw`) with its status bar. Kernel messages still go to serial; a panic draws over the screen as now.
- **D8. Switching away keeps the owner.** Alt+F1 to Alt+F4 still switch consoles. Switching away from an acquired console queues a release event for every held key, then a `Hidden` event. Switching back queues `Shown`, and the program must present the whole screen again, since the kernel keeps no copy (four 3 MiB copies would be needed otherwise).

### Input

- **D9. Events are read from the same descriptor.** While a console is acquired and shown, the keyboard sends key events to the owner's queue instead of VT100 bytes to the terminal. `read` returns whole 8-byte events: `{uint16_t code; uint8_t kind; uint8_t modifiers; uint32_t time_ms}`. `kind` is press, repeat, release, `Shown` or `Hidden`; `code` uses Linux's input numbers, as `Input::KeyCode` already does, exported as `KEY_*`; `time_ms` is `CLOCK_MONOTONIC`. A read blocks unless the descriptor has `O_NONBLOCK` (then `EAGAIN`), and `poll` reports `POLLIN`. The queue holds 64 events; when it is full, new ones are dropped and counted (`FB_GET_INFO` reports the count).
- **D10. A repeat is not a press.** `Keyboard` already sees held keys repeat; `Input` tracks which keys are held and marks a second press as a repeat, the same on PS/2 and virtio-input.
- **D11. Ctrl+C still interrupts.** In graphics mode, Ctrl+C sends `SIGINT` to the console's foreground group as well as being queued, so a stuck program can be stopped; it then exits and releases the screen. Ctrl+Z is only queued, since a stopped owner would leave a screen nobody draws.
- **D12. Timing stays as it is.** `CLOCK_MONOTONIC` and `nanosleep` count whole milliseconds on a 10 ms tick, so a game loop runs at up to 100 updates and at most 50 presented frames per second, pacing itself with `poll` timeouts. A faster tick is not part of this milestone.

### The library

- **D13. `src/user/graphics/`**, in `featheros_user_support`:
  - `Graphics::Surface`: an owned XRGB8888 buffer with `Fill`, `FillRectangle`, `DrawRectangle`, `Blit` (with a transparent colour) and `DrawText`, which uses the kernel's 8x16 font (`src/kernel/framebuffer/font.c`, compiled into the library too), with an integer scale.
  - `Graphics::Display`: opens and acquires `/dev/fb0`, collects dirty rectangles and presents them merged (whole screen past a threshold), reads events with a timeout, and releases in its destructor.
  - The interface Swift sees takes plain pointers and sizes and returns status codes, with no templates, so it imports cleanly.
  - Host tests in `tests/unit/user/graphics_tests.cpp`: clipping, blits, text, dirty-rectangle merging and event decoding (with the kernel calls stubbed).

### The game

- **D14. `featherfall`, an original falling-block puzzle.** It has its own name, palette, layout and scoring, and borrows only the genre's mechanics:
  - a 10x20 well (plus 2 hidden rows), seven 4-cell pieces from a shuffled bag of seven, a preview of the next three, hold (once per piece), a ghost piece;
  - rotation both ways with our own wall kicks (try in place, one left, one right, one up);
  - gravity speeding up every 10 lines, a 500 ms lock delay reset by at most 15 moves, soft and hard drops;
  - scoring of our own: 100/300/500/800 times the level for 1 to 4 lines, 1 per soft-dropped row, 2 per hard-dropped row;
  - side panels with score, level, lines, the next pieces and the held piece, plus pause (P), game over and quit (Esc).
- **D15. Controls** come from presses and releases, not the kernel's repeats: Left/Right move with the game's own auto-repeat (170 ms delay, 50 ms rate), Down soft-drops, Space hard-drops, Up or X rotates clockwise, Z anticlockwise, C or Shift holds.
- **D16. High scores** (top 10, three letters each) live in `$HOME/.featherfall`, or `/tmp/.featherfall` without `HOME`; a file that does not parse is ignored and replaced.
- **D17. Determinism for tests.** All game logic is a pure state machine: `step(state, inputs, 10 ms)` with a seeded random generator, kept apart from drawing and the clock. `featherfall --selftest` runs the rule checks (rotation and kicks, line clears, bag order, scoring, lock delay) in QEMU, since Embedded Swift has no host test target here. `featherfall --demo --seed N` plays a fixed input script without a display and prints the final score, lines and a hash of the well; the expected values are the same on both architectures.

## Steps

1. **The device and present.** `Devices::Device::Framebuffer`, syscall 73 and libc `ioctl` routing, `FB_GET_INFO`/`FB_ACQUIRE`/`FB_PRESENT`/`FB_RELEASE`, graphics mode in `console.cpp` and `Term`, release on close, `exec` and exit, the format conversion on `Framebuffer` (host-tested for XRGB, BGRX and 16-bit layouts), `<featheros/framebuffer.h>`. `fbdemo` draws a test pattern and exits on a timer; `fbtest` checks the errors (`ENOTTY` from a pseudo-terminal, `EBUSY`, `EFAULT`, clipping). New smoke mode `GRAPHICS_TEST=ON` (`tools/smoke/cases/graphics.py`): runs `fbdemo`, takes a QMP `screendump`, checks the pattern's pixels, and checks the text console is back with its status bar after exit, on both architectures.
2. **Key events.** The per-owner queue, `read`/`O_NONBLOCK`/`poll`, repeats (D10), `Shown`/`Hidden` and the releases on switch (D8), Ctrl+C (D11). `fbdemo --keys` prints each event on its terminal, which the harness reads from serial; the harness sends separate key-down and key-up events with QMP `input-send-event`, holds a key long enough to repeat, and switches to Alt+F2 and back.
3. **The library.** `src/user/graphics/` (D13) with its host tests, `fbdemo` rewritten on it, and the Swift module over it (`swift_cxx/module.modulemap`) with a tiny Swift check program.
4. **The game's rules.** The Swift state machine (D14, D17), `--selftest` and `--demo`, run from the `GRAPHICS` smoke mode.
5. **The game.** Drawing, controls (D15), pause, game over, high scores (D16), and a smoke part that plays a few seconds with QMP keys and checks a `screendump` shows the well; `docs/development.md` (mode, syscall 73), `docs/posix.md` (the header), matrix cases on both architectures, `add-program` checklist for both programs.
