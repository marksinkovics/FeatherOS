# M22 Part 6 step 5: ext3 and ext4 read-write in FeatherOS, with a periodic sync (design)

**Scope.** Kernel and harness only. `src/fs/core/` does not change; §2.3 explains why ext2 needs no core change. After this step:
- `mount -t ext3 vda3` and `mount -t ext4 vda4` are read-write when asked, and the core decides whether a volume really is.
- A kernel task syncs every writable ext2, ext3 and ext4 mount every 5 s.
- Unmount and shutdown close ext3/ext4 journals, so the volume is clean afterwards.
- `STORAGE`, the shell case and the power cases check the partitions with `e2fsck`/`debugfs`.
- ext3/ext4 are still never the root (that is Part 6b).

**Done when:** `./build.sh unit-test`, `bash tools/quality.sh check`, `tools/check.sh --arch both --modes "STORAGE SHELL"`, then `tools/check.sh --arch both --matrix`.

## Decisions (user, 2026-11-18)

- **D1.** The periodic 5 s sync covers ext2 as well as ext3/ext4, using the core's existing `Sync` (§2.3). FAT16 and the virtual filesystems get no periodic sync: FAT16 writes go straight through, its `Sync` is only a device flush, and the in-memory filesystems have no disk.
- **D2.** `Detach` closes the core mount (commit, checkpoint, clear `needs_recovery`, reopen read-only) only for ext3/ext4. For ext2 and FAT16, `Detach` is `Sync`, as unmounting is today.
- **D3.** After a journal I/O error, `/proc/mounts` still says `rw` and changes fail with `EROFS`. This is a known hard limit.
- **D4.** The interval is fixed at 5 s, with no mount option.
- **D5.** A writable mount whose replay finds damage (`Corrupt`) falls back to read-only, with the core's "run e2fsck" line, and the mount returns 0. This is a known hard limit.
- **D6.** `STORAGE` boot 1 deliberately ends with ext3/ext4 journals that need recovery. The harness repairs only copies, so boot 2 replays them.

## 0. Why unmount has to change

- `VFS::Unmount` (`vfs.cpp:340`) calls only `driver->Sync()`, and `CoreDriver` keeps its core mount open afterwards.
- For a journalled volume, core `Sync` only commits (`ext/write.cpp:1361`). Only `ExtFilesystemType::Unmount` (`Sync` + `CloseJournal`, `ext/ext2.cpp:1084`) checkpoints the log and clears `needs_recovery`.
- `Files::Quiesce` (`files.cpp:1672`) also only calls `VFS::SyncAll()`.

Without a change, every unmount and every shutdown of ext3/ext4 would leave a full log with `needs_recovery` set. This step adds a driver hook, `Detach`, for that.

## 1. Files, types, signatures

### 1.1 `src/kernel/filesystem/filesystem.h` (class `Driver`)
```cpp

// it when it removes the mount and at shutdown. false: the mount stays (LastError says why).
virtual bool Detach();                      // default (filesystem.cpp): return Sync();
// Wants Sync every Writeback::IntervalSeconds while mounted.
virtual bool SyncsInBackground() const;     // default: false
```

### 1.2 `core_driver.{h,cpp}`
```cpp
struct CoreOptions
{
    bool periodic_sync = false;      // the writeback task syncs it while writable
    bool close_on_detach = false;    // Detach unmounts the core (closing a journal), reopens it read-only
};
constexpr CoreDriver(Properties properties, CoreOptions options = {});
bool Detach() override;
bool SyncsInBackground() const override;
private: CoreOptions options;
```

`SyncsInBackground` returns:
```cpp
options.periodic_sync && filesystem != nullptr && !core_read_only
    && filesystem->GetCapabilities().writable
```
The last term is false after a journal abort or a `remount-ro` error, so such mounts are skipped.

`Detach`:
1. If `!options.close_on_detach`, or `filesystem == nullptr`, or `core_read_only`, return `Sync()`.
2. `type->Unmount(*filesystem)`. This is Sync + CloseJournal. If it fails, return `Fail(error)`; the core mount stays as it was.
3. Set `filesystem = nullptr` and `core_read_only = true`. Remount with `type->Mount(volume, {.read_only = true})`.
4. If that remount fails, set `partition_number = 0`, log `ext: <type> could not be reopened read-only`, and **still return true**: the volume is already clean. The next `OpenForMount` fails with `Io`.

`OpenForMount` is unchanged: a read-write mount reopens the core writable and falls back to read-only with the core's log line.

### 1.6 New `src/kernel/writeback.{h,cpp}` (in `src/kernel/`, beside `files.cpp`)
```cpp
namespace FeatherOS::Writeback {
constexpr uint32_t IntervalSeconds = 5;
// Starts the kernel task that syncs writable ext2, ext3 and ext4 mounts every IntervalSeconds.
// Once, after the timer runs and after every kernel test that calls the VFS without the file
// system lock.
void Start();
}
```
The task:
```cpp
uint64_t WritebackTask(void*)
{
    const uint64_t interval = IntervalSeconds * Time::TicksPerSecond();
    uint64_t next = Time::TickCount() + interval;
    bool failing = false;
    for (;;)
    {
        while (Time::TickCount() < next) Scheduler::SleepUntil(next);   // wakeups may be spurious
        next = Time::TickCount() + interval;                            // no catch-up bursts
        const bool synced = Files::SyncPeriodic() == 0;
        if (!synced && !failing) logger.Warning("Writeback: a mount did not sync");
        failing = !synced;
    }
}
```
- `logger` is a `constinit KLogger`, as in `core_host.cpp`.
- `Start` follows the console's status task: `CreateTask`, then `SetPriority(High)`, and `Panic("Could not start the writeback task")` on failure.
- Add the file to `src/kernel/CMakeLists.txt`. It is not in the host tests.

## 2. The periodic sync

### 2.1 Context and locking

**Where it runs.** A kernel task at High priority, so CPU-bound programs cannot starve it; it sleeps almost all the time. Timer callbacks are rejected: they cannot take the `Sync::Mutex`, and disk I/O cannot run from interrupt context.

**Finding the mounts.** `VFS::SyncPeriodic` walks the mount table and calls `Sync()` on each driver whose `SyncsInBackground()` is true: the ext2, ext3 and ext4 instances that are mounted, writable in the core, and not refusing writes.

**Locking.**
- The task takes `file_system_lock` like any file syscall, so it is serialised with every file operation, mount and unmount.
- Lock order: `file_system_lock` (mutex), then `mount_lock` (spinlock, never held across a driver call), then the core's `Host::Lock`s.
- A syscall that arrives during a commit waits for up to two flushes.

**Unmount** runs under the same lock. After it, the mount is gone from the table, and for ext3/ext4 the core is read-only.

**Quiesce** takes the lock forever. A pass already running finishes first; any later pass blocks forever in `Mutex::Lock`.

**Both architectures and SMP.** No arch-specific code. Both use the 100 Hz tick, and the task can run on any CPU. `QEMU_CPU_COUNT > 1` in every case.

### 2.2 ext3/ext4

- Core `Sync` commits the running transaction (two flushes). With nothing running, it writes nothing and only flushes the device.
- On an `Io` error, the core aborts the journal and logs `ext2: journal aborted, no more writes: ...`. `SyncsInBackground` then turns false.
- Later changes on that mount give `EROFS`; `/proc/mounts` still says `rw` (D3). The next writable mount replays.

### 2.3 ext2: how the background sync stays honest (no core change)

The core already keeps one rule, stated here as **I12**: `StateClean` on disk implies that the on-disk metadata is complete and consistent.
- `BeginChange` (`ext/write.cpp:215`) clears `StateClean`, writes the superblock and flushes before the first change after a mount or a `Sync`.
- `MarkMounted` clears it at a writable mount.
- `Sync` (`write.cpp:1361`) writes the dirty group descriptors and counts, flushes, sets `StateClean` and the write time, writes the superblock and flushes.

So the periodic pass is plain core `Sync`:
- An idle ext2 volume writes nothing; with `superblock_clean`, `Sync` only flushes.
- An ext2 volume changed less than about 5 s before a stop is left not clean. At the next boot it mounts read-only, as today, until `e2fsck -fy`.
- One stopped later is clean and consistent, and mounts read-write.

**How this differs from Linux.** Linux's ext2 sets `VALID_FS` only at unmount, so on Linux "clean" also means "not mounted". Here it means "consistent on disk", so `e2fsck -p` skipping such a volume is safe.

**Rejected alternative: a `Sync` variant that leaves the clean bit off.** Every stop from outside (the harness's normal end) would then leave the root read-only at the next boot, which is worse than today and gains nothing in honesty.

The errors path is unchanged: a volume with `StateErrors` refuses writes, so `SyncsInBackground` is false for it.

### 2.4 The Part 4b rule, reworded

**Old:** "an ext2 root left unsynced mounts read-only at the next boot".

**New:** "an ext2 volume stopped before the writeback pass that follows its last change (within about 5 s) is left not clean and mounts read-only until `e2fsck -fy`. `sync`, unmount and shutdown make it clean at once."

**Harness checks that relied on the old rule:**

## 3. What changes for ext3/ext4 mounts

- Without `-r`, they come up `rw` in `/proc/mounts` when the core takes writes. With `-r`, `ro`.
- A core refusal still gives `ro`, with the core's line `ext2: mounted read-only: <reason>`: unsupported journal features, errors recorded, a malformed orphan list, a `Corrupt` replay (D5).
- Each writable mount increments `s_mnt_count` and sets `needs_recovery` (`MarkMounted`). `Detach` (unmount or shutdown) clears it.
- `sync` (syscall 71) commits but does not checkpoint, as on Linux. After `sync` and a power cut, the host needs `e2fsck -fy`.

## 4. Recovery at boot

- At boot, `MountExt3`/`MountExt4` mount the core read-only. A volume with `needs_recovery` is not replayed: it reads as its home blocks are on disk.
- A `-r` VFS mount also never replays and never writes.
- Only a writable VFS mount replays:
  1. `OpenForMount` unmounts the read-only core and mounts it writable.
  2. The core replays (`RecoverJournal`; log line `ext2: journal recovered; transactions replayed: 0x...`).
  3. It processes orphans and then mounts writable.
- A `Corrupt` replay falls back to read-only and writes nothing (D5).

## 5. Invariants

- **I1. All access under the lock.** After `Writeback::Start`, every call into a core ext2/ext3/ext4 or FAT16 filesystem is made under `file_system_lock`: file syscalls, `Files::SyncPeriodic`, `Mount`/`Unmount` and `Quiesce`. Before `Start`, only the boot thread calls the VFS (`kernel_runtime.cpp`, `kernel_test.cpp`). Procfs's `DescribeMount` reads only the cached `mounted_read_only` under `mount_lock`.
- **I2. Lock order.** `file_system_lock` → `mount_lock` → core `Host::Lock`. `mount_lock` is never held across a driver call.
- **I3. 5 s bound.** While the system runs, within `IntervalSeconds` + the longest single file operation + one sync of a change:
  - on a writable ext3/ext4 mount, the change is in a committed transaction on disk;
  - on a writable ext2 mount, the volume is consistent and marked clean on disk.
- **I4. Clean after unmount, no write after unmount (ext3/ext4).** When `VFS::Unmount` returns `Done`: the log is empty on disk, `needs_recovery` is clear, the device is flushed, the core mount is read-only. Nothing writes to the partition until the next writable `VFS::Mount`.
- **I4b. ext2 after unmount.** When `VFS::Unmount` returns `Done` for ext2, the volume is synced and clean, and the task no longer syncs it.
- **I5. Shutdown.** After `Files::Quiesce`, every mount is detached: ext3/ext4 closed as in I4 (or with an aborted journal); ext2 synced and clean. No task writes to any partition again.
- **I6. Failed unmount.** A failed `Detach` leaves the mount in the table and the core mount as it was (`EIO`). After a journal abort, `Detach` succeeds and writes nothing; the volume keeps `needs_recovery`.
- **I7. Read-only means no writes.** A read-only mount (asked for, or a fallback) never writes, is never synced by the task, and never replays. Only a writable mount replays.
- **I8. Idle passes write nothing.** A periodic pass on a mount with nothing to commit or write writes no block. It may flush the device.
- **I9. `/proc/mounts` at mount time.** It says `rw` for ext3/ext4 exactly when the core mount was writable at mount time. Every core refusal gives `ro` and a log line.
- **I10. What the task syncs.** Only drivers with `periodic_sync` (ext2, ext3, ext4); never FAT16, tmpfs, devfs, procfs or the initramfs.
- **I11. The tests never touch the originals.** The tests never change the test disk's original ext3/ext4 files (`hello.txt`, `big.txt`, `docs/`, `link`, `extents.bin`). They work under `/os`, `/periodic.txt` and `/shell.txt`.
- **I12. Clean means consistent.** On an ext2 volume, `StateClean` on disk implies that the on-disk metadata is complete and consistent (§2.3).

## 6. Write order and what a stop leaves (kernel level)

### ext3/ext4

| Point | On disk | Host `e2fsck -fy`, then `-fn` | Our next writable mount |
|---|---|---|---|
| Before any writable mount | clean | `-fn` clean directly | nothing |
| Writable mount, no change | `needs_recovery`, empty log | `-fy` clears the flag; `-fn` 0 | empty-log recovery clears the flag |
| Change < 5 s old, no sync | new data maybe in free blocks; metadata in memory only | previous committed state; overwrites inside a file may show new bytes (ordered mode) | same |
| After a periodic sync or `sync` | log holds T, home blocks stale | replays T; `-fn` 0 | replays T |
| Inside a commit (commit block not flushed) | torn tail | T dropped | same |
| Inside a checkpoint | log still valid | replays again | same |
| Inside `Detach` (commit → checkpoint → clear flag → flush) | one of the rows above | final state | final state |
| After `Detach` / `Quiesce` | clean | `-fn` 0 directly | nothing |

### ext2

| Point | On disk | Next boot |
|---|---|---|
| Change < 5 s old (after `BeginChange`'s flush) | not clean; write-ordered (Part 4 rules) | read-only until `e2fsck -fy` |
| After the periodic `Sync`, `sync` or `Detach` | clean and consistent (I12) | read-write; `-fn` 0 |
| Inside `Sync` (before the clean bit is flushed) | not clean | read-only until `-fy` |

## 7. Edge cases and errno

| Case | Result |
|---|---|
| `mount -t ext4 vda4 P` on a volume the core writes | 0, `rw` |
| Core refusal (bad journal, errors, orphans, ...) | 0, `ro`, core log line; changes `EROFS` |
| Replay `Corrupt` | 0, `ro`, "run e2fsck" line, nothing written (D5) |
| `-t ext4 vda3` / `-t ext3 vda4` / `-t ext2 vda4` | `ENOENT` |
| Instance already mounted elsewhere | `EBUSY` |
| A change on a read-only mount | `EROFS` (VFS, before the driver) |
| Volume full, or a change too big for one transaction | `ENOSPC` |
| I/O error in a change or commit | `EIO`; journal aborted; later changes `EROFS`; `/proc/mounts` still `rw` (D3) |
| ext2 I/O error in a periodic `Sync` | no caller; the volume stays not clean; retried every 5 s; one `Writeback:` warning per failure streak |
| `umount` with an open file, a working directory or a mount inside | `EBUSY`, nothing written |
| `umount` when `CloseJournal` fails | `EIO`, still mounted. The core aborts the journal, so a second `umount` gives 0, and the volume still needs recovery. |
| Read-only reopen fails after a clean close | `umount` 0, logged; the next `mount` gives `EIO` |
| `sync` on an aborted journal | 0 (the core writes nothing) |
| `Detach` fails at shutdown | `KERN/W: Shutdown: a filesystem did not close cleanly`; the next writable mount replays (ext3/ext4), or the next boot mounts read-only (ext2) |
| Wall clock unavailable or jumping | the core's own 5 s rule may not act; the tick-based task still bounds it |
| A long write holds the lock | the pass waits; the core still commits at a quarter of the journal |

## 10. Risks for the implementer

- **The 5 s window.** `sleep 8` leaves 3 s of margin. The task and `sleep` count the same ticks.
- **New kernel task.** If `ps`/`top`/procfs count scheduler tasks, a new task may shift expected output. The console's status task is the precedent; check `top.py`, `workers.py` and the `ps` expectations.
- **`cp` of 2 MiB on AArch64 TCG** adds seconds to the session; watch `SHELL_TIMEOUT_SECONDS`.
- **Shared disks.** `STORAGE` and `SHELL` may share a disk. That is safe: the shell part's read-write mount replays a dirty volume, and every check reads files the tests own (I11).
- **Root writes during the 8 s sleep.** The root must not be written after the periodic pass and before the stop; nothing in the session does.
