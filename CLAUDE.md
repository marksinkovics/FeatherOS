# FeatherOS — agent quick start

Hobby kernel for **x86-64 and AArch64**, booted by Limine, freestanding C/C++ + ASM, built with CMake/Ninja via `build.sh`, run and tested in QEMU. Read this first; open the docs below only when the task needs them.

- Known hard limits: 16 KiB kernel stacks (guard-paged pool), 1024 pages per process, 32 descriptors per process (64 open disk files system-wide), TCP rings of at most 256 KiB each way (64 KiB receive window unscaled), 4 out-of-order TCP ranges, a listen backlog of 16, `poll` on at most 64 descriptors, 16 pseudo-terminal pairs, FAT16 long names ASCII-only and at most 63 characters, `/tmp` and `/etc` together at most 128 entries and 4 MiB, `/etc` a RAM copy of the initramfs whose edits are lost at reboot (stopgap; better design in `docs/ideas.md`, "A persistent `/etc`"), 63-page user stack, only the top of the heap can be returned to the kernel (no `mmap`), ≤16 program args in 63 chars, program path included (double quotes group words), program files ≤1 MiB, environments ≤1 KiB and 32 variables, no console end-of-file key, no `long double` arithmetic on AArch64 (no compiler runtime), sin/cos/tan imprecise above about 10^6, 16 threads per process with 63-page stacks, no per-CPU run queues, `KLogger` not locked.

## Branches

- `main` — default branch with M1–M13, M15, M20, M23 and M24, each squash-merged from a feature branch; M21 is complete on `feat/embedded_swift`, where M25 is in progress.
- Do feature work on `feat/<topic>` branches cut from `main`, and squash-merge each one back into `main`.

## Layout

- `src/kernel/` — architecture-neutral kernel: `kernel.cpp` (startup), `scheduler.*`, `process.*`, `syscall.*`, `console.*`, `exception.*`, `panic.*`, `klogger.*`, `smp.*` (secondary CPU startup), `cpu.*` (per-CPU index), `kernel_test.*` (in-kernel QEMU test hooks), plus `memory/`, `filesystem/` (USTAR, FAT16, VFS), `network/` (virtio-net, Ethernet, ARP, IPv4, IPv6, ICMP, ICMPv6, neighbor discovery, UDP, sockets, settings and name servers), `virtio/` (shared virtqueue), `elf/`, `framebuffer/`, `input/`, `storage/`, `sync/` (spinlocks), `time/`, `string/`.
- `src/kernel/arch/{x86_64,aarch64}/` — entry, GDT/IDT/TSS or vectors/GIC, paging, context switch, syscall entry, UART, RTC, PIC/PIT or Generic Timer, virtio PCI/MMIO.
- `src/libc/` — the C library: C headers in `include/`, freestanding C++ implementation, `start.cpp` (`_start` → `main`), `arch/<arch>/setjmp.cpp`.
- `src/user/` — userspace programs (`shell`, `calc`, `date`, `echo`, `upper`, `uptime`, `ls`, `cat`, `write`, `rm`, `test_program`, …) the shared `command_line.h`, and the ABI the C library and kernel tests use (`syscall_abi.h`, `syscall.h`).
- `tests/test_boot_matrix.py` — QEMU integration matrix (Python `unittest`). `tests/unit/` — Catch2 host tests.
- `tools/` — `smoke_test.py`, `qemu_run.py`, `create_test_disk.py`, `quality.sh`, font generation. `toolchains/` — cross-compiler builder. `configs/<arch>/` — Limine configs.

## Commands

```sh
./build.sh --arch x86_64 all        # build + ISO + run in QEMU (aarch64 also needs QEMU_EFI if not auto-found)
./build.sh --arch <arch> test       # headless serial smoke test
./build.sh test-all                 # full QEMU matrix, both arches
./build.sh unit-test                # host Catch2 tests
./build.sh --arch <arch> benchmark  # cppbench against swiftbench in QEMU
BUILD_TYPE=Release ./build.sh --arch <arch> test  # -O2 instead of the default -O0 -g
bash tools/quality.sh --fix         # clang-format/tidy, ruff, shellcheck/shfmt
```

You must always pass an architecture (`--arch` or `ARCH=`). Feature tests are env toggles, e.g. `SHELL_TEST=ON`, `SCHEDULER_TEST=ON`, `SMP_TEST=ON`, `STORAGE_TEST=ON`, `NETWORK_TEST=ON`, `PANIC_TEST=ON` (add `QEMU_CPU=max` for the hardware-protection CPU model; `QEMU_NO_REBOOT=1` makes interactive runs exit on reset; the window scales with its size by default, `QEMU_ZOOM=0` shows the guest's 1024x768 unscaled), which map to `FEATHEROS_*_TEST` CMake options. Outputs go under `build/<arch>/`.

## Change workflow: lint before testing

Get the code lint-clean **before** running any QEMU smoke test or `test-all`. Alternating between smoke runs and lint runs wastes runs, because lint fixes change code that then has to be tested again.

1. Edit the code.
2. Build **both** architectures (`./build.sh --arch x86_64 build` and `./build.sh --arch aarch64 build`). clang-tidy reads `build/<arch>/compile_commands.json` and only checks architectures that have been built, so a build that skips one architecture leaves that architecture's `arch/` code unlinted.
3. Run `bash tools/quality.sh --fix`, then fix every remaining diagnostic by hand. Repeat until `bash tools/quality.sh check` passes. The pre-commit hook runs this same check.
4. Run `./build.sh unit-test`, then the relevant `./build.sh --arch <arch> test` modes, then `./build.sh test-all`.
5. If a test failure forces a code change, write the fix to be lint-clean and run `quality.sh check` before re-running the test.

`tools/check.sh` does steps 2-4 in one command, printing one line per stage and only the relevant lines of a failure (full logs in `build/check/`): `tools/check.sh --modes "SHELL" --arch x86_64`, `--arch both`, `--matrix`. Every smoke test saves its whole session to `build/<arch>/smoke-output.txt`, so a failure is read there instead of re-run; in the matrix, a failed case also keeps its session as `build/<arch>/smoke-output-<test name>.txt`. A shell failure ending in "(stopped at the N s limit)" ran out of time; check how far the session got. Cadence: while working on a step, unit tests plus the affected smoke mode on x86-64; at the end of a step, that mode on both architectures; the full matrix once per milestone part, not per step.

## Conventions

- Shared code goes in `src/kernel/`. Anything CPU- or board-specific goes under `arch/<arch>/`. Never share GDT/TSS/IDT concepts with AArch64. Full rules: "Architecture Boundaries" in `docs/roadmap.md`.
- Put implementations in `.cpp` files and only declarations in headers; templates are the exception.
- Keep comments minimal: only for education (hardware quirks, non-obvious invariants) or when the code can't be understood without them. Never describe what a function does; that goes stale when the code changes.
- Namespaces are `FeatherOS::<Subsystem>`, with PascalCase functions. clang-format uses LLVM style, 4-space indent, 100 columns.
- Early logging and panic must not allocate. Physical addresses use explicit 64-bit types, and code must not hard-code physical memory addresses (obtain them from the Limine memory map).
- Every feature should land with tests on **both** architectures: a QEMU case in `test_boot_matrix.py` and, where logic is host-testable, a unit test.
- To add a user program, create `src/user/<name>.cpp` with a `main` and add `<name>:<name>` to `FEATHEROS_PROGRAMS` in `src/user/CMakeLists.txt` (a Swift one: `src/user/<name>.swift` with top-level code, in `FEATHEROS_SWIFT_PROGRAMS`). Use libc, not raw syscalls, unless the program tests the kernel ABI itself. Code shared between programs goes in a header with declarations and a `.cpp` listed in `featheros_user_support` (and in `tests/unit/CMakeLists.txt` when host-tested). A missing POSIX call belongs in `src/libc/`, documented in `docs/posix.md`.
- When a milestone completes, update `docs/roadmap.md` (mark it Complete and add a summary), `docs/development.md` (user-facing details), and the Status section above.
